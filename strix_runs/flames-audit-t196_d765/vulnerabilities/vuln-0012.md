# Attacker-controlled QR pairing payload becomes the device's active gateway with no destination validation or origin confirmation

**ID:** vuln-0012
**Severity:** HIGH
**Found:** 2026-09-15 06:58:55 UTC
**Target:** Flames Android application (`ai.hermes.flames`, Flutter/Dart), repository source at audit root
**Endpoint:** Pairing flow: QrScannerScreen -> ServerProfileCubit.addFromPairingPayload -> GatewayClient.connect
**Method:** N/A
**CWE:** CWE-346
**CVSS:** 7.1
**Confidence:** Medium
**Fix Effort:** Medium

## Description

The Flames Android app pairs with a gateway by scanning a QR code (or pasting the same JSON into a manual-entry dialog). The payload is entirely attacker-controlled and its `gatewayUrl` field becomes the device's active gateway destination with only a scheme check — any `http`/`https` host is accepted, no allowlist, no same-origin check and no rejection of URL user-info. The app then persists the destination and immediately connects and authenticates to it, showing the user only a success message containing attacker-chosen text. The chosen origin gains the device's remote tool-execution channel (arbitrary readable file access, clipboard, notifications/OTP, screen tree) and can invoke ungated side-effecting tools.

## Impact

A hostile QR code (printed, pasted into a chat, or handed to the user as "pair with your gateway") silently makes an attacker-controlled origin the device's active gateway. After pairing, that origin receives the device's full agent tool manifest and can issue tool-call frames that the app executes: `read_device_file` reads any path the app can read (its permission check is hardcoded to allow), `clipboard_read` reads the clipboard, `read_recent_notifications` and `extract_latest_otp` read notification content and one-time passcodes, `ui_find_elements` reads the foreground screen's accessibility tree, and several Tier-1 tools perform ungated device side effects (clipboard write, memory write/delete, local notifications, geofence, background service). Pairing also overwrites the stored `llm_base_url`/`llm_api_key` pair, so the app's own LLM and text-to-speech traffic is repointed to the attacker origin. The user is never shown which origin they paired with. The user's previously stored LLM API key is not itself transmitted to the attacker origin, because the base URL and key are always rewritten together from the same payload; a leak of a key the user re-enters afterwards is possible but requires that later user action.

## Counterevidence

The strongest argument against this finding is that scanning a pairing code is itself a deliberate user consent action, so the user chose to pair with whatever the code contains and nothing is "unauthorized". This does not neutralize the issue: the app never discloses the counterparty being consented to. The success message echoes the payload-supplied `profileName` while the origin is never rendered, so the user cannot tell a legitimate gateway from an attacker origin, and the destination-confusion variant (`https://trusted.example@pair.evil.example`) additionally lets the payload string name a trusted host while the socket contacts a different one. Consent without a disclosed counterparty is not informed consent, and the same parser is fed by a paste dialog where the JSON is even easier to disguise.

A second argument is that the pairing token is supplied by the same payload, so no secret of the user's leaks to the attacker origin. This is correct and is why this report does not claim the user's stored LLM API key is exfiltrated: the base URL and API key are always written as a matched pair from the same payload (`server_profile_cubit.dart:128,140-145`; `secure_storage_service.dart:281-288`), and no split write was found. The impact is therefore scoped to what the hostile origin gains — the device's remote tool-execution channel plus the repointed LLM/TTS destination — rather than to credential theft. A leak of a user key is possible only if the user later re-enters their own key while the attacker profile is active, which requires a further user action and is not counted toward the severity.

A third argument is that Android blocks cleartext by default (the manifest declares no `usesCleartextTraffic` and no `network_security_config`), so the `http` variant would fail closed and the cleartext-interception concern is moot. This narrows only the cleartext variant; it has no effect on the `https`/`wss` variants, which are fully accepted by the same check. Whether `dart:io`'s socket layer honours Android's network security policy could not be established statically in this environment (no device, no emulator, external documentation lookup unavailable), so the cleartext path is reported as an additional risk rather than as a demonstrated interception.

Finally, the repository's own tests treat `http://192.168.1.50:18789` as a valid pairing payload, showing that plaintext LAN pairing is a deliberate design choice rather than an oversight. That is why no HTTPS-only patch is proposed: it would break intended behaviour, and the recommended control is destination confirmation plus rejection of user-info instead.

Checked for and not found: any host allowlist, same-origin comparison against the existing configuration, user-info handling, destination preview, confirmation dialog, or warning that names the origin anywhere in the pairing path (`lib/domain/tools/pairing/`, `lib/presentation/screen/pairing/`, `lib/presentation/screen/server_profiles/`). Also checked and ruled out: an alternative non-QR path that sets the base URL with weaker validation — the only other writers are the settings reset to defaults and the user-typed Add-Profile form, and no registered tool writes the base URL or API key, so a paired gateway cannot re-point the destination through the tool channel.

## Confidence Rationale

Unconfirmed, not dynamically validated. The environment provides no emulator, no adb and no running app instance, and the Dart/Flutter SDK present cannot execute on this host architecture, so the parser, the profile write, the WebSocket connect, the authentication frame and the tool dispatch could not be executed or observed. Every hop in the chain was verified by reading the cited source lines; the static evidence is complete and mutually consistent, but no runtime observation confirms the end-to-end behaviour.

## What Would Change This Severity

A dynamic reproduction in which a hostile QR origin receives the authentication frame and then successfully executes `read_device_file` or `clipboard_read` would confirm the high rating; conversely, if the app were shown to display the resolved destination origin and require explicit confirmation before persisting or connecting, or to reject non-HTTPS destinations outright, the finding would drop to informational. Confirmation that Android blocks the cleartext variant while the app still accepts any HTTPS host would leave the rating unchanged.

## Technical Analysis

## 1. Decode path — the only destination control

`QrScannerScreen._handleBarcode` feeds every scanned code to `PairingParser.parse`:

```dart title=lib/presentation/screen/pairing/qr_scanner_screen.dart startLineNumber=147 endLineNumber=167

  if (_isProcessing) return;
  _isProcessing = true;

  final result = widget.parser.parse(
    rawBarcode,
    currentTime: widget.currentTime,
  );

  result.fold(
    (failure) {
      _isProcessing = false;
      if (!mounted) return;
      AppToast.error(context, failure.message);
    },
    (payload) {
      if (!mounted) return;
      widget.onPayloadScanned?.call(payload);
      Navigator.of(context).pop(payload);
    },
  );
}
```

The same handler is reachable from the manual paste dialog (`_showManualInputDialog`, `qr_scanner_screen.dart:170-258`; submit at `:247-251` calls `_handleBarcode(text)` at `:250`), so no camera is required.

`PairingParser.parse` contains the sole destination validation in the entire pairing path:

```dart title=lib/domain/tools/pairing/pairing_parser.dart startLineNumber=53 endLineNumber=62
final uri = Uri.tryParse(rawGateway);
final isValidHttpUrl = uri != null &&
    (uri.scheme == 'http' || uri.scheme == 'https') &&
    uri.hasAuthority;

if (!isValidHttpUrl) {
  return const Left(
    ParseFailure('Invalid pairing payload: gatewayUrl must be a valid HTTP/HTTPS URL'),
  );
}
```

The predicate enforces only a scheme from a two-element set and a non-empty authority. It does not require `https`, does not compare the host against an allowlist or the currently configured origin, and never inspects `uri.userInfo`. Consequently `https://trusted.example@pair.evil.example` passes validation while the socket is opened to host `pair.evil.example` — the visible part of the string can name a trusted host that is not the host contacted.

The payload schema carries the destination, the credential and the display name from the same untrusted source (`lib/domain/entities/pairing/pairing_payload.dart:7-22`), and freshness is attacker-controlled: `PairingPayload.fromJson` defaults a missing `timestamp` to `DateTime.now()` (`pairing_payload.dart:51`) and `isExpired` (`:87-96`) then compares against that default, so a payload that omits `timestamp` and `expiresAt` never expires.

## 4. Authority granted to the destination

## Proof of Concept

1. The attacker prepares a pairing QR whose JSON contains `gatewayUrl` pointing at an origin they control (for example `https://pair.evil.example`), a `token` value, a reassuring `profileName` such as `Office Hermes Gateway`, and deliberately omits `timestamp`/`expiresAt` so the payload never expires.
2. The victim opens the app's Chat screen and taps the QR scan button (`chat_qr_scan_button`), or opens Settings and taps Scan QR, and scans the attacker's code — the application's normal, advertised pairing flow. The same payload can alternatively be pasted into the manual input dialog.
3. `PairingParser.parse` accepts the payload because the only destination check admits any `http`/`https` authority.
4. The app creates a new server profile, marks it active and overwrites the stored `llm_base_url`/`llm_api_key` settings pair with the payload values.
5. The app immediately opens a WebSocket to the attacker origin and sends the authentication frame containing the payload token.
6. The only feedback to the victim is a success snackbar reading `Paired with Office Hermes Gateway`; the destination origin is never displayed and no confirmation is requested.
7. After authentication the attacker origin receives the device tool manifest and can issue tool-call frames that the app executes, including `read_device_file` (any readable path), `clipboard_read`, `read_recent_notifications`, `extract_latest_otp`, `ui_find_elements`, and the Tier-1 side-effecting tools.
8. Destination-confusion variant: a payload with `gatewayUrl` set to `https://trusted.example@pair.evil.example` passes the same check and the connection is established to `pair.evil.example`, so even a user who reads the payload string sees a trusted-looking host that is not the host contacted.

## Remediation

1. Require explicit user confirmation of the destination origin before a pairing payload is persisted or connected. Before calling the profile cubit, display the resolved origin (scheme, host and port as they will actually be contacted) and require an affirmative action; abort pairing on cancel. The confirmation must render the host that the socket will use, not the raw payload string, so user-info confusion is visible.

2. Reject payloads whose `gatewayUrl` carries user-info. In `PairingParser.parse`, after parsing the URI, fail when the user-info component is non-empty. No legitimate gateway URL in this codebase uses user-info — the credential travels in the authentication frame — and rejecting it removes the destination-confusion class entirely.

3. Decide and enforce the transport policy for pairing deliberately. Pairing currently accepts `http` by design, which is exercised by the existing tests that treat `http://192.168.1.50:18789` as valid; a blanket HTTPS-only rule would break the intended LAN pairing flow and must therefore be a product decision rather than a silent parser change. If plaintext LAN pairing is retained, restrict it explicitly to private-range hosts and require HTTPS/WSS for any other destination, so a hostile public origin cannot be paired over cleartext.

4. Apply the same validation to the manual paste entry point and to the Settings entry point, so a pasted payload cannot bypass the confirmation added for the camera flow.

5. Treat the gateway destination as a security-sensitive setting: when an incoming payload would change an already-configured active destination, require re-confirmation and surface a prominent notice identifying the previous and new origins.

6. Consider constraining the authority granted to a newly paired gateway. The remote tool channel currently exposes arbitrary readable file access, clipboard content, notification/OTP content and the foreground screen tree to whichever origin authenticated; scoping those tools per-profile, or requiring in-app approval for the highest-impact tools regardless of tier, limits the blast radius of any future pairing compromise.

## Fix Verification

No patch is attached to this report, deliberately. The gates below could not be cleared in this environment, so the fix is described in remediation prose only rather than shipped as an applyable suggestion.

Security closure: not applicable — no patch was produced. The identified root cause is that the pairing destination is neither validated against an allowlist nor disclosed to the user before it is persisted and authenticated; a correct fix must therefore add a confirmation of the resolved origin before `addFromPairingPayload` is called, and reject user-info in the parser.

Bypass review (reasoned, not executed): the pairing path has two entry points that must both be covered — `chat_screen.dart:1199` and `settings_screen.dart:158` — and the manual paste dialog (`qr_scanner_screen.dart:250`) reaches the same parser, so a fix applied only to the camera flow would be bypassable by pasting. Rejecting user-info closes only the destination-confusion variant; it does not by itself stop a payload that simply names the attacker host directly, which is why confirmation is the primary control. A HTTPS-only parser rule was considered and rejected: the repository's own tests assert `http://192.168.1.50:18789` is a valid pairing payload (`test/domain/tools/pairing/pairing_parser_test.dart:42-60`, and `test/integration/e2e_fase2_gateway_test.dart:590`), so an unconditional HTTPS requirement would break the intended LAN pairing flow — that is a product decision, not a safe unilateral patch.

Preserved behaviour: not verified. The confirmation step changes the observable flow of the pairing widgets and would require updating existing widget and integration tests that currently expect pairing to complete after a single scan (`test/integration/e2e_fase2_gateway_test.dart:614-619`, which asserts `Paired with Camera Node` and `Connected` immediately after `triggerScan!`). Those tests cannot be run or updated here.

Repository checks: not run. The Flutter/Dart toolchain present in this environment is an x86-64 SDK that cannot execute on this host (its dynamic loader is absent), so `flutter test`, `dart analyze` and the repository's layout checks could not be executed. Gate 4 is therefore an explicit, acknowledged gap, and it is the main reason no `fix_after` is attached.

## Assumptions

Static, source-only assessment: no emulator, no adb and no running application instance were available, and the Flutter/Dart SDK present in the environment cannot execute on this host architecture, so no hop could be exercised at runtime. The reported behaviour is derived entirely from reading the cited source lines. The attack additionally assumes the victim performs the app's normal pairing action (scanning or pasting the attacker's payload) and that the app is in gateway mode for the remote tool channel to be live; pairing itself switches the app into gateway mode in the same handler.
