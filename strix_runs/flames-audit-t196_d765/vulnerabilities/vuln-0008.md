# Tier-2 OTP extraction tool bypasses the app's own sensitive-notification filter and transmits a live second-factor code off-device without per-use confirmation

**ID:** vuln-0008
**Severity:** MEDIUM
**Found:** 2026-09-15 06:36:26 UTC
**Target:** /workspace/flames-audit-t196 (Flames Android application, package ai.hermes.flames)
**Endpoint:** agent tool: extract_latest_otp
**Method:** N/A (in-app agent tool invocation, not HTTP)
**CWE:** CWE-863
**CVSS:** 4.8
**Confidence:** Medium
**Fix Effort:** Trivial

## Description

The Flames agent tool `extract_latest_otp` extracts a live one-time passcode from another application's notification and returns the code to the configured large-language-model endpoint, while the application's own privacy filter deliberately excludes those same OTP and banking notifications from its sibling notification-reading tool. The tool is classified Tier 2 "permissioned", which means it executes automatically once Notification Listener access has been granted a single time, with no per-use user confirmation — so the one control the application built to keep second-factor codes away from the model is bypassed by a path that then transmits the code off the device.

## Impact

A live second-factor code — together with the sending application's name, package identifier, and a body snippet — is extracted from another application's notification and transmitted off the device to the configured large-language-model endpoint, and on the gateway path to the remote Hermes server, without any per-use user confirmation. Because the extraction path never consults `isSensitive`, the application's own exclusion of OTP, banking, and password notifications from the model is defeated: the one notification class the product deliberately withholds from the model is the exact class this tool hands over. Nothing binds the extracted code to a transaction the user initiated, and no confirmation step exists, so the code is disclosed to a third party that has no functional need for it. The repository's own end-to-end test further has the model persist the extracted code into the long-term memory vault via the auto-executing Tier-1 `save_memory` tool, and that vault is a plain, unencrypted SQLite database (`flames_memory.db`), which extends the window in which the code is readable at rest. On a device that receives OTPs for banking, email, or account recovery, this converts a short-lived authentication secret into a durable third-party disclosure.

## Counterevidence

Argued both directions and tested each claim against the source rather than accepting it:

1. "It is a documented, intentional feature." TRUE — the tool description, the `notification_triage` skill text, and the repository's own integration test all establish that OTP extraction is intended. This does NOT neutralise the finding, because the objection addresses the feature's existence while the finding is about the control around it. The app's own sibling path deliberately excludes these exact notifications, and the feature ships with the weakest gate the registry has (auto-execute). A sensitive feature can be intended and still be under-gated.

2. "The user granted notification access." TRUE but does not neutralise it. That grant is a single coarse OS-level toggle whose system-dialog wording covers reading notifications generally; it is not a per-use consent for a specific live second-factor code, and it is never re-requested. The design distinction the app itself draws is per-use: Tier 3 tools prompt the user every time via the approval sheet. This tool never does.

3. "The user configured the LLM endpoint themselves." TRUE and it genuinely limits the threat model — the OTP goes to an origin the user chose, not to an arbitrary attacker origin. It does NOT eliminate the risk: it converts the finding from "attacker exfiltration" to "unnecessary third-party disclosure of a live credential," and most deployments point at a cloud service.

4. "The model must cooperate (stochastic)." TRUE — a real trigger is not guaranteed and depends on model behaviour. This is a genuine constraint and the reason the finding is medium rather than high; it is reflected in the CVSS complexity rating rather than treated as a kill.

5. "The OTP extraction was not executed." TRUE — no device was available. This is the reason for medium confidence, not a reason to suppress.

What was checked and found NOT to exist (i.e. no control that rules this out): no binding check ties the extracted code to a transaction the user initiated — `extractLatestOtp` accepts only `appFilter` and `limit`; no per-use confirmation exists on the Tier-2 path; `isSensitive` is never consulted on this path; the result JSON always carries the `otp` field when `found` is true; the memory vault is a plain SQLite database (`flames_memory.db`) with no application-level encryption, and the repository's own integration test has the model persist the extracted code there via the auto-executing Tier-1 `save_memory` tool.

## Confidence Rationale

Static-only trace. No emulator, no adb and no running app instance were available, so neither the OTP extraction nor the outbound request body was executed or observed. Specifically unverified at runtime: that a real notification reaches the in-memory listener buffer with an extractable code, that the tool-call round trip actually places the `otp` field in the outbound HTTP body, and that the configured endpoint is a third-party cloud service for a given deployment. Each hop was confirmed by reading source, and the two transmission sinks were confirmed to consume the tool result verbatim.

## What Would Change This Severity

Confirming that the model can be induced to call `extract_latest_otp` by attacker-controlled text the device ingests (a hostile notification body, a fetched web page, or an imported skill) and that the resulting code reaches the outbound request body would raise this to high, because the OTP would then be exfiltrated by a third party rather than merely disclosed to a user-chosen endpoint. Conversely, demonstrating that the configured endpoint is consistently a self-hosted server under the user's own control, or that the model in practice refuses to extract authentication codes, would lower the severity toward low.

## Technical Analysis

**The two notification paths disagree.** `NotificationTriageService` exposes one private loader and two public readers. `getRecentNotifications` (`lib/data/datasources/tools/chat/notification_triage_service.dart:242-262`) filters the loaded entries with `.where((e) => matchesAppFilter(e, appFilter) && !isSensitive(e))` at `:249-252`. `extractLatestOtp` (`:277-310`) calls the same loader directly at `:284` — `final entries = await _loadEntries(limit: limit);` — and never invokes `isSensitive`. Both therefore read the identical in-memory notification buffer, but only the first applies the application's sensitive-content exclusion. The `_sensitiveKeywords` list at `:87-118` includes `otp`, `one-time`, `verification code`, `password`, `passcode`, `pin`, `cvv`, `cvc`, `bank`, `transaction`, `payment`, `balance`, `account number`, and `credit card`, and `isSensitive` at `:119-122` matches them against the lowercased `title` and `body`. By construction, every notification this tool is designed to find is a notification the sibling tool refuses to return.

**The extracted secret is returned in full.** `extractOtp` (`:137-151`) applies a contextual pattern `(?:code|otp|pin|passcode|verification)[^\d]{0,24}(\d{4,8})` and falls back to any bare four-to-eight digit group, so the match is not limited to notifications that literally say "OTP". On a hit, the service returns an `OtpExtractionResult` (`:290-297`) carrying the live code plus the sending application's display name, package name, timestamp, and a 120-character body snippet. `OtpExtractionResult.toJson` (`lib/domain/tools/chat/notification_triage_service.dart:79-89`) emits `'otp': otp` unconditionally, so the secret is present in the serialized tool result. There is no redaction, masking, or truncation of the code at any point.

**No binding check ties the code to the user's own action.** `extractLatestOtp` accepts only `appFilter` and `limit` (`:277-280`); there is no transaction identifier, no correlation with a login the user initiated, and no verification that the user is the party the code is meant for. The tool returns whatever the newest matching notification contains, so an attacker-crafted notification can be used to have the agent surface the attacker's own code, and a code received on the victim's device for an attacker-initiated login can be harvested without any check that the user requested it.

**The gate is auto-executing.** The tool is registered at `lib/domain/tools/chat/tool_registry.dart:851` with `securityTier: SecurityTier.tier2Permission` at `:871` and `checkPermission: () => service.checkPermission()` at `:872`. The enforcement point at `:250-255` evaluates that permission once and never re-prompts; `checkPermission` in turn merely confirms the OS-level Notification Listener grant (`notification_triage_service.dart:196-207`), which is a single coarse toggle the user sets once. The agent loop confirms the tier semantics: `lib/presentation/screen/chat/cubit/agent_cubit.dart:759-765` pauses for human approval only when `registered.securityTier == SecurityTier.tier3Hitl`, and Tier 1 and Tier 2 fall through to `emit(ExecutingTool(...))` followed by `executeTool` at `:766`. The tier is read from a local constant fixed at registration and is never derived from model output, a gateway frame, a skill package, or a tool result, so the classification itself cannot be downgraded remotely — but the classification as written is the defect.

**Two independent off-device sinks consume the result.** In the local ReAct loop the result string is appended as `ChatMessage(role: 'tool', toolCallId: callId, name: toolName, content: resultStr)` at `agent_cubit.dart:820-825`; `_messages.map((m) => m.toWireJson())` at `:906` serializes it, and `toWireJson` (`lib/domain/entities/chat/chat_message.dart:116-127`) writes `content` verbatim into the map; the resulting `messagesToSend` is passed to `_llmRepository.streamCompletion(...)` at `:923-930`. The endpoint is the user's configured model base URL, defaulting to `https://api.openai.com/v1` at `:121` and overridden from profile settings at `:482-483` and `:491-492`. Separately, when the call originates from a gateway `tool_call_request`, `lib/domain/services/gateway/gateway_rpc_receiver.dart:148` executes the same tool and the success branch at `:166-171` returns the full parsed result map — including the `otp` field — to the remote Hermes server via `gatewayClient.sendToolCallResponse`. Both sinks are governed by the same single tier constant, which is why reclassification closes both.

**The value is also persisted.** `agent_cubit.dart:826` calls `_persistMessages()`, which writes the session history through `lib/data/datasources/local/chat/chat_local_datasource.dart:113-121` into FlutterSecureStorage — so the chat-history copy is encrypted at rest and is not itself a plaintext exposure. The stronger persistence path is the one the project's own integration test encodes: `test/integration/e2e_fase3_intelligence_test.dart:280-293` has the model follow an `extract_latest_otp` result with a `save_memory` call whose content is the extracted code. `save_memory` is Tier 1 and auto-executes (`tool_registry.dart:884`), writing into the memory vault, which is a plain SQLite database (`lib/data/datasources/local/memory/sqlite_memory_datasource.dart:16`, `databaseFileName = 'flames_memory.db'`) with no application-level encryption, so the code would be readable at rest beyond its normal validity window.

**Intent.** The repository is explicit that this is a deliberate capability — the tool description says it "Extracts the latest OTP code from captured notifications", the `notification_triage` skill is documented as reading notifications and extracting security OTP verification codes (`lib/domain/services/skills/skills_registry_service.dart:610-625`), and the deployment documentation states that Flames "requires Notification Listener permission to capture 2FA OTP codes" (`docs/connecting-to-remote-hermes.md:270`). The finding is therefore not that the feature exists, but that the control around it is inconsistent with the application's own privacy design: the product deliberately withholds these notifications from the model on one path while handing the extracted secret to the model on another, and the path that hands it over is the one that requires no per-use confirmation.

## Proof of Concept

1. On the device, grant Flames Notification Listener access once (Android Settings, Notification Access). This is the only consent step, and it is never re-requested.
2. Cause any installed application to post a notification containing a one-time passcode, for example a bank or mail application delivering a login verification code.
3. In a Flames chat session, send a message that induces the agent to call the `extract_latest_otp` tool — for example a request to retrieve the latest verification code.
4. Observe that the tool executes immediately with no approval dialog. The Tier-2 classification means `agent_cubit.dart` never enters the `WaitingApproval` branch.
5. Observe that the tool result is appended as a `role: tool` message and included in the subsequent request body, so the passcode is transmitted to the configured model endpoint.
6. Optionally observe the same result being returned to the remote gateway server when the call originates from a gateway `tool_call_request` frame.

## Remediation

1. Reclassify `extract_latest_otp` from Tier 2 (permissioned, auto-execute) to Tier 3 (HITL) in `lib/domain/tools/chat/tool_registry.dart`, so every extraction requires an explicit per-use user confirmation showing the tool name and arguments. This is the minimal change that closes both the local-model and gateway transmission paths, because all three `executeTool` call sites consult the same registration-time tier constant.
2. Update the tier expectation in `test/domain/tools/chat/tool_registry_test.dart`, which currently asserts the Tier-2 classification, and add a regression test asserting that the tool cannot execute without approval.
3. Prefer, as a follow-up, never transmitting the passcode to the model at all: have `extract_latest_otp` return only a non-secret acknowledgement (for example, that a code was received and from which application) and surface the actual code in a local user interface element, so the secret never enters a prompt, a request body, or a gateway response.
4. Do not attempt to close this by applying the `isSensitive` keyword filter inside `extractLatestOtp`: every OTP notification matches those keywords, so the tool would permanently report that no code was found. The keyword list is a topic filter for the general notification reader, not a redaction primitive for the extraction tool.
5. Treat the notification-listener grant as a coarse capability rather than consent for any individual secret: audit the other notification-derived tools (`read_recent_notifications`) for the same assumption, and consider an explicit, revocable in-app toggle specifically for second-factor extraction.
6. Consider whether the long-term memory vault should accept secret-shaped content at all, given that the auto-executing `save_memory` tool can persist an extracted code into an unencrypted SQLite database; at minimum, exclude OTP-shaped values from memory writes or encrypt the vault.

**Gate 2 — Security closure.** Re-traced both sinks through the patched source. The tier value is read from a local constant at registration (`tool_registry.dart:871`) and never from remote input, so it cannot be influenced by a gateway frame, skill package, tool result, or model-supplied argument. **Gate 3 — Bypass review.** Enumerated every caller of `ToolRegistry.executeTool` (`grep -rn "executeTool" lib/`): exactly three — `agent_cubit.dart:611`, `agent_cubit.dart:766`, `gateway_rpc_receiver.dart:148` — and all three consult `securityTier`, so no ungated caller exists.
