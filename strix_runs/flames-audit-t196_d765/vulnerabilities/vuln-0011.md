# Any co-resident app can auto-submit an agent turn through the exported share-target activity, with no user confirmation and an attacker-chosen URL fetch

**ID:** vuln-0011
**Severity:** MEDIUM
**Found:** 2026-09-15 06:52:45 UTC
**Target:** /workspace/flames-audit-t196 (Flames Android application, package `ai.hermes.flames`)
**Endpoint:** ai.hermes.flames/.MainActivity (ACTION_SEND share target)
**Method:** INTENT (android.intent.action.SEND)
**CWE:** CWE-940
**CVSS:** 4.0
**Confidence:** Medium
**Fix Effort:** Low

## Description

The exported, non-permission-guarded `MainActivity` of the Flames Android app declares `ACTION_SEND` / `ACTION_SEND_MULTIPLE` share-target filters. Text delivered through that channel is consumed by the `receive_sharing_intent` plugin and routed into the chat pipeline, which **submits it to the on-device agent as a user turn with no confirmation step of any kind**. Any installed app — requiring no Android permissions — can therefore drive a full agent turn (a request to the configured LLM endpoint plus the on-device ReAct tool loop). When the shared text contains an `http`/`https` URL, the app also issues that request from the victim's device before submitting, and the URL host is not validated beyond scheme and non-empty host, so loopback, RFC1918 and link-local addresses are reachable. **This finding is unconfirmed and not dynamically validated: the assessment was source-only, with no emulator, device or `adb` available.**

## Impact

A co-resident app with no permissions and no special access can cause the Flames agent to run a turn that the user never initiated, and can choose a URL that the device then fetches.

1. **Unattended agent turn.** `AgentCubit.sendMessage` is invoked with attacker-authored text (`chat_screen.dart:1505`, `:1522`). The turn is persisted to the chat session, sent to the configured remote LLM endpoint, and drives the ReAct tool loop (`agent_cubit.dart:502-536`, `:864`). The attacker's text arrives as an ordinary user turn with no provenance marking, so the model has no basis to treat it as untrusted. Consequences are bounded by the existing tier gates: Tier-3 tools still stop at the human-in-the-loop modal, and the agent's reply is rendered in the app's own chat view. The demonstrable consequence is unauthorized consumption of the user's paid LLM quota and an unattended tool loop operating on the user's behalf, with the attacker's text as the instruction source.

2. **Attacker-chosen outbound request.** When the shared text contains a URL, the app fetches it from the device before submitting (`chat_screen.dart:541-542`). The only validation is scheme (`http`/`https`) plus non-empty host (`lib/domain/tools/chat/url_reader_service.dart:59-70`); there is no loopback, RFC1918, link-local or hostname restriction, and `followRedirects: true` means a redirect can move the target after the check. `http://127.0.0.1:<port>/`, `http://192.168.x.x/`, `http://10.x.x.x/` and `http://169.254.169.254/` all pass. The response body is reduced to text and embedded in the prompt that is sent to the LLM (`shared_payload.dart:74-81`), so content from an internal endpoint that the attacker cannot reach directly can be pulled into the model context. This is a blind primitive — the attacker does not receive the response — and it is a client-side fetch, not a server-side one, so it is reported as a secondary aspect of this finding rather than as a standalone high-severity issue.

3. **Reachability and visibility.** `MainActivity` is `launchMode="singleTop"`, so when Flames is already running the payload is delivered to the live instance via the plugin's `NewIntentListener` without a restart. When Flames is not in the foreground, starting the activity brings the Flames window to the front, so the launch itself is visible; the turn that follows is not announced. The attacker cannot hide the window, and the reported severity reflects that.

## Counterevidence

Actively attempted to break the chain and could not find a control on it:

(a) **Confirmation gate** — searched the whole repository for a dialog, consent step, settings toggle or feature flag on this path (`confirm`, `consent`, `showDialog`, `autoSubmit`/`autoSend`, and every key in the settings key list). None exists; `_submitSharedPayloads` calls `_handleSubmitted` directly. The only user-visible signal is the Flames window opening, which does not gate the submission.

(b) **Is the subscription actually live?** — confirmed `ChatScreen` is mounted in production: `app_router.dart:28` (`initialLocation: '/splash'`) → `splash_screen.dart:66-108` → `main_navigation_shell.dart:34-42`, where `ChatScreen()` is the first entry of an `IndexedStack`, so `initState` runs and both the cold-start drain (`share_target_cubit.dart:32-35`) and the live subscription (`:26-30`) are active without user interaction.

(c) **Is one of the two delivery paths dead?** — both are wired: cold start via `getInitialMedia` (plugin `:72`) and live via the `NewIntentListener` (plugin `:188`, `:205-208`), with `launchMode="singleTop"` meaning an already-running instance receives the payload rather than restarting. The plugin is registered in `GeneratedPluginRegistrant.java:129`.

(d) **Does the handler run before user action?** — yes. The only guards are `payloads.isNotEmpty` and `mounted`, both of which hold. There is no mode check that would prevent it: `_mode` defaults to `ChatMode.direct` (`chat_screen.dart:76`), and the gateway branch has its own sink at `:1522`.

(e) **Does the fetch really happen, and does the validator really permit internal hosts?** — yes; `validateUrl` (`lib/domain/tools/chat/url_reader_service.dart:59-70`) checks only scheme and host presence, and `extractUrl` (`:10-37`) also accepts bare domains, so no private-range exclusion is applied anywhere. One honest correction to the briefing this finding was based on: Dart's `dart:io` HTTP client does not consult Android's `NetworkSecurityPolicy`, so the absence of `usesCleartextTraffic` does not block the `http://` case — that conclusion is reasoned from the platform's client implementation, not observed, and is the weakest link in the fetch leg. If it were wrong, the `https://` and hostname forms would still work and the auto-submit leg would be unaffected.

(f) **Is the shared text marked as untrusted?** — partially, and not in a way that helps. `[LINK CONTEXT]` (`shared_payload.dart:55`) is applied only to the fetched link block (`:74-81`); the attacker's raw text remains present unmarked in the same prompt, and the non-URL kinds (`text`, `file`, `image`, `video`) receive no marker at all (`toChatPrompt`, `:36-49`).

(g) **Could an unprivileged app do this anyway?** — partly, and this constrains severity. The attacker cannot read the fetched response, so the fetch is blind and is not an exfiltration primitive. The tool loop is bounded by the existing tier gates, so a Tier-3 tool still stops at the approval modal. What is not otherwise available to an arbitrary app is an unattended agent turn against the user's own configured credentials and device tools, triggered without the user touching Flames. The severity below reflects that bounded consequence rather than a worst case.

**Constraints that lower severity, stated plainly:** the Flames window becomes visible when the app is not already foregrounded; the fetch is blind to the attacker; and no tool invocation was demonstrated, only the turn that could lead to one. The report is therefore scoped to the unauthorized turn and the attacker-chosen request, both of which are deterministic from the source.

## Confidence Rationale

Static-only trace. The audit environment provided no Android device, emulator or `adb`, so no intent was delivered, no agent turn was observed, and no outbound request was captured. Every hop of the chain was verified by reading the source (manifest, plugin Kotlin, Dart service, cubit, screen, cubit-to-agent handoff), and the absence of a confirmation gate was established by repository-wide search. The specific unverified steps are runtime behaviours: that the injected intent reaches `onNewIntent`/`onCreate` with the extra intact, that the Flutter engine is live at that moment, and that Dart's HTTP client issues the cleartext request despite Android's default cleartext policy. Runtime confirmation on a device would be required to raise confidence to high.

## What Would Change This Severity

Demonstrating on a device that the injected share intent reliably produces an LLM request carrying the attacker's text, or that the fetched response from a loopback/private address reaches the model context, would raise the severity. Conversely, evidence that Android's cleartext policy blocks the fetch leg on current platform versions would narrow it to the HTTPS/hostname case, and a product decision that share intents should auto-submit (with the user's informed consent recorded in settings) would lower the auto-submit leg to informational.

## Technical Analysis

## Root cause

`MainActivity` must be exported to serve as the launcher entry point, but the same component also declares share-target intent filters and carries no guarding permission, so the share channel is reachable by any third-party app:

```xml title=android/app/src/main/AndroidManifest.xml startLineNumber=57 endLineNumber=92
<activity
    android:name=".MainActivity"
    android:exported="true"
    android:launchMode="singleTop"
    ...
    <intent-filter>
        <action android:name="android.intent.action.SEND"/>
        <category android:name="android.intent.category.DEFAULT"/>
        <data android:mimeType="text/*"/>
    </intent-filter>
```

The manifest additionally declares `SEND` for `image/*` and `*/*` and three matching `SEND_MULTIPLE` filters (lines 83-108). `MainActivity` has no `android:permission` attribute, and no caller-identity check exists anywhere in the Android sources — a repository-wide search for `getCallingActivity`, `getCallingPackage`, `Binder.getCallingUid`, `checkCallingPermission` and `getReferrer` returns no matches. Explicit intents do not need to match an intent filter at all, so the attacker does not even depend on the filter declarations; they are cited because they establish the component as a legitimate share target.

## CWE selection

Recorded as **CWE-940 (Improper Verification of Source of a Communication Channel)**. The defect is that the app consumes an IPC message from an unauthenticated, unverified sender and acts on its content as though it were user input; the missing authorization is a consequence of that missing source verification, and CWE-862 would describe the broader exported-component family already recorded separately for the action-extra channel. CWE-940 names the specific broken control here.

## Controls examined and found absent

- No confirmation dialog, user tap, settings toggle, feature flag or consent gate anywhere on the intent → `sendMessage` path (repository-wide search for `confirm` / `consent` / `autoSubmit` and for any share-related preference key returned nothing; the only settings keys in `settings_keys` concern LLM, gateway, geofence, overlay, NFC, TTS and ambient settings).
- No allowlist, sanitisation or provenance marking applied to the shared text. A `[LINK CONTEXT]` prefix exists (`shared_payload.dart:55`) but is applied only to the fetched link block at `:74-81`; the attacker's raw text remains present unmarked in the same prompt, and for the non-URL cases (`text`, `file`, `image`, `video`) no marker is applied at all (`toChatPrompt`, `shared_payload.dart:36-49`).
- No caller verification in the Android layer (searches listed above).
- No destination restriction on the fetch beyond scheme and host presence.

## Distinctness from the action-extra channel

This is a separate attacker-controlled input and a separate consumer from the `extra_flames_action` path recorded elsewhere for this component. `MainActivity.extractActionFromIntent` (`MainActivity.kt:73-85`) reads only `extra_flames_action`; the share payload never passes through it. Here the input is share-sheet content (`EXTRA_TEXT` / `EXTRA_STREAM`) and the consumer is the share-target pipeline terminating in `chat_screen.dart`. The two share the same root exported-component weakness but are independently fixable — an allowlist on the action extra does nothing for the share text, and the Dart-side fix proposed here does nothing for the action extra.

## Proof of Concept

Source-only audit: no device, emulator or `adb` was available, so the steps below describe the attack as it would be mounted against a real installation and were established by complete static trace, not executed.

1. Install any third-party app on the same device as Flames. It requires no Android permissions — only the ability to start an activity and send an intent, which every app has.
2. From that app, construct an intent with action `android.intent.action.SEND`, type `text/plain`, and extra `Intent.EXTRA_TEXT` set to the attacker's chosen text. Set the component explicitly to `ai.hermes.flames/.MainActivity` so no intent-filter matching is required.
3. Call `startActivity` with `FLAG_ACTIVITY_NEW_TASK`. The Flames window comes to the front.
4. The plugin's Kotlin `ACTION_SEND` branch reads `EXTRA_TEXT` and publishes it as the JSON `path` field on the `receive_sharing_intent/events-media` channel; the cold-start path also exposes it via `getInitialMedia`.
5. `ShareTargetService.mapFile` wraps it in a `SharedPayload`; `ShareTargetCubit` emits `ShareTargetReceived`.
6. `ChatScreen`, mounted as the first tab of the main shell, consumes the payload and calls `_submitSharedPayloads` with no user interaction.
7. If the text contains an `http`/`https` URL (or a bare domain), the app fetches that URL from the device — with no host restriction, so loopback and private addresses are accepted — and embeds the returned text in the prompt.
8. `_handleSubmitted` calls `AgentCubit.sendMessage(prompt)`, which appends the attacker's text as a `role: 'user'` message and runs the ReAct loop: a request is made to the configured LLM endpoint and any tool calls the model returns are executed under the existing tier gates.

To demonstrate the outbound-request leg specifically, set `EXTRA_TEXT` to `http://127.0.0.1:8080/` (or any reachable RFC1918 / link-local address) and observe that the app issues the GET before any user interaction. No dynamic confirmation of this was possible in the audit environment.


## Remediation

Treat content arriving through a share intent as untrusted input that requires explicit user action, rather than as a message the user sent.

1. Remove the automatic submission. When a share payload arrives, stage the generated prompt in the chat composer and let the user review and send it themselves; do not call the submit path from the share handler. This single change removes both the unattended agent turn and the unattended fetch, because the fetch happens inside the same handler.
2. Keep the user-visible notification that content was staged, so the feature remains discoverable and the user understands what was added to the composer.
3. Apply the same treatment to the cold-start path and the live path, since both reach the same handler.
4. Independently of the share flow, restrict the URL reader's destination policy: reject loopback, link-local, and private-range addresses, resolve the host and re-check after each redirect, and disable automatic redirect following so that the destination cannot change after validation. This protects the `read_web_page` agent tool as well, which shares the same reader and the same gap.
5. Where a shared payload is later shown to the model, mark it as externally supplied content so the model can distinguish it from user instructions; do not rely on the surrounding prose for that signal.
6. Add a regression test asserting that delivering a share payload does not reach the message-submission path without a user action.

## Fix Verification

The fetch leg is closed by the same change: the `reader.fetchReadableText(url)` call at `:542` sits inside the method whose only exit was the submission, and with the submission removed the fetched content is staged rather than sent — so the unattended outbound request no longer occurs either. The PoC could not be executed against the patched code (no device, emulator or `adb`), so closure is established by trace, not by re-running the attack.

**Gate 3 — Bypass review.** (i) *Sibling call sites*: `_handleSubmitted` has other callers (voice submission at `:1556` via `_handleVoiceSubmitted`, the composer's `onSubmitted` at `:2817`, and the send button at `:2885`). Those are genuine user-initiated actions and are intentionally left unchanged — the patch removes only the programmatic call, which is the one with no user action behind it. (ii) *Equivalent sinks*: `_handleVoiceSubmitted` is the voice path and is user-initiated; the gateway-mode sink at `:1522` is inside `_handleSubmitted`, so it is covered by the same removal. (iii) *Alternate input classes checked by reasoning*: `SEND_MULTIPLE` (multiple payloads) — the batch prompt is staged the same way, since the patch sits after prompt assembly and covers every payload shape; `EXTRA_STREAM` / `content://` payloads — these reach `mapFile` and produce a `SharedPayload` whose prompt is likewise only staged; an empty or whitespace-only payload — `mapFile` returns null for empty paths (`share_target_service.dart:106`) and `buildSuggestedPrompt` returns `''` for an empty list, which `_handleSubmitted` already rejected at `:1496` and which now simply stages an empty string; a payload delivered while the user is mid-composition — the staging assignment replaces composer content, which is a usability consideration, not a security one, and is preferable to silent submission. (iv) *Residual exposure*: the patch does not restrict who may deliver a share intent, so an attacker can still cause Flames to come to the foreground and populate the composer with chosen text; that is the standard behaviour of a share target and is bounded to what a user would see before sending. Fully excluding third-party delivery would require removing the share filters, which is a product decision recorded in the remediation steps rather than something this minimal patch should assume.

**Gate 4 — Preserved behaviour.** The share feature still works end-to-end: the payload is still received, still enriched with fetched link text when a URL is present, and still turned into the same prompt string via `SharedPayload.buildSuggestedPrompt` / `toPromptWithLinkContext`; only the final dispatch step changes. The legitimate user-initiated paths (composer send button, keyboard submit, voice submission) are untouched. Error semantics are preserved — the `try`/`catch` around the fetch still falls back to the raw prompt (`:560-562`), and the `mounted` guard still runs first so a disposed widget is never touched. The new `_textController.text` assignment is safe with respect to widget state: the controller already has a listener registered at `:183` (`_onTextChanged`), which itself calls `setState` when the text becomes non-empty, so the assignment must **not** be wrapped in `setState` — the patch assigns directly and lets that existing listener enable the send button (`_isComposing`).

**Gate 5 — Repository checks (not executed — gap).** The Flutter/Dart toolchain is not installed in the audit environment: `dart analyze` fails with `No such file or directory` (confirmed by running it), and there is no Android SDK or emulator, so the change was neither analysed nor compiled nor tested. The relevant existing test is `test/presentation/screen/share/cubit/share_target_cubit_test.dart`, which asserts cubit states (`ShareTargetListening` → `ShareTargetReceived`) and is unaffected because the patch does not touch the cubit; `test/integration/e2e_fase6_skills_test.dart:100-130` exercises the share pipeline up to `suggestedPrompt` and likewise does not assert submission. No existing test asserts the auto-submission behaviour, so no test needed updating — but equally, no test currently protects the fix. **Explicit gaps: gates 2 and 5 were verified by inspection only; no compiler, no analyser, no test run, no device.** A reviewer should run `dart analyze` and `flutter test` and add a widget assertion that delivering a share payload leaves `sendMessage` uncalled.

**Narrowest complete change.** Two contiguous hunks in one file, no new imports, no unrelated refactor. The fix is placed at the single point where the untrusted share payload would otherwise become an agent turn, which is the narrowest place the invariant can be enforced without changing the share pipeline itself.

## Assumptions

Assumes the standard co-resident-app threat model for exported Android components: a malicious app is installed on the same device as Flames. It needs no Android permissions and no special access. Assumes the user has configured the app for normal use (an LLM profile exists in direct mode, or a gateway connection exists in gateway mode); without a usable transport the turn is attempted but cannot complete. Assumes Flames has been launched at least once so its chat screen and DI graph exist. The attacker cannot hide the Flames window when the app is not already in the foreground, so the launch itself is user-visible.
