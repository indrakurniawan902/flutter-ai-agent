# Release build signed with the public Android debug keystore

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-09-15 05:15:23 UTC
**Target:** /workspace/flames-audit-t196 (Flames Android application, package ai.hermes.flames)
**Endpoint:** android/app/build.gradle.kts
**CWE:** CWE-321
**CVSS:** 4.2
**Confidence:** Medium
**Fix Effort:** Low

## Description

The release build type is configured to sign with the shared Android debug keystore instead of a private release key. Because the debug keystore and its password are public and identical on every development machine, the shipped release APK is signed with a key any third party can reproduce. Anyone holding that key can build an APK that Android accepts as a legitimate update to this application, and the application can never be published to Google Play under a trustworthy signing identity.

This finding is based on static source review only and is **unconfirmed, not dynamically validated** — no APK was built and no update was delivered in this assessment.

## Impact

The application's release artifacts are signed with a key that is not secret. If the APK is distributed outside Google Play (which the permission set and feature set make likely for this product), an attacker can produce a tampered APK that carries the same signing identity and installs as an in-place update over the legitimate app, with no signature-mismatch warning to the user. Such an update runs with the application's identity and privileges and can read the app's private data — including the locally stored chat transcripts, the agent memory vault, and the Action Center store — and can exercise every device capability the app has been granted (notifications, accessibility, location, camera, Health Connect). The app also cannot be published to Google Play with this signing configuration, so the release pipeline is not production-ready.

## Counterevidence

Actively checked for constraints that would neutralise this finding. (1) A release `signingConfigs` block or a `key.properties` file could have existed and overridden the debug config — neither is present anywhere in the repository, and `key.properties` is only referenced in `.gitignore`. (2) Gradle could have injected a signing config through a property or an included build — `android/build.gradle.kts` only sets repositories, build directories and JVM targets, and `gradle.properties` contains no signing properties. (3) The impact could be limited to "cannot publish to Play", which would make it informational — but the update-hijack consequence is real for any non-Play distribution channel, which is the realistic channel for this app given its permission set. The genuine constraint that lowers severity is that exploitation requires the attacker to already be able to deliver an APK to the victim and the victim to accept the install, so this is not a remotely triggerable issue on its own; that precondition is reflected in the `attack_complexity` and `user_interaction` metrics rather than being used to dismiss the finding. No dynamic validation was possible, so the exploitability of the update path is reasoned from Android's documented signing behaviour rather than demonstrated.

## Confidence Rationale

The code fact is certain and directly observable — the release build type is configured with `signingConfig = signingConfigs.getByName("debug")` and no release signing material exists in the repository. What is not dynamically validated is the downstream consequence: no APK was built, no signing certificate was inspected, and no update-over-install was attempted, because this assessment had no Android SDK, emulator or device. The conclusion that a same-certificate APK installs as an update relies on documented Android platform behaviour rather than on an executed proof.

## What Would Change This Severity

Confirmation that release APKs built from this repository are actually distributed to users outside Google Play would raise the severity, because the forgeable update channel would then be live rather than hypothetical; conversely, evidence that the project only ever builds debug artifacts locally (and that the release configuration is unused scaffolding) would reduce this to an informational build-hygiene observation.

## Technical Analysis

`android/app/build.gradle.kts` declares a `release` build type whose only configuration is a signing config that resolves to the built-in `debug` keystore:

```kotlin title=android/app/build.gradle.kts startLineNumber=35 endLineNumber=41
    buildTypes {
        release {
            // TODO: Add your own signing config for the release build.
            // Signing with the debug keys for now, so `flutter run --release` works.
            signingConfig = signingConfigs.getByName("debug")
        }
    }
```

The `signingConfigs` block that a real release build needs is absent from the file, and no `key.properties` file is present in the repository (the Android `.gitignore` already lists `key.properties`, `**/*.keystore` and `**/*.jks`, showing the release keystore was intended but never wired up). No `isMinifyEnabled` / `isShrinkResources` settings are declared for the release build type either.

The debug keystore is generated by the Android SDK at `~/.android/debug.keystore` with the well-known alias `androiddebugkey` and password `android`; it is identical across all installations. Any party can therefore sign an APK that carries the same certificate as a legitimate release build of this app. Android treats an APK with the same `applicationId` (`ai.hermes.flames`) and the same signing certificate as an in-place update to the installed application.

Note that this defect is independent of the source code's runtime security posture — it is a build/release configuration issue, and the fix is confined to the Gradle file plus an out-of-repository keystore.

## Remediation

1. Generate a private release keystore and store it outside the repository, with the credentials in a `key.properties` file that is already covered by the Android `.gitignore`.
2. Declare a `signingConfigs { create("release") { ... } }` block in `android/app/build.gradle.kts` that loads `key.properties`, and point the `release` build type at that config instead of `debug`.
3. Make the release build fail loudly when `key.properties` is absent, so a debug-signed release can never be produced by accident again.
4. Enable code shrinking and resource shrinking for the release build type (`isMinifyEnabled = true`, `isShrinkResources = true`) and add a ProGuard/R8 keep rules file.
5. Store the release keystore and its passwords in the CI secret store, and use Play App Signing if the app is distributed through Google Play.
6. Rotate the signing identity before any public release — an already-distributed debug-signed build cannot be safely upgraded in place.

## Fix Verification

Gate 1 — Applicability: `fix_before` is a character-for-character copy of `android/app/build.gradle.kts` lines 35-41 as read from the checkout, and the replacement is confined to that block (it stays inside the existing `android { }` extension, before the `kotlin { }` block). No syntax/type check could be executed: this environment has no Flutter SDK, no Android SDK and no Gradle, so `./gradlew` cannot run (gate 4 is an explicit gap). The Kotlin DSL shape used (`signingConfigs { create(...) }`, `keyAlias`/`keyPassword`/`storeFile`/`storePassword` as `String?` properties, `isMinifyEnabled`/`isShrinkResources` on the release build type) matches the current Android Gradle Plugin Kotlin DSL used by the rest of the file.

Gate 2 — Security closure: after the patch the release build type resolves `signingConfigs.getByName("release")`, whose material comes exclusively from `key.properties`. The `require(...)` guard means a build without that file throws during configuration instead of silently producing a debug-signed artifact, so the previous failure mode (a release APK signed with the public debug key) is unreachable. The `debug` signing config is no longer referenced by any build type.

Gate 3 — Bypass review: the change is checked against the other paths that could still produce a debug-signed release — the `debug` and `profile` build types (which legitimately keep the default debug signing), the `flutter { source = "../.." }` block (no signing role), and `android/build.gradle.kts` / `gradle.properties` (no signing properties; verified). `key.properties` is already ignored by `android/.gitignore`, so the fix does not introduce a secret into version control. The residual risk that a developer commits a keystore is outside this file.

Gate 4 — Repository checks: NOT RUN — no Flutter/Android/Gradle toolchain is installed in the assessment environment, so neither `./gradlew :app:assembleRelease` nor a Gradle configuration check could be executed. This gate must be run by the repository owner before merging.

Gate 5 — Preserved behaviour: `flutter run --release` and `flutter build apk --release` continue to work for anyone who has created `key.properties`; only the previously-implicit fallback to the debug keystore is removed, which is the intended fail-closed behaviour. No public API, error semantics, or runtime code is touched. Narrowest-complete-change judgement: the patch is the smallest repository-native change that fully removes the public-key signing path — it adds no unrelated refactors, and the only new out-of-repository artefact it depends on (`key.properties`) is already anticipated by `.gitignore`.

## Assumptions

Assumes the release APK produced from this repository is distributed to users (via sideload, an MDM/enterprise channel, or a third-party store) rather than only being built locally for development. Google Play would reject an APK signed with the debug key, so the Play-distribution scenario is not affected. The update-hijack scenario additionally assumes the victim installs an attacker-supplied APK that presents itself as an update.
