# Screen text read from any app is injected into the agent prompt as a tool result with no untrusted-data framing

**ID:** vuln-0004
**Severity:** HIGH
**Found:** 2026-09-15 05:38:51 UTC
**Target:** ai.hermes.flames — Flutter AI agent workstation (Android), repository root (source-only audit)
**Endpoint:** ui_find_elements (tool channel ai.hermes.flames/accessibility_inspector)
**Method:** TOOL
**CVSS:** 8.1
**Confidence:** Medium
**Fix Effort:** Low

## Description

The Android agent can read the accessibility tree of whatever app is in the foreground and hand that text to the LLM as a tool result (`ui_find_elements`). The tree is rendered from the window of *another* app, so its text is authored by that app, not by Flames or by the user — yet nothing marks it as untrusted, and the result is placed verbatim in the model's context. The codebase already ships a prompt-injection scanner (`SkillSecurityScanner`) but applies it only to imported skill text, so screen content reaches the model unframed and unscanned. The same model can then call Tier-1 tools that need no user approval (`save_memory`, `clipboard_write`) and read Tier-1/2 sensitive data (clipboard, location, files, notifications, OTP, health, contacts). Memory entries are re-injected on later turns as a `role: "system"` message, which converts transient screen text into persistent, highest-authority instructions. **Unconfirmed, not dynamically validated** — this is a source-only audit; there is no emulator, no device and no running app, so no payload was executed against a live model.

## Impact

Attacker-authored text on screen gains instruction authority inside a tool-calling agent. A malicious app that renders a crafted window (or a hostile web page / message rendered in any app) and waits for the user to invoke the agent can attempt to steer the model into data-collecting tool calls, and to persist the payload into the memory vault where it is re-injected as a system message on every subsequent turn. Because the injected text can invoke `save_memory` (Tier 1, auto-executed, no approval) and `clipboard_write` (Tier 1), the payload can be made persistent and can be staged for collection by a co-resident app. Read tools that need no approval include `list_device_files`, `read_web_page`, `calendar_list_events`, `external_camera_list`, `search_memories` and `list_memories`. The concrete end-to-end result is model- and payload-dependent and was not demonstrated: the attacker cannot directly observe the agent's replies, so exfiltration requires the model to also follow a second injected step that writes the data to an observable sink (clipboard, an external URL, or a WhatsApp message).

## Counterevidence

Strongest case against: (1) Capture is explicit-call-only — `captureTree` has exactly one caller, reached solely through the `getScreenTree` method channel, and `onAccessibilityEvent` never pushes anything, so the app cannot be made to read the screen in the background; the user must actively run the agent against the screen. (2) Prompt injection is probabilistic — a given model may ignore the injected text entirely, and nothing here demonstrates compliance; no payload was executed. (3) The attacker cannot read the agent's replies, so a successful injection yields influence, not directly observable data theft; exfiltration needs a second, independent step. (4) The user grants the accessibility permission deliberately, so the data source is consent-gated rather than covert. (5) A `role: "tool"` result is the standard OpenAI channel and many models do treat tool output as lower-trust data by convention. Checked and found absent: no input validation, sanitisation, injection scan, untrusted-data marker, or content-security control of any kind on this path; `_sanitize` was confirmed to be display formatting only; the repo's own scanner was confirmed to have exactly one production caller, on a different input class.

## Confidence Rationale

Static-only trace, executed nowhere. There is no emulator, no `adb`, no device and no running app in this environment, and no Dart/Flutter or Android SDK, so the tool result was never produced by a live capture and no model was ever induced to act on it. The code path from `captureTree` through the method channel, the serializer, the registry and into the wire message is fully traced with verified line references, and the absence of framing/scanning is established by exhaustive search, but the two end-to-end steps (model compliance, and the second-step exfiltration) are reasoned, not observed. The password-field behaviour is additionally device-dependent and was not verified on any hardware.

## What Would Change This Severity

Demonstrating on a device that a crafted foreground window reliably induces a Tier-1 tool call (in particular a `save_memory` write, or a `clipboard_read` followed by `clipboard_write`) would raise this to critical; conversely, evidence that the target model consistently treats tool-result content as inert data, or that Tier-1 tools are disabled in shipped configurations, would lower it to medium.

## Technical Analysis

**1. The collected data.** `FlamesAccessibilityService.captureTree()` walks the foreground window and emits `text`, `contentDescription` and `packageName` for every node, with no exclusion of secure fields. The service config enables `canRetrieveWindowContent="true"` and `flagRetrieveInteractiveWindows`, so the tree of any foreground app is readable.

**2. The pull-only path.** Capture is strictly on demand: `captureTree()` is reached only from the `getScreenTree` method-channel handler, which is reached only from the Dart platform wrapper, which is reached only from `findElementsFormatted`. Nothing is pushed to Dart on accessibility events — `onAccessibilityEvent` only records `lastEventPackage`, which is never read. There is no background or continuous collection.

**3. No framing, no scan.** `findElementsFormatted` returns `AccessibilityTreeSerializer.serialize(...)` directly, and that string becomes the tool result content. The only transformation applied is `_sanitize`, which strips newlines/tabs and replaces double quotes with single quotes — a display-formatting step, not an injection control. The repo's own prompt-injection scanner (`SkillSecurityScanner`, twelve patterns including chatml delimiters and instruction overrides) has exactly one production caller, `SkillImportService.buildPreview`, so it never sees screen text. There is no untrusted-data marker anywhere on this path, and the assembled messages are serialized and posted verbatim to the configured chat-completions endpoint.

**4. Amplifier — persistent system-role injection.** `save_memory` is registered as `SecurityTier.tier1Auto`, so the model can write memory with no user approval. On a later turn, matching memories are inserted into the request as a message with `'role': 'system'`, i.e. the highest-authority position available. Attacker-influenced text therefore survives the conversation it arrived in and is re-presented as an instruction to the model.

**5. Missing redaction (observation, not an independent claim).** `captureTree()` never calls `AccessibilityNodeInfo.isPassword()`; the identifier appears nowhere in the Android or Dart trees. Documented Android behaviour is that an accessibility service holding `canRetrieveWindowContent` can read password-field text, and that redaction is device/OEM dependent — so the client-side absence of an exclusion is the only thing this audit can establish. Whether the platform already redacts on a given device was **not** verified here; the fix therefore skips password nodes client-side rather than relying on the platform.

## Remediation

Treat every accessibility-tree result as untrusted data before it becomes a tool result, and stop relying on the platform to redact secure fields.

1. Frame the tool result explicitly at the single point where the tree is turned into text (the data-layer `findElementsFormatted`). Prefix and suffix the serialized tree with a short, unambiguous statement that the block is screen content captured from another app, that it must be treated strictly as data, and that nothing inside it may change the agent's task, tool policy, or disclosures. Leave the empty-tree message unframed so existing behaviour is preserved.
2. Reuse the existing prompt-injection scanner rather than writing a new one. Screen text is the same untrusted class as an imported skill body, so run `SkillSecurityScanner` over the serialized tree and, when patterns match, prepend the matched pattern identifiers so the model and the user can see that the screen contains a suspected payload. Because the scanner is pattern-based and evadable by paraphrase, keep the explicit framing as the primary control and treat the scan as defence in depth.
3. Exclude secure fields on the device side. In `captureTree`, skip nodes whose `isPassword` flag is set, and skip their subtrees, so password and other secure-field values are never collected even if a given device does not redact them.
4. State the data class in the tool description so the model's own tool contract carries the warning, not just the result payload.
5. Apply the same framing to the other untrusted text channels that feed the prompt — notification text, web-page text, and recalled memory entries — and stop injecting recalled memory as a `role: "system"` message, which currently gives attacker-influenced text the highest available authority. This is outside the code changed here and remains open.

## Fix Verification

**Gate 1 — Security closure (reasoned, not executed).** Re-traced the source→sink path through the patched code. The patched `findElementsFormatted` is the only production producer of accessibility-tree text (the platform wrapper's `getScreenTree` is called from exactly that one place, and the only caller of `findElementsFormatted` is the `ui_find_elements` registration), so every non-empty tree now passes through `AccessibilityMessages.untrustedFraming` before it can become tool-result content. All three outcomes are covered: the inactive/not-connected paths return `Left` and never carry tree text; the empty tree returns the unchanged constant; a non-empty tree is framed. The empty-tree short-circuit was added specifically so that the existing exact-match assertion on the canonical empty message still holds. On the device side, `node.isPassword` is checked before any node is added to the result, and `continue` skips the node *and* its subtree, so a secure field's value cannot be collected even where the platform does not redact. **Not executed** — no device and no live model, so closure is established by trace, not by re-running a PoC.

**Gate 2 — Bypass review (reasoned).** Named sibling/alternate inputs checked: (a) the scanner is pattern-based and evadable by paraphrase or encoding — this is why the framing, not the scanner, is the primary control, and the scan result is additive only; (b) the scanner is constructed per call (`AccessibilityTreeInjectionScanner()`), so no cross-turn state or shared mutable state is introduced; (c) `SkillScanResult.isRejected` is deliberately **not** used here — screen text must never be *blocked*, only framed, because dropping a legitimate screen would break the tool, so only `findings` is consumed; (d) the sibling channels that feed the prompt — notification text, web-page text, recalled memory — are **not** covered by this patch and are carried as an open item; (e) the `_truncate`/`_sanitize` display helpers were confirmed not to be injection controls, so no reliance is placed on them. Alternate malicious input classes (chatml delimiters, HTML-comment hiding, instruction override) are all covered by existing scanner patterns, and the framing applies regardless of whether any pattern matches.

**Gate 3 — Preserved behavior (reasoned, not executed).** Exact-string assertions live at the serializer layer and the registry layer, both of which are untouched: the serializer's canonical output test and the registry test that echoes a mocked service string. The data-layer tests assert with `contains` rather than equality, so the added prefix/suffix does not break them; the empty-tree case is short-circuited so its exact-match assertion is unaffected. Public API surface is unchanged: `findElementsFormatted` keeps its signature and still returns `Either<Failure, String>`; only the string's framing changes. Error semantics are untouched. The `ui_find_elements` parameter schema is unchanged, and only its `description` text grows.

**Gate 4 — Repository checks: NOT RUN — explicit gap.** This environment has no Dart SDK, no Flutter SDK and no Android SDK (`dart`, `flutter` are not present on `PATH`; no SDK found under `/opt` or elsewhere on the image), so `dart analyze` on the touched files, `flutter test` for the accessibility/serializer/registry suites, and any Kotlin compilation could not be executed.
