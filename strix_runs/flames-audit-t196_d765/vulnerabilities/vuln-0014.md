# Path traversal in share-intent file handling writes attacker-controlled content outside the app cache directory

**ID:** vuln-0014
**Severity:** MEDIUM
**Found:** 2026-09-15 07:12:48 UTC
**Target:** Flames Android application (ai.hermes.flames) source repository
**Endpoint:** android:exported MainActivity (ai.hermes.flames/.MainActivity) - ACTION_SEND with EXTRA_STREAM content:// URI
**CWE:** CWE-22
**CVSS:** 6.8
**Confidence:** Medium
**Fix Effort:** Low

## Description

The app accepts ACTION_SEND intents from any installed application through its exported MainActivity. The receive_sharing_intent 1.9.0 plugin that consumes those intents resolves an attacker-supplied content:// URI by copying the provider's stream into a path built from the provider-controlled _display_name value, with no sanitisation. A malicious co-resident app can therefore supply a name containing parent-directory segments and have arbitrary bytes written to any path inside the Flames application's private data directory - including all three SQLite databases, the Hive store, and the secure-storage preference files.

## Impact

A malicious application installed on the same device can overwrite arbitrary files inside the Flames private data directory (/data/user/0/ai.hermes.flames/) with arbitrary bytes. Affected targets include the three application SQLite databases (databases/flames_skills.db, databases/flames_chat.db, databases/flames_memory.db), the Hive action-centre store (app_flutter/flames/action_center.hive), and the shared_prefs/ files backing flutter_secure_storage. Consequences: destruction or substitution of the user's persisted agent skills, chat history and memory vault; replacement of the imported-skills table with attacker-authored rows that are loaded at startup and rendered into the agent system prompt; and loss or corruption of the stored LLM API key and server profiles. Code execution was not achieved and is not claimed - no code path in the application loads or executes files from these directories.

## Counterevidence

The strongest case against the finding was that the traversal might be blocked by Android itself or by a control in the application. Both were checked and neither holds.

(1) Android does not constrain _display_name. It is a provider-supplied string with no platform-mandated character set or length limit; ContentResolver.query returns exactly what the provider writes into the cursor. The copy destination is chosen entirely by the plugin.

(2) No sanitisation exists anywhere in the path. The plugin source was searched in full for sanitiz, normaliz, canonical, validate, isAbsolute, contains('..'), startsWith and SecurityException; the only matches are MIME-type prefix comparisons. The Dart consumer at lib/domain/services/share/share_target_service.dart:105-114 performs only an emptiness check, and no other Dart code validates the resolved path.

(3) The premise that an absolute child path discards the parent does NOT hold on Android/Linux - UnixFileSystem.resolve concatenates, so an absolute _display_name stays inside the cache directory. The escape therefore depends specifically on parent-directory segments, which was confirmed by direct reproduction rather than assumed. This narrows the primitive but does not remove it.

(4) The uri.authority == null branch (FileDirectory.kt:131-144) returns a provider-supplied _data value without copying. It was assessed as a read primitive and rejected: content:// URIs normally carry an authority, and an authority-less content:// URI would make ContentResolver.query throw rather than return attacker data. It is not claimed as a read primitive here.

(5) Code execution was explicitly ruled out. Searches of lib/ and android/app/src/main/kotlin/ for Process.start, Runtime.getRuntime, DexClassLoader, System.load, DynamicLibrary.open and dart:ffi return nothing; no artefact under databases/, shared_prefs/ or app_flutter/ is ever loaded or executed. The impact is data integrity only.

(6) Background activity launch restrictions on Android 10+ are a genuine constraint on the attacker and are reflected in the assumptions. They reduce the reliability of the launch but are not a control in the application: an attacker app in the foreground, holding SYSTEM_ALERT_WINDOW, or using a foreground service can still deliver the intent.

(7) The prompt-injection escalation through flames_skills.db was traced statically (skills_local_datasource.dart:115-130 to skills_registry_service.dart:332-372 to agent_cubit.dart:916-921) and is reachable, but it was not executed and is described as a plausible follow-on rather than a demonstrated outcome.

## Confidence Rationale

Unconfirmed, not dynamically validated. No emulator, device or adb was available for this assessment, so the write was never performed against the real application. The evidence is (a) verbatim source of the vulnerable plugin, verified byte-for-byte against the lockfile hash; (b) an offline harness that reproduces the exact path-construction and copy logic and demonstrates the escape outside the cache directory; and (c) a compiled, analyzer-clean behavioural test of the proposed fix. The unverified step is Android runtime behaviour itself - that Context.getCacheDir() yields /data/user/0/ai.hermes.flames/cache and that the kernel resolves the parent-directory segment during FileOutputStream creation. Both follow from documented platform semantics but were not observed on a device.

## What Would Change This Severity

Confirmation on a device that the write lands outside the cache directory and that a substituted flames_skills.db survives into the agent system prompt would raise this to high by establishing a remote-content-to-agent-instruction path; conversely, evidence that the affected databases are recreated or integrity-checked at every startup would lower the integrity impact.

## Technical Analysis

**Reachability.** android/app/src/main/AndroidManifest.xml:57-116 declares MainActivity with android:exported="true" and no android:permission, so any third-party app may start it. Six SEND/SEND_MULTIPLE filters (AndroidManifest.xml:78-108) accept text/*, image/* and */*, so an ACTION_SEND intent with type="image/*" matches.

**Sink.** The receive_sharing_intent 1.9.0 plugin (declared at pubspec.yaml:56, resolved at pubspec.lock:1402-1409) is registered on the Flutter activity and receives the intent through onAttachedToActivity / onNewIntent (ReceiveSharingIntentPlugin.kt:186-208). Its media branch requires a non-null MIME type and calls FileDirectory.getAbsolutePath on the supplied EXTRA_STREAM URI (ReceiveSharingIntentPlugin.kt:86-91, :141).

In FileDirectory.getDataColumn, the uri.authority != null branch queries the provider for the _display_name column and builds the destination directly from the returned value:

```kotlin title=android/src/main/kotlin/com/kasem/receive_sharing_intent/FileDirectory.kt startLineNumber=93 endLineNumber=128
if (uri.authority != null) {
    var cursor: Cursor? = null
    val column = "_display_name"
    ...
    val fileName = cursor.getString(columnIndex)
    targetFile = File(context.cacheDir, fileName)
    ...
    context.contentResolver.openInputStream(uri)?.use { input ->
        FileOutputStream(targetFile).use { fileOut ->
            input.copyTo(fileOut)
        }
    }
    return targetFile.path
}
```

No sanitisation, normalisation or containment check exists anywhere in the plugin - a repository-wide search for sanitiz, normaliz, canonical, validate and the parent-directory token returns only MIME-type startsWith comparisons.

**Why the traversal works.** On Android/Linux, java.io.File(File parent, String child) resolves through UnixFileSystem.resolve, which concatenates parent + "/" + child - an absolute child does not discard the parent (that behaviour is Windows-only). Consequently an absolute _display_name stays inside the cache directory, but a name containing parent-directory segments survives verbatim into the path string and is resolved by the kernel at open() time. With cacheDir = /data/user/0/ai.hermes.flames/cache, a _display_name of ../databases/flames_skills.db produces /data/user/0/ai.hermes.flames/cache/../databases/flames_skills.db, which the kernel resolves to /data/user/0/ai.hermes.flames/databases/flames_skills.db - outside the intended root.

**Application-side consumer.** The path returned by the plugin is surfaced to Dart as SharedMediaFile.path, mapped without validation in lib/domain/services/share/share_target_service.dart:105-114, and rendered into the chat prompt by lib/presentation/screen/chat/chat_screen.dart:531-564. No Dart-layer validation of the resolved path exists on any hop.

**Escalation.** databases/flames_skills.db is opened at startup (lib/data/datasources/local/skills/skills_local_datasource.dart:53-76) and its imported_skills.payload rows are deserialised and registered (:115-130), then rendered into the system prompt by lib/domain/services/skills/skills_registry_service.dart:332-372 and sent to the remote model at lib/presentation/screen/chat/cubit/agent_cubit.dart:916-921. Because the attacker controls the entire file, they can supply a well-formed database matching the known schema and thereby place attacker-authored instructions into the agent's system prompt.

## Proof of Concept

1. Install a malicious application on the same device. It declares an exported ContentProvider (for example authority com.evil.app.provider) whose query() returns a cursor exposing a _display_name column with the value ../databases/flames_skills.db, and whose openFile() returns attacker-chosen bytes.
2. From that application, construct an ACTION_SEND intent with type="image/*" (any non-null MIME type), EXTRA_STREAM set to content://com.evil.app.provider/x, CATEGORY_DEFAULT, and FLAG_GRANT_READ_URI_PERMISSION.
3. Target the exported component explicitly with setClassName("ai.hermes.flames", "ai.hermes.flames.MainActivity") and call startActivity().
4. On Android 10 and later the sending application must be in the foreground (or hold SYSTEM_ALERT_WINDOW) for the activity launch to be permitted; the target app then launches and processes the intent.
5. The plugin queries the provider for _display_name, builds File(cacheDir, "../databases/flames_skills.db"), opens the provider stream and writes the bytes with FileOutputStream, resolving outside the cache directory.
6. Confirm on the device that /data/user/0/ai.hermes.flames/databases/flames_skills.db now contains the attacker-supplied bytes rather than the previous database.

```python title=poc_share_provider_traversal.py
#!/usr/bin/env python3
"""Offline PoC for the share-intent content:// provider path traversal."""
import os
import shutil
import sys

APP_DATA = "/data/user/0/ai.hermes.flames"
CACHE_DIR = f"{APP_DATA}/cache"


def jvm_file_resolve(parent: str, child: str) -> str:
    """java.io.File(File parent, String child) on Android/Linux.

    OpenJDK UnixFileSystem.resolve() concatenates parent + "/" + child and
    UnixFileSystem.normalize() is a no-op, so parent-directory segments survive
    into the path string and are resolved by the kernel at open() time.
    """
    if child == "":
        return parent
    if child.startswith("/"):
        return child if parent == "/" else parent + child
    return parent + "/" + child if parent != "/" else parent + child


class HostileProvider:
    """ContentProvider registered by a co-resident malicious app.

    Both the query() projection and openInputStream() are attacker-controlled.
    """

    def __init__(self, display_name: str, payload: bytes):
        self.display_name = display_name
        self.payload = payload

    def query_display_name(self) -> str:
        return self.display_name

    def open_input_stream(self) -> bytes:
        return self.payload


def file_directory_get_data_column(cache_dir: str, provider: HostileProvider):
    """Mirror of FileDirectory.kt:90-129 (the uri.authority != null branch)."""
    file_name = provider.query_display_name()          # attacker-controlled
    target_file = jvm_file_resolve(cache_dir, file_name)

    with open(target_file, "wb") as fh:                # FileOutputStream
        written = fh.write(provider.open_input_stream())
    return target_file, written


def main() -> int:
    root = "/tmp/poc-flames-traversal"
    shutil.rmtree(root, ignore_errors=True)
    sandbox_data = os.path.join(root, APP_DATA.lstrip("/"))
    cache_dir = os.path.join(root, CACHE_DIR.lstrip("/"))

    for d in (cache_dir, f"{sandbox_data}/databases", f"{sandbox_data}/shared_prefs"):
        os.makedirs(d, exist_ok=True)

    victim = f"{sandbox_data}/databases/flames_skills.db"
    with open(victim, "wb") as fh:
        fh.write(b"SQLite format 3\x00[legit skill rows]")

    display_name = "../databases/flames_skills.db"
    provider = HostileProvider(display_name, b"SQLite format 3\x00[ATTACKER ROWS]")
    resolved, written = file_directory_get_data_column(cache_dir, provider)

    real = os.path.realpath(resolved)
    escaped = not real.startswith(os.path.realpath(cache_dir))
    print(f"provider _display_name : {display_name!r}")
    print(f"File(cacheDir, name)   : {resolved}")
    print(f"kernel realpath        : {real}")
    print(f"escaped cacheDir       : {escaped}")
    print(f"bytes written          : {written}")
    print(f"content now            : {open(real, 'rb').read()!r}")

    # Control: a benign share stays inside the cache directory.
    benign = HostileProvider("IMG_20260101.jpg", b"\xff\xd8\xff\xe0JPEGDATA")
    ok_path, _ = file_directory_get_data_column(cache_dir, benign)
    inside = os.path.realpath(ok_path).startswith(os.path.realpath(cache_dir))
    print(f"benign share inside cacheDir: {inside}")

    return 0 if (escaped and written > 0 and inside) else 1


if __name__ == "__main__":
    sys.exit(main())
```

## Remediation

Validate the resolved share path in the application's own mapping layer before it is used, rejecting any file-backed payload whose path contains a parent-directory segment. The guard belongs at the single point where plugin output is converted into a domain payload, so every consumer inherits it.

Treat the third-party plugin as untrusted: its copy destination is derived from a provider-controlled display name, so no path it returns should be assumed to live inside the cache directory. If an upstream release fixes the issue, upgrade and keep the guard as defence in depth.

Consider additionally constraining the share surface itself, since the exported activity accepts intents from any application. If cross-application sharing is required, validate that each resolved path lies under the expected cache root by comparing canonicalised paths rather than by string inspection alone, and prefer copying the stream into an application-chosen filename instead of one derived from provider metadata.

Finally, review whether the persisted skill store should be trusted input at startup: imported skill instructions are rendered into the agent system prompt, so a tamper-evident or integrity-checked store would limit the effect of any future write primitive.

## Fix Verification

Gate 1 - Applicability. fix_before was copied from the working tree with sed -n '104,114p' lib/domain/services/share/share_target_service.dart and byte-compared; the block is exactly 11 lines and start_line/end_line cover it precisely. dart format --output=none --set-exit-if-changed on the patched file reports no changes needed, so the change is formatter-clean. dart analyze on the patched file in a package with resolved dependencies reports "No issues found!", matching the unpatched baseline.

Gate 2 - Security closure. The guard runs inside mapFile, which is the single mapping point for every share payload: mapMediaFiles (line 95) delegates to it, and both getInitialPayloads (line 68) and the live stream handler in startListening (line 49) reach the prompt only through mapMediaFiles. A payload whose path contains a parent-directory segment is dropped before a SharedPayload is constructed, so it can never reach lib/presentation/screen/chat/chat_screen.dart:531-564 or the agent turn. The write inside the plugin still occurs - the fix removes the path's use, not the plugin's copy - but the attacker-supplied destination is no longer acted upon by the application, and the corresponding prompt entry is suppressed.

Gate 3 - Bypass review. The diff was re-read against the sink rather than the rationale. Alternate input classes were tried: multiple stacked parent segments (a/b/../../../databases/x.db), a parent segment embedded in a longer filename (a..b.png, correctly not flagged), and dot-prefixed hidden files (..hidden.txt, correctly not flagged). Sibling call sites of the mapping helper were enumerated (mapMediaFiles, getInitialPayloads, startListening) and all route through the patched method. The kind gate deliberately exempts text and url payloads, whose values are free text and may legitimately contain the parent-directory token. A real behavioural test of the patched class (compiled and executed) passes 33 assertions covering hostile names, benign names, MediaStore _data paths, text/URL payloads and the repository's existing test expectations. A negative control ran the same hostile inputs through the unpatched method: all three traversal names passed through unmodified, confirming the new test fails without the fix.

Gate 4 - Preserved behavior. Legitimate shares continue to work: cache filenames such as IMG_20260101.jpg, report.pdf and a..b.png are kept; genuine MediaStore _data paths such as /storage/emulated/0/DCIM/Camera/IMG_1.jpg are kept; text and url payloads are never path-checked; mimeType, thumbnail and message are still propagated. The repository's own assertions (test/domain/services/share/share_target_service_test.dart:153-167, and the kind-mapping tests at :108-150) were re-executed against the patched class and still pass.

Gate 5 - Repository checks. dart analyze on the patched file: no issues. The package's full test suite could not be executed because the Flutter SDK in this environment is an x86-64 build on an aarch64 host, and pub.dev is unreachable for dependency resolution. This is an explicit gap: the fix was verified with a standalone package that compiles the patched class verbatim against the real entity and a stub of the plugin's public surface, not with flutter test on the repository.

Narrowest complete change. The fix is confined to the mapping method plus two small private helpers in the same class, uses no new dependencies, and does not alter the plugin, the cubit, the UI or any public signature.

Residual gap (documented, not fixed). The check is a pure-string test and does not resolve symlinks, so a symlink placed inside an allowed directory would not be caught; the plugin's destination is built with a plain string concatenation and no symlink is created by this path. The root cause remains in the third-party plugin, and no upstream release fixes it (1.9.0 is the current published version), so a Dart-layer guard is the only remediation available inside this repository.

## Assumptions

Assumes a malicious application is installed on the same device and is permitted to start the exported MainActivity (on Android 10 and later it must be in the foreground or hold SYSTEM_ALERT_WINDOW for the background activity launch to be allowed). Assumes the user has granted Flames no special privilege beyond normal installation. Assumes the provider supplies a _display_name column; a provider that omits it causes an uncaught IllegalArgumentException in the plugin rather than a write. Impact is confined to the Flames application's own private data directory - a different application's sandbox is not reachable, because the attacker app's UID cannot write outside /data/user/0/ai.hermes.flames/.
