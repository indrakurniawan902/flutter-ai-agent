# Unrestricted file read and unbounded directory enumeration via read_device_file / list_device_files agent tools

**ID:** vuln-0007
**Severity:** MEDIUM
**Found:** 2026-09-15 06:29:20 UTC
**Target:** Flames Android app (ai.hermes.flames) — repository at /workspace/flames-audit-t196
**Endpoint:** agent tool: read_device_file / list_device_files
**Method:** N/A (in-app agent tool invocation, not HTTP)
**CWE:** CWE-22
**CVSS:** 5.3
**Confidence:** Medium
**Fix Effort:** Low

## Description

The agent tools **`read_device_file`** and **`list_device_files`** accept an absolute filesystem path supplied by the language model and pass it to `File(path).readAsBytes()` / `Directory(path).list()` without any containment check against a workspace root. The declared "device workspace" boundary exists only in the tools' prose descriptions and is never enforced in code.

The one gate that was supposed to constrain `read_device_file` is inert: its Tier-2 permission check resolves to a hardcoded `true`. **`list_device_files` is declared Tier-1 (auto-execute) and therefore has no gate at all**, and it accepts `recursive: true`.

Both paths are reachable from remote model output — tool-call arguments are decoded from the model's JSON with no validation and auto-executed. Because untrusted text (notification bodies, remote skill packages, tool results) reaches the model with no data/instruction separation, a prompt-injection payload can direct the agent to read or enumerate files. **Unconfirmed, not dynamically validated** — this is a source-only audit with no emulator, no device and no running app.

## Impact

An attacker who influences the model's tool-call arguments (a remote or compromised model endpoint, a remote skill package, a crafted notification body, or an indirect injection via any tool result) can direct the agent to read and enumerate files as the application's own UID, with no workspace boundary enforced.

**Demonstrated by code path (not runtime-verified):**

- **Unbounded directory enumeration — fully effective.** `list_device_files` is Tier 1 (auto-execute, no gate) and accepts `recursive: true`. It returns names, absolute paths, sizes, modification times and extensions for the whole subtree. Directory listing applies no content filter of any kind, so it enumerates the app's entire private storage — including the `databases/`, `shared_prefs/`, `files/` and `app_flutter/` trees. This discloses the storage layout and reveals which features hold data, which is meaningful reconnaissance for follow-on attacks and is not blocked by any control.
- **Read of NUL-free text files within the app's UID.** `read_device_file` returns any text file the app can open, including application-private XML and JSON. This includes the FlutterSecureStorage backing file under the app's `shared_prefs/` directory (the app constructs `const FlutterSecureStorage()` with no options override at `lib/common/injection/modules.dart:22-23`, so plugin defaults determine the filename; the exact name was not observed on a device). That file holds the **encrypted** credential blobs for the API key, gateway token and server profiles. Because these are ciphertext, this does not by itself disclose the credentials — it discloses the encrypted material, the stored key names, and the existence and structure of the credential store.
- **Filter bypass via the PDF branch.** A path ending in `.pdf` is routed to PDF text extraction *before* the extension denylist and null-byte checks run, and `extractPdfText` applies neither filter. Any file addressed under a `.pdf` name is therefore read with no binary screening at all.

**Explicitly NOT demonstrated, contrary to an earlier draft of this finding:** the plaintext SQLite databases (`flames_memory.db`, `flames_skills.db`, `flames_chat.db`) are **not** readable through `read_device_file`. They are blocked twice over — `db`/`sqlite` appear in the extension denylist, and a real SQLite file contains a NUL byte at offset 15 of its header, which the null-byte sample rejects regardless of filename. Memory-vault contents are also already available to the model through the Tier-1 `list_memories` / `search_memories` tools, so reading the database file would add little.

**Why this is still a finding.** The app intends a workspace boundary — its own bundled skill descriptor states the invariant "read file contents within allowed directories" — and no code enforces it. The absence of containment is the root defect: any future text file the app writes into its private storage (a token cache, a log, an export) becomes immediately readable by model output, and enumeration of the private tree is ungated today. Scope limits, stated honestly: no `READ_EXTERNAL_STORAGE` / `MANAGE_EXTERNAL_STORAGE` is declared, so arbitrary `/sdcard` reads fail on modern Android; impact is confined to the app's own private storage.

## Counterevidence

Actively sought constraints, and **two of them defeated part of my own initial claim** — recorded here rather than hidden.

**Constraints that genuinely limit impact.** (1) The plaintext databases are NOT readable: `db` and `sqlite` are in `_binaryExtensions` (`file_workspace_service.dart:98-124`) *and* any real SQLite file has a NUL byte at offset 15, which `_containsNullByte` (`:133-140`) rejects independently of the filename. My first draft asserted these were readable; that was wrong and has been corrected. (2) Memory-vault content is already reachable by the model through the Tier-1 `list_memories` / `search_memories` tools (`tool_registry.dart:905-945`), so reading the vault file would add nothing. (3) Chat message bodies live in `FlutterSecureStorage`, not in `flames_chat.db`, so the database holds only session titles in any case. (4) No `READ_EXTERNAL_STORAGE` / `MANAGE_EXTERNAL_STORAGE` is declared anywhere under `android/`, so `/sdcard` reads fail on modern Android — broad external-storage access is not claimed. (5) The data belongs to the same user who installed the app; this is not cross-tenant exposure. (6) The attacker must first land influence on the model's arguments; this is not unauthenticated access to a listening service.

**What is NOT a control.** The binary-extension denylist and the null-byte sample do not cover the `.pdf` branch: `readFile` dispatches to `extractPdfText` *before* either check runs (`:159-163`), and `extractPdfText` (`:178-211`) applies neither. The denylist also inspects only the filename extension, so it constrains naming rather than access. Directory enumeration passes through no filter at all. I verified there is no canonicalisation, no base-directory join and no symlink resolution anywhere on either call path, and that `getDocumentsDirectory()` is used only for PDF writes.

**Checked and not reachable as a bypass.** Argument mutation between approval and execution: the Tier-3 HITL sheet renders the real `request.parameters` JSON (`action_approval_sheet.dart:44-45`) and `approveAction()` executes the stored object, so there is no TOCTOU window — moot here, since neither tool reaches HITL. Tier downgrade by remote input: the tier is a local `const` on `RegisteredTool` with no setter, so remote input cannot change it; the defect is the tiers as declared in source.

**Residual.** A symlink planted inside the workspace would defeat a lexical-only fix; my verification exercised that case and confirmed the symlink check is required. A check-to-open TOCTOU swap is theoretically possible but no model-reachable primitive creates symlinks (`export_document_pdf` writes regular files only), so I do not treat it as exploitable.

## Technical Analysis

**1. `read_device_file` — declared Tier 2, gate is a no-op**

Registration at `lib/domain/tools/chat/tool_registry.dart:759-790` declares `securityTier: SecurityTier.tier2Permission` and wires `checkPermission: () => service.checkPermission()`. The parameter is documented as an **absolute file path**. The implementation at `lib/data/datasources/tools/chat/file_workspace_service.dart:77-81` is:

```dart title=lib/data/datasources/tools/chat/file_workspace_service.dart startLineNumber=77 endLineNumber=81
  @override
  Future<bool> checkPermission() async => true;

  @override
  Future<bool> requestPermission() async => true;
```

The registry's only permission gate (`tool_registry.dart:250-255`) therefore always passes:

```dart title=lib/domain/tools/chat/tool_registry.dart startLineNumber=250 endLineNumber=256
      if (SecurityPolicy.requiresPermission(tool.securityTier) &&
          tool.checkPermission != null) {
        final granted = await tool.checkPermission!();
        if (!granted) {
          return Left(PermissionFailure('Permission denied for tool: $name'));
        }
      }
```

**2. `readFile` performs no containment, and the PDF branch skips both filters**

`file_workspace_service.dart:149-175` reads the raw caller-supplied path. There is **no** `startsWith` check, **no** canonicalisation, **no** base-directory join and **no** symlink resolution. `getDocumentsDirectory()` — the only workspace-root accessor — is used solely for PDF *writes* (`lib/data/datasources/skills/doc_builder_skill.dart:86`), never to bound reads. A whole-tree search of `lib/` for containment vocabulary returns no hit on this path.

The two filters that do exist are applied only on the non-PDF branch, and only after the PDF dispatch:

```dart title=lib/data/datasources/tools/chat/file_workspace_service.dart startLineNumber=159 endLineNumber=169
      final ext = _extensionOf(path).toLowerCase();
      if (ext == 'pdf') {
        final result = await extractPdfText(path);
        return result.map((text) => _paginate(text, maxLines: maxLines, offset: offset));
      }
      final bytes = await _fileSystem.readFileAsBytes(path);
      if (_binaryExtensions.contains(ext) || _containsNullByte(bytes)) {
        return Left(CacheFailure('Binary file not readable: $path'));
      }
      final content = await _fileSystem.readFileAsString(path);
```

`extractPdfText` (`:178-211`) reads the file with `readAsBytes` and applies neither `_binaryExtensions` nor `_containsNullByte`. Any path ending in `.pdf` is therefore read with no binary screening.

**3. `list_device_files` — declared Tier 1, no gate at all**

`tool_registry.dart:791-815` registers it at `securityTier: SecurityTier.tier1Auto` with no `checkPermission`, accepting an arbitrary `directoryPath` and `recursive`. `listFiles` (`file_workspace_service.dart:224-281`) calls `Directory(path).list(recursive: recursive)` unbounded, and directory listing applies no content filter.

**4. The "workspace" boundary is prose, not a control**

The tool description says "device workspace directory", and the bundled skill descriptor states the intended invariant — `lib/domain/services/skills/skills_registry_service.dart:643`: "Inspect file paths safely and read file contents within allowed directories." No code implements "allowed directories".

**5. What the filters do and do not block**

`db` and `sqlite` are present in `_binaryExtensions`, and a real SQLite file carries a NUL byte at offset 15 (`SQLite format 3\0`), which `_containsNullByte` over the first 8000 bytes rejects independently. The plaintext databases are therefore blocked by both filters. They do not protect text files (XML/JSON/logs), and they do not apply to the `.pdf` branch.

**6. Attacker reachability**

Tool-call arguments originate from the model and are decoded without validation in `lib/presentation/screen/chat/cubit/agent_cubit.dart:720-726` (`arguments = jsonDecode(toolCall.argumentsFragment)`), then passed straight to the registry at `:766-768`. Only `tier3Hitl` tools pause for approval (`:760-765`); Tier 1 and Tier 2 auto-execute. No layer validates, normalises or confines `path` or `directoryPath`. The HITL sheet does render the real argument JSON (`lib/presentation/screen/chat/widgets/action_approval_sheet.dart:44-45`), so raising a tier is an effective control where it applies — but neither tool reaches it.

## Proof of Concept

No device or emulator was available, so the end-to-end exploit was not executed. The following is the source-level attack path, with a static harness that proves the control is absent.

1. Establish the attacker-controlled input. Any of: a remote or compromised OpenAI-compatible endpoint returning a crafted tool call, an imported remote skill package, a notification body read by the listener service, or an indirect injection carried in a tool result. All reach these paths with no data/instruction separation.
2. For enumeration, cause the model to emit a `list_device_files` tool call with `directoryPath` set to the app's private data directory and `recursive: true`. It is declared Tier 1 and executes with no gate at all, returning names, absolute paths, sizes, timestamps and extensions for the whole subtree — the app's entire private storage layout.
3. For a read, cause the model to emit a `read_device_file` call whose `path` targets a text file under the app's private storage. The Tier-2 `checkPermission` returns hardcoded `true`, so the registry gate passes, and `readFile` opens the caller-supplied absolute path directly.
4. Note the filter ordering: a path ending in `.pdf` is dispatched to `extractPdfText` before the extension denylist and null-byte checks run, and `extractPdfText` applies neither, so a `.pdf`-named path is read with no binary screening.
5. The result is returned as the tool result, appended to the conversation as a `role: tool` message, and transmitted to the configured remote LLM endpoint.
6. Note what is NOT reachable: the plaintext SQLite databases are blocked both by the `db`/`sqlite` extension denylist and by the NUL byte at offset 15 of any real SQLite header, which the null-byte sample rejects independently.

Static confirmation (no app execution): the harness reproduces the conditions above against the repository source and asserts the absence of the control — declared tiers, the hardcoded permission grant, the absence of any containment primitive in `readFile`/`listFiles`, the unused workspace-root getter, and the unvalidated `jsonDecode` of model arguments.

## Remediation

Enforce a workspace boundary on every agent file tool, at the point where the model-supplied argument enters.

1. Introduce a single containment primitive on the file-workspace service, and use it in the `execute` closure of both `read_device_file` and `list_device_files` before any filesystem access. Do not rely on the tool description to communicate the boundary.
2. Resolve the requested path against the application documents directory, canonicalise it (collapse dot segments and normalise separators), and reject anything that is not a strict descendant of that root. Compare with a trailing-separator-aware prefix test so a sibling directory sharing the root's name prefix is not accepted.
3. Resolve symbolic links on both the candidate path and the root before the final comparison, so a symlink created inside the workspace cannot be used to reach outside it.
4. Replace the hardcoded permission grant in the default filesystem wrapper with a real evaluation. If the intended gate is a user-facing one, wire it to an actual platform permission or approval rather than returning a constant.
5. Raise `list_device_files` from Tier 1 (auto-execute) to at least Tier 2 so enumeration is no longer performed without evaluation; promote it to Tier 3 if enumeration of the private data directory should require explicit user approval. Note that the HITL sheet already renders the real argument JSON, so a Tier-3 promotion would show the user the exact directory being listed.
6. Add regression tests that assert an absolute path outside the workspace, a traversal sequence, and a symlink escape are each rejected, and that an in-workspace path still succeeds.

## Fix Verification

Gates worked in order. **Gate 1 (applicability)** and **Gate 4 (repository checks)** could only be partially executed — the Flutter package has no `.dart_tool/package_config.json`, no pub cache and no network, so a package-wide `dart analyze`/`dart test` was impossible. What I did run: `dart format --output=none` over all three patched files reported no parse errors; the patch was applied to the working tree, diffed byte-identical against an independently prepared copy, then reverted so the `fix_before` blocks remain verbatim against the current checkout.

**Gate 2 (security closure)** — re-traced source-to-sink through the patched code. `read_device_file` and `list_device_files` now evaluate `service.isWithinWorkspace(path)` before reaching `readFile`/`listFilesFormattedJson` and return `ValidationFailure` when it is false. `isWithinWorkspace` returns false when the path is empty, when the workspace root cannot be resolved, or when the canonicalised path is not under the canonicalised root; it then re-checks containment after `resolveSymbolicLinks()` on both the candidate and the root. Because the guard sits in the `execute` closure — the single point where the model-supplied argument enters — every caller that passes model input is covered. I could not re-run the original PoC (no device), so closure rests on the isolated execution below plus the trace.

**Executed:** the containment logic was run against a real filesystem in a standalone Dart program, 16/16 cases correct — traversal (`../../../databases/flames_memory.db`), sibling-database paths, `/etc/hosts`, `/sdcard/Download/secret.txt`, doubled separators, dot-segments, and prefix confusion against a sibling directory named `app_flutter_backup` (which a naive `startsWith(root)` would wrongly allow). A symlink created inside the workspace pointing at a file outside it was correctly **rejected after resolution** while the lexical check alone allowed it — that case is why the symlink step is required.

**Gate 3 (bypass review)** — re-read the diff against the sibling call sites. Two were checked: (a) `chat_screen.dart:880` `_pickDocument()` also calls `readFile`, but with a path chosen by the user through the platform picker, which may legitimately be outside the workspace; this is why containment is enforced at the tool boundary rather than inside `readFile` — confining the service would have broken the file-attachment feature and eight existing unit tests that use paths such as `/docs/note.txt` against a fake root of `/fake/docs`. (b) `export_document_pdf` writes through the same wrapper but creates regular files only, so it offers no symlink-creation primitive to defeat the check; a check-to-open TOCTOU swap is therefore theoretical here. Alternate input classes tried: doubled separators, dot-segments, and symlink escape (all rejected).

**Gate 4 (preserved behaviour)** — legitimate inputs verified as still accepted: a path inside the workspace, the workspace root itself, and `dir/..` resolving back inside. Error semantics are preserved — `CacheFailure`/`ValidationFailure` as before, and the existing missing-file path still returns `Left`. The single new interface member (`isWithinWorkspace`) is satisfied by the real implementation; the only other implementers of the interface are Mockito mocks (`test/helpers/mocks.dart:135`, `test/domain/tools/chat/tool_registry_test.dart:27`), which auto-satisfy added members, so no test file needed changing.

**Deliberate design note for the reviewer:** moving `list_device_files` from Tier 1 to Tier 2 raises it off auto-execute and gives it a permission evaluation, consistent with the codebase's own tier definitions (`security_policy.dart:3-5`: Tier 1 = read-only/ambient, Tier 3 = state-modifying/destructive). It is the *containment check*, not the tier, that enforces the invariant for both tools — a reviewer wanting an explicit user tap for enumeration could instead promote it to Tier 3, and the HITL sheet would then display the real `directoryPath` argument (`action_approval_sheet.dart:44-45`).
