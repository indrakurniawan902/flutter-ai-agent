# Inbound gateway chat frame role field is unvalidated and can inject a system-role instruction into the LLM context

**ID:** vuln-0016
**Severity:** MEDIUM
**Found:** 2026-09-15 07:58:14 UTC
**Target:** Flames Android application (ai.hermes.flames), repository under audit
**Endpoint:** lib/presentation/screen/chat/chat_screen.dart
**Method:** WebSocket (JSON-RPC frames)
**CWE:** CWE-863
**CVSS:** 4.2
**Confidence:** Medium
**Fix Effort:** Low

## Description

The gateway WebSocket client takes the role field of an inbound chat_message frame verbatim from the wire, stores it, persists it, and later re-serializes it into the model request unfiltered. A frame declaring "role": "system" becomes a system-role instruction in the language model's context, giving whoever controls the gateway connection authority over the model's instructions rather than only over its data. The entry survives mode switches and restarts because it is persisted and reloaded into the same in-memory list the direct-mode LLM call serializes. Unconfirmed, not dynamically validated: no emulator, device, or running gateway was available.

## Impact

A party able to send frames on the gateway connection can plant text the model subsequently treats as its own system-level instructions rather than conversation data. Because the entry is persisted and reloaded into the list the direct-mode request serializes, the injection outlives the delivering turn, survives mode switches, and survives restart. The practical consequence is instruction authority over the agent: gateway-supplied text can direct later model behaviour, and since Tier 1 tools auto-execute on model output and the Tier 2 gate is inert for tools registered without a checker, that authority can be converted into device actions. The demonstrated consequence is the misplaced authority itself, not an observed action.

## Counterevidence

Timing is the strongest argument against: gateway-mode turns are answered by the server, so a planted entry may not reach a model request in the same turn. That limits immediacy but not the defect - the entry is written to the session store by addMessage (agent_cubit.dart:185-189), reloaded into the shared _messages list by _loadSessionMessages (:330-352), survives the mode switch (_toggleMode at chat_screen.dart:1084-1112 never clears _messages), and is serialized verbatim by :906 and chat_message.dart:116-127. The window is the life of the session, not one turn. A second argument is that the peer is the operator's own gateway; that reduces who can plant the entry but not the missing control.

Checked and found absent: any allowlist or normalization of role on the inbound path; any filtering in toWireJson; and any check distinguishing a locally-authored system message from a socket-supplied one. The only role comparisons in the codebase are message.role == 'assistant' (chat_screen.dart:307, UI settling) and message.role == 'user' (agent_cubit.dart:881, prompt pruning). No runtime confirmation was possible.

## Confidence Rationale

Static trace only. Every hop is evidenced at a named location, but no frame was delivered to a running application and no model request was observed, because there is no emulator, device, or gateway in the assessment environment.

## What Would Change This Severity

A runtime demonstration that a peer-supplied role "system" frame changes subsequent model behaviour on a device - for example the model executing a tool it was directed to by that frame - would raise this to high; conversely, evidence that the deployment never issues direct-mode turns on a session that also carries gateway traffic would lower it.

## Technical Analysis

The role is unvalidated at the parse boundary. gateway_message.dart:358-364 sets role from json['role'] with no allowlist and no normalization, so "system" is accepted exactly like "user" or "assistant". The value is then stored verbatim: chat_screen.dart:311-316 builds ChatMessage(role: message.role, content: message.content), and the only role test on that path is the UI-settling comparison at :307. It is persisted and reloaded by agent_cubit.dart:185-189 (addMessage appends and calls _persistMessages) and :330-352 (_loadSessionMessages restores the list). The list is shared across modes: _toggleMode (chat_screen.dart:1084-1112) clears only gateway tool-event cards, never _messages. Serialization preserves the role: chat_message.dart:116-119 emits 'role': role unconditionally, and agent_cubit.dart:906 maps every message through toWireJson into serializedMessages, which is passed to the LLM client at :923-930 and posted by chat_datasource.dart:38-54. Why this is a control defect rather than a naming detail: the application constructs system messages locally in exactly two places - the memory block and the skill prompt at agent_cubit.dart:907-921 - so system is explicitly a reserved role for content the application considers authoritative. Nothing prevents an inbound frame from claiming it, and once stored there is no way to distinguish the peer-supplied entry from the locally-constructed ones.

## Remediation

1. Constrain the inbound role at the parse boundary: normalize the incoming value and map it through an explicit allowlist, coercing anything that is not a known safe role to a data role such as assistant. Coercing at the parse site covers every present and future reader of the field.
2. Treat the gateway channel as a data source, not an instruction source. No frame received over the socket should produce a message with system authority; system-role content should only be constructed locally.
3. Apply the same discipline to the other text-bearing frame types (text_delta, tool_event, error) so the rule is uniform across the protocol.
4. Where a peer genuinely needs to influence model behaviour, use the protocol's explicit channels (tool manifest, elicitation request) rather than the conversation stream, so the influence is visible and gated.
5. Add a regression test asserting that a chat_message frame carrying role "system" (and "tool", and an unknown value) is surfaced as assistant, and that assistant and user pass through unchanged.

## Fix Verification

Gate 1 (security closure) — REASONED, NOT EXECUTED: the only path by which a gateway frame becomes a ChatMessage is chat_screen.dart:311-317, which now receives a role narrowed at the parse site (gateway_message.dart:358-372). A frame declaring system is coerced to assistant, so it cannot enter _messages with system authority; serialization at agent_cubit.dart:906 then emits only assistant or user. Coercing at the parse boundary covers every consumer, including the voice dispatcher's reply matcher (gateway_voice_prompt_dispatcher.dart:60-62). Not executed: no Dart/Flutter toolchain, emulator, or device was available.

Gate 2 (bypass review): reviewed without relying on the rationale that produced the patch. GatewayChatMessage is constructed only from fromJson and local code; its role is read at exactly two places (chat_screen.dart:307 for UI settling, gateway_voice_prompt_dispatcher.dart:61 for reply matching), neither weakened by the coercion. Alternate input classes checked: alternate spellings (System, SYSTEM, whitespace-padded) are normalized before the allowlist test; a missing or non-string role already fell back to user and still does; the other text-bearing frame types (text_delta, tool_event, error) are handled separately in chat_screen.dart and never construct a ChatMessage with a role. One deliberate narrowing accepted: a peer sending role "tool" gets assistant, because a tool role without a matching tool_call_id is not a valid request shape for the OpenAI format anyway.

Gate 3 (preserved behaviour): CONFIRMED by inspection. An assistant reply still arrives as role 'assistant', still settles the running tool cards (chat_screen.dart:307), still satisfies the voice dispatcher's matcher, and is still stored and rendered as before. Direct-mode requests are unaffected because they are built from locally-authored messages plus the two locally-constructed system entries (agent_cubit.dart:907-921). The parse still never throws on a malformed role — it normalizes instead.

Gate 4 (repository checks) — NOT RUN, explicit gap: dart analyze and flutter test are unavailable (no Dart or Flutter SDK in the assessment environment). The patch adds a static const Set to an existing class and introduces no new imports, and the line range was verified against the file, but no formatter, analyzer, or test suite was executed. A reviewer must run the package's own checks before merging, and a regression test should assert that a chat_message frame with role "system" is surfaced as assistant.

## Assumptions

Assumes a completed gateway connection delivering at least one chat_message frame (normal gateway-mode operation), and that the peer is not fully trusted: the gateway destination is attacker-influenceable via the QR pairing path (vuln-0012), and no role restriction is applied regardless. Assumes at least one later direct-mode turn, since gateway turns are answered server-side; the entry persists across mode switches and restarts.
