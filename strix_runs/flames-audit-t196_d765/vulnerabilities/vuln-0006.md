# Tier-2 permission gate fails open for tools registered without a permission checker

**ID:** vuln-0006
**Severity:** MEDIUM
**Found:** 2026-09-15 06:25:47 UTC
**Target:** Flames Android app (Flutter package `flutter_ai_agent`) — `lib/domain/tools/chat/tool_registry.dart`
**Endpoint:** lib/domain/tools/chat/tool_registry.dart
**CWE:** CWE-863
**CVSS:** 4.3
**Confidence:** Medium
**Fix Effort:** Low

## Description

The agent tool registry enforces its "Tier 2 — permissioned" security tier with a condition that also tests whether the tool declares a permission checker. A tool registered as Tier 2 without that checker therefore skips permission evaluation entirely and auto-executes exactly like a Tier 1 tool. Seven registrations are in this state, five of them silently (no explanatory comment and no equivalent check inside the underlying service). Because the ReAct loop and the remote gateway RPC path both treat every non-Tier-3 tool as auto-executable, model output and server-supplied tool calls can invoke these device capabilities with no in-application permission evaluation. Unconfirmed, not dynamically validated: no emulator, device, or Flutter toolchain was available, so no tool call was executed.

## Impact

The application's declared authorization invariant — that a Tier 2 capability runs only after its runtime permission is evaluated — is not enforced for tools registered without a checker. The two most consequential affected tools are `launch_system_setting`, which can navigate the user to the notification-listener, accessibility, and overlay-apps settings pages (the exact pages that grant this app additional device authority), and `open_email_composer`, which can prefill an outbound message. Both can be driven by untrusted text reaching the model, with no in-app confirmation. The demonstrated effect is bounded: the operating system toggle and the mail client's send button still require a user action, so no permission is granted and no message is sent by the tool call itself. The remaining affected tools are neutralised by other controls (scheme allow-list, OS capture UI, physical NFC tap). The durable risk is that the gate silently degrades any future Tier 2 tool that omits the field.

## Counterevidence

The strongest case against this finding is that for most of the affected tools there is no runtime permission for the gate to evaluate, so "the gate did not run" may have no consequence beyond a misleading tier label. That argument holds for part of the list and was tested tool by tool.

- `camera_take_photo` — neutralised. The `execute` closure reaches `image_picker`'s OS capture Activity (`lib/data/datasources/tools/chat/camera_vision_service.dart:73-87`), which is a foreground UI the user must operate and which raises the runtime permission request itself; a denial surfaces as `PermissionFailure` at `camera_vision_service.dart:100-107`. The `retrieveLostData()` pre-path (`:50-67`) only recovers a capture the user already took. Adding a check-only probe here would in fact regress first use, because a read-only probe cannot raise the prompt.
- `open_external_url` — neutralised. `lib/domain/tools/chat/contact_launcher_tools.dart:159-163` rejects any URI that is not `http`/`https` with a non-empty host, so `intent://`, `javascript:`, `file:`, and `market://` are refused, and the launch uses `LaunchMode.externalApplication` (`:170`). No runtime permission exists for opening a browser URL, so the omitted check skips no evaluation.
- `open_email_composer` — partially neutralised. It only builds a `mailto:` URI and launches the composer (`lib/data/datasources/tools/chat/intent_launcher_service_impl.dart:186-205`); the recipient goes to the URI path and subject/body to percent-encoded query parameters, so there is no header or query injection, and no message is sent. No runtime permission exists for composing mail. What remains is a model-driven prefill of an outbound message the user did not author.
- `launch_system_setting` — partially neutralised. The allow-list is enforced on both sides (`intent_launcher_service_impl.dart:223`, `MainActivity.kt:431-448`), so no arbitrary settings action can be injected, and no runtime permission exists for launching a settings page. However the allow-list deliberately includes `notification_listener`, `accessibility`, and `overlay`, the pages that grant this app further authority, and the tool description itself instructs the model to use them (`tool_registry.dart:1505-1512`). The consequence is a privilege-chaining primer; the user must still operate the OS toggle, and nothing in the source shows the tool can flip it.
- `nfc_read_tag`, `nfc_read_emoney_balance` — neutralised and mislabelled. `android.permission.NFC` is an install-time permission for which Android shows no runtime dialog, so there is no runtime permission to evaluate; the real gates are physical (a card must be tapped within a twenty-second window — `lib/data/datasources/tools/device/nfc_service.dart:70-80`, `:260-277`) and both tools are read-only.
- `ui_find_elements` — deliberate, documented omission, not a defect. The registration carries the comment *"No checkPermission: the registry gate would return a generic PermissionFailure, while the service returns the actionable [accessibility_not_enabled] message the model needs"* (`tool_registry.dart:1761-1763`) and the service independently refuses to read the tree unless the service is active (`lib/data/datasources/tools/chat/accessibility_inspector_service.dart:109-112`, via `checkStatus()` at `:72-86`). A naive fail-closed patch would silently change this documented behaviour, which is why the recommended fix uses an explicit marker.

Checked and found absent: no remote path can influence a tool's tier or checker (only literal assignments, two construction sites, and `toOpenAiTool()` exposes neither); no skill enablement requirement gates these tools (`register()` defaults to enabled at `tool_registry.dart:210`, and a tool listed in no skill is never disabled — `open_email_composer`, `launch_system_setting`, and both NFC tools appear in no bundled skill); no direct call to a tool's `execute` closure exists anywhere outside the registry (`tool.execute` is invoked at exactly one place, `tool_registry.dart:257`). Nothing here demonstrates confidentiality or availability impact, and no permission is actually granted or message sent by a tool call alone — the impact metrics below reflect only the limited, user-mediated effect that could be evidenced. No runtime confirmation was possible: there is no emulator, device, or Flutter/Dart toolchain in the assessment environment, so the defect was never executed.

## Technical Analysis

`SecurityTier` documents the intended contract as *"Tier 2: Sensitive / Permissioned (auto-execute only if runtime permission is granted)"* (`lib/domain/tools/chat/security_policy.dart:1-10`), and `SecurityPolicy.requiresPermission` returns true for that tier (`security_policy.dart:26-28`). The registry is the single place that contract is enforced:

```dart title=lib/domain/tools/chat/tool_registry.dart startLineNumber=250 endLineNumber=256
      if (SecurityPolicy.requiresPermission(tool.securityTier) &&
          tool.checkPermission != null) {
        final granted = await tool.checkPermission!();
        if (!granted) {
          return Left(PermissionFailure('Permission denied for tool: $name'));
        }
      }
```

The second conjunct is the defect. When `checkPermission` is null the whole block is skipped and control falls through to `return await tool.execute(arguments);` (`tool_registry.dart:257`), so the tool behaves as Tier 1. `checkPermission` is an optional constructor parameter (`tool_registry.dart:51`, `:59`), so nothing prevents the omission.

`SecurityPolicy.requiresPermission` is referenced in exactly one place in the application source — this gate — so there is no secondary Tier 2 enforcement point. `executeTool` is defined at `tool_registry.dart:238` and has three call sites: `lib/presentation/screen/chat/cubit/agent_cubit.dart:611` (resume after approval), `agent_cubit.dart:766` (ReAct loop), and `lib/domain/services/gateway/gateway_rpc_receiver.dart:148` (remote gateway frame). The first two gate only Tier 3 (`agent_cubit.dart:753`, with the comment *"Tier 1 & Tier 2: Auto-execute."* at `:764`); the gateway path gates only Tier 3 (`gateway_rpc_receiver.dart:89`). Tier 2 therefore depends entirely on the fail-open gate.

The tool name and arguments are unvalidated model output on the ReAct path (`agent_cubit.dart:717` reads `toolCall.name`, `:723` `jsonDecode`s the model-supplied argument fragment) and server-supplied data on the gateway path (`gateway_rpc_receiver.dart:148-151` passes `request.tool` and `request.arguments`).

Affected registrations, all declared `SecurityTier.tier2Permission` with no `checkPermission` and no equivalent check inside the called service:

- `camera_take_photo` — tier at `tool_registry.dart:371`
- `open_external_url` — tier at `tool_registry.dart:1432`
- `open_email_composer` — tier at `tool_registry.dart:1493`
- `launch_system_setting` — tier at `tool_registry.dart:1524`
- `nfc_read_tag` — tier at `tool_registry.dart:1568`
- `nfc_read_emoney_balance` — tier at `tool_registry.dart:1621`
- `ui_find_elements` — tier at `tool_registry.dart:1760` (documented deliberate omission; the service self-checks — see counterevidence)

Five of these carry no explanatory comment, which distinguishes them from the deliberate case. The omission is a registration defect, not remote tampering: `securityTier` is a `final` field (`tool_registry.dart:49`) assigned only from literals, there are no assignment sites for `securityTier`/`checkPermission` anywhere in the source, and `RegisteredTool` is constructed in only two files (`tool_registry.dart` and `lib/data/datasources/skills/doc_builder_skill.dart:39`). `toOpenAiTool()` (`tool_registry.dart:62-71`) exposes neither the tier nor the checker to the model or the gateway manifest. Imported skills are force-disabled on import (`lib/domain/services/skills/skill_security_scanner.dart:189-190`), and the skill registry only toggles enablement (`lib/domain/services/skills/skills_registry_service.dart:386-405`).

## Remediation

1. Make the Tier 2 gate fail closed in `ToolRegistry.executeTool`. A Tier 2 tool that declares no permission checker must be refused before its `execute` closure runs, rather than falling through to execution.
2. Make the deliberate omission explicit rather than implicit. The gate currently cannot distinguish "the author forgot" from "the author intended the service to self-enforce". Introduce an explicit opt-in marker on `RegisteredTool` (for example a `selfEnforcesPermission` flag defaulting to false) and treat a Tier 2 tool with neither a checker nor the marker as a hard failure.
3. Apply the marker only to the two registrations where another mechanism genuinely performs the evaluation, and record the reason in a comment at the registration site: `ui_find_elements`, where the accessibility inspector service already returns a status-specific failure before reading the tree, and `camera_take_photo`, where the OS capture Activity raised by the image picker performs the runtime request and enforcement itself.
4. Resolve the tier of the remaining affected registrations, which currently have no runtime permission to evaluate and therefore cannot supply a meaningful checker: `launch_system_setting` and `open_email_composer` should require human approval before they run, because they land the user on privilege-granting settings pages or create an outbound message the user did not author; `nfc_read_tag`, `nfc_read_emoney_balance`, and `open_external_url` should be treated as non-permissioned, because NFC has no runtime permission and requires a physical tap, and the URL launcher already restricts schemes to http and https. This is a policy decision for the maintainers and should be ratified rather than applied silently.
5. Add a registry-level invariant test asserting that every registered tool whose tier is not Tier 1 declares either a permission checker or the self-enforcement marker, so a future omission fails the build instead of silently bypassing the gate.
6. Review the same gate for the analogous no-op case already present in the codebase, where a checker is supplied but unconditionally returns true; a present-but-vacuous checker is not distinguishable from a real one at the call site.

## Fix Verification

Gate 1 — Security closure: REASONED, NOT EXECUTED. Tracing the patched source, a Tier 2 tool with a null checker and `selfEnforcesPermission == false` now returns `Left(ServerFailure(...))` at `tool_registry.dart:250-256` before reaching `tool.execute(arguments)` at `:257`. Because `tool.execute` is invoked at exactly one place in the application source and all three `executeTool` call sites (`agent_cubit.dart:611`, `agent_cubit.dart:766`, `gateway_rpc_receiver.dart:148`) route through that method, no path reaches an affected tool's closure. The previously-silent omission now fails closed. This was not executed: no Dart/Flutter toolchain is available, so neither the vulnerable nor the patched behaviour was observed.

Gate 2 — Bypass review: reviewed without relying on the rationale that produced the patch. Sibling call sites of the same helper were enumerated (`tool.execute` at one site only); equivalent sinks were checked (`executeTool` has three callers, all through the gate); and the alternative input class — remote influence over the tier or checker — was tested and refuted (`securityTier` is `final`, assigned only from literals; `RegisteredTool` is constructed in two files; `toOpenAiTool()` exposes neither the tier nor the checker). One deliberate direction change was identified and accepted: five registrations that currently auto-execute will now be refused until their tier is resolved, which is fail-closed rather than fail-open.

Gate 3 — Preserved behaviour: PARTIAL. `ui_find_elements` keeps its documented actionable error, and `camera_take_photo` keeps first-use capture, because both are marked as self-enforcing; a check-only probe on the camera tool would otherwise have blocked the first permission prompt. The legitimate inputs and error semantics for the remaining five registrations change: `open_external_url`, `open_email_composer`, `launch_system_setting`, `nfc_read_tag`, and `nfc_read_emoney_balance` will return a failure instead of executing. That is intentional — their Tier 2 label has no runtime permission behind it — but it is a behaviour change that must be applied together with the tier decision in remediation step 4, and it will require the existing execution tests for those tools to be updated (for example `test/domain/tools/chat/tool_registry_test.dart:916` and `:1027`, `test/domain/tools/nfc_tools_test.dart:42` and `:100`). This is the gate that could not be fully cleared, and it is a product decision rather than a code gap.

Gate 4 — Repository checks: NOT RUN, and this is an explicit gap. `dart analyze` and `flutter test` are unavailable in the assessment environment; there is no Dart or Flutter SDK. The patch was written against the file's existing style and imports (`ServerFailure` and `PermissionFailure` are already imported and used in the same method at `:245` and `:254`), and the line ranges were verified against the file, but no formatter, analyzer, or test suite was executed. A reviewer must run the package's own checks before merging.

Narrowest-complete-change judgement: the smallest change that fully enforces the invariant is the fail-closed gate plus the explicit marker; the marker is required rather than optional, because without it the patch cannot distinguish a forgotten checker from a deliberate one and would silently break the accessibility tool's documented error semantics.

## Assumptions

Assumes the app's own tier model is the intended security contract — that a Tier 2 capability is meant to run only after its runtime permission is evaluated. Assumes an attacker can influence model output (for example via notification text, fetched page content, or imported skill text) or, on the gateway path, that the paired server supplies the tool call; the gateway and LLM endpoints themselves are treated as trusted infrastructure. Assumes the user has granted the permissions the app requests, and that the operating system permission dialog, the OS capture Activity, and the physical NFC tap remain in force — none of which this finding bypasses.
