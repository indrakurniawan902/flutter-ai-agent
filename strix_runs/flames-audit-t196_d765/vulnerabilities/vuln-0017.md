# Gateway bearer token disclosed to an arbitrary origin via WebSocket handshake redirect

**ID:** vuln-0017
**Severity:** MEDIUM
**Found:** 2026-09-15 07:59:36 UTC
**Target:** /workspace/flames-audit-t196 (Flutter/Dart Android app "Flames")
**Endpoint:** lib/data/datasources/remote/gateway/gateway_socket.dart
**CWE:** CWE-522
**CVSS:** 5.3
**Confidence:** High
**Fix Effort:** Low

## Description

The app connects to the Hermes Gateway with `WebSocket.connect()` and immediately writes an `auth` frame containing the stored gateway bearer token. The dart:io WebSocket handshake is an ordinary `GET` issued by a shared `HttpClient` whose request objects default to `followRedirects = true` with up to 5 redirects. A `301`/`302`/`303`/`307`/`308` response to the handshake is therefore followed automatically, the upgrade is completed against the redirect target, and the credential frame is written to that socket. The client never checks that the origin it finally connected to is the origin it was configured with. Reproduced against a local redirect server: the token frame arrived at the redirect target, including a `wss://` to `http://` cleartext downgrade.

## Impact

The stored gateway bearer token is disclosed to whoever controls the HTTP response to the handshake for the configured origin. Because the same value is reused as the LLM API key, the disclosed credential also authenticates the OpenAI-compatible chat endpoint. The disclosure is silent (no user-visible error, the socket reports as connected) and is independent of TLS: a `wss://` profile can be redirected to a cleartext `http://` listener, so the token crosses the network in plaintext. The attacker needs the ability to answer for the configured host - a MITM on the path, a hostile Wi-Fi/DNS/proxy, or control of the endpoint itself.

## Counterevidence

Actively hunted for a control and found none on this path:

- **No `followRedirects = false` anywhere in the WebSocket path.** The only occurrences in the repository are `url_reader_service.dart:47` (`followRedirects: true`, an unrelated read-only fetcher) and `skill_remote_loader.dart:64` (`followRedirects: false`, an unrelated skill download). Neither is on the gateway path.
- **No `customClient` is passed** to `WebSocket.connect` (`gateway_socket.dart:71-74`), so there is no opportunity for a caller-supplied redirect policy.
- **No origin check before the auth frame.** `connect()` (`gateway_client.dart:175-216`) normalizes the configured URL, connects, and immediately sends the auth frame; it never compares the reached origin with `_currentGatewayUrl`.
- **Not a server-supplied-URL issue.** No gateway frame type carries a URL (`gateway_message.dart` frame set: auth/auth_success/auth_failure/ping/pong/text_delta/tool_call_request/tool_call_response/tool_event/elicitation_request/elicitation_response/chat_message/tool_manifest/error/chat_cancel/raw), and the reconnect path reuses the locally stored `_currentGatewayUrl` (`gateway_client.dart:376-380`). The redirect is the only way the client is re-pointed.
- **Not blocked by TLS.** Confirmed live: a `wss://` first hop that redirects to an `http://` target results in the token being written to the cleartext listener.
- **TLS certificate validation is not the mitigating factor here** - it is intact (no `badCertificateCallback`/`onBadCertificate`/`setTrustedCertificates`/`SecurityContext`/`HttpOverrides` anywhere in `lib/` or `android/`), but certificate validation only authenticates the *first* hop; the redirect target is reached by design afterwards.

Limiting factor, stated plainly: the attacker must be positioned to answer for the configured origin. This is not a remote unauthenticated attack from an arbitrary internet host; it is a credential-disclosure primitive for an attacker on the path or in control of the configured endpoint. That is why the rating is Medium rather than High, and it is scored as such.

## Confidence Rationale

The mechanism was reproduced live with a Dart runtime using the exact call shape of the application (`WebSocket.connect` without `customClient`, followed by an auth frame), and the redirect was demonstrated both cross-origin and as a `wss://` -> `http://` cleartext downgrade. The application-side source and the pinned dart:io sources were read directly. The one thing not exercised is the compiled Flutter APK on a device, since no emulator is available - the finding is therefore unconfirmed *on-device*, though the underlying transport behaviour it depends on is proven.

## What Would Change This Severity

Confirmation that this occurs against a production Hermes Gateway deployment with a real stored token (rather than the isolated local reproduction) would raise confidence to fully on-device and justify treating it as High; conversely, evidence that deployments pin the gateway origin at the network layer (for example a mutually authenticated tunnel or an origin-locked reverse proxy) would reduce the practical impact to Low.

## Technical Analysis

**Call path**

1. `lib/data/datasources/remote/gateway/gateway_client.dart:189-193` - `connect()` calls `socketFactory.connect(uri, timeout: ..., pingInterval: ...)`. No headers and no HTTP client are supplied.
2. `lib/data/datasources/remote/gateway/gateway_socket.dart:71-74` - `IoGatewaySocketFactory.connect` calls `WebSocket.connect(uri.toString(), headers: customHeaders)` with `customHeaders == null`. The `customClient:` parameter, which is the only supported way to control the handshake request, is not used.
3. In dart:io (`sdk/lib/_http/websocket_impl.dart`), `WebSocket.connect` rewrites the `ws`/`wss` scheme to `http`/`https` and issues the handshake via a **static shared** `HttpClient` (`static final HttpClient _httpClient = HttpClient();`, `openUrl("GET", uri)`). Nothing in that path sets `followRedirects = false`.
4. In dart:io (`sdk/lib/_http/http_impl.dart`), `_HttpClientRequest` defaults `bool _followRedirects = true;` and `int _maxRedirects = 5;`, and `_handleIncoming` re-issues the request to the `Location` target when `followRedirects && response.isRedirect`. For `GET`, `isRedirect` covers `301`, `302`, `303`, `307` and `308`.
5. `lib/data/datasources/remote/gateway/gateway_client.dart:212-216` - once the (redirected) socket is established, the client immediately sends `GatewayAuthMessage(token: token ?? '', clientId: clientId)`.
6. `lib/domain/entities/gateway/gateway_message.dart:117-124` - `GatewayAuthMessage.toJson()` serialises the raw token into the frame body.

**Origin binding is never re-established**

`connect()` stores `_currentGatewayUrl` and `_currentToken` at `gateway_client.dart:179-180` and passes them to the socket factory without re-validating the URL that was actually reached. There is no origin/allowlist check before `send(authMessage)`, and the reconnect path reuses the locally stored URL (`gateway_client.dart:376-380`), so no server-supplied URL is involved - the exposure is purely the redirect behaviour of the handshake.

**Header-copy note (not the leak vector, but relevant)**

dart:io's `shouldCopyHeaderOnRedirect` only strips `authorization`/`www-authenticate`/`proxy-*`/`cookie`/`cookie2` on cross-origin hops (`http_impl.dart` `sensitiveHeaders`). The WebSocket upgrade headers (`Connection`, `Upgrade`, `Sec-WebSocket-Key`) are re-sent, and after the upgrade succeeds the application's own auth frame - which is not an HTTP header - is written to whichever socket was returned.

**Verified against primary sources at the pinned revisions**

The project pins framework revision `d3b14c876900e553bc736ca19295fc09e3853e8e` (`.metadata`), whose engine revision is `a804b261645ef8c13eb3d5c44a5c2fb0340c5539`, whose Dart revision is `60a57cd42d64dc03e9f07aa60a2e250755c1ef28`. The dart:io sources above were read at that Dart revision and the app-side sources from the repository.

## Proof of Concept

The PoC stands up two local HTTP listeners: one "configured" origin that answers the WebSocket handshake with a `302` pointing at the second, "attacker" listener, which completes the WebSocket upgrade and records every frame it receives.

1. Start the attacker listener and the redirecting origin (ports chosen dynamically).
2. Call `WebSocket.connect(uri)` using the same call shape as `IoGatewaySocketFactory.connect` - no `customClient`.
3. Write an `auth` frame in the same shape as `GatewayClient` does after connecting.
4. Observe that the connection succeeds, and that the attacker listener receives the frame including the token.

The same PoC was re-run with the configured origin on `wss://` (self-signed certificate) redirecting to a cleartext `http://` attacker listener; the token again arrived at the cleartext listener.

A companion probe confirms the proposed fix: an `HttpClient` whose `openUrl` sets `request.followRedirects = false` causes all five redirect status codes to be refused, while a legitimate non-redirecting endpoint still connects and carries a frame normally.

## Remediation

Disable HTTP redirect following on the WebSocket handshake so the socket can only ever reach the origin the user configured, and treat a redirecting origin as a connection failure. The concrete change is in `lib/data/datasources/remote/gateway/gateway_socket.dart`: pass a `customClient:` to `WebSocket.connect` whose requests set `followRedirects = false` (see the suggested patch).

As defence in depth, consider verifying the origin actually reached before the authentication frame is written, and re-checking it on every reconnect. If the deployment expects redirects (for example an HTTP-to-HTTPS upgrade on the gateway), resolve them explicitly with an allowlist rather than letting the transport follow them implicitly.

The failure is explicit rather than silent: `WebSocketException: Connection to 'http://127.0.0.1:37427/device/ws#' was not upgraded to websocket, HTTP status code: 302`. `GatewayClient.connect` catches this at `gateway_client.dart:221-223` and routes it to `_handleSocketError`, which triggers the normal reconnect/backoff path - so a redirecting origin now surfaces as a connection failure instead of a silent credential disclosure.

**Bypass review (executed).** Checked all five redirect status codes dart:io treats as redirects for `GET` (`301`, `302`, `303`, `307`, `308`) - all refused. The patched client is applied at the single handshake call site (`gateway_socket.dart:71`), which is the only `WebSocket.connect` in the repository, so there are no sibling call sites that bypass it. The `_NoRedirectHttpClient` sets the flag on the request returned by `openUrl`, which is the same request object dart:io subsequently sends the upgrade headers on, so there is no path where a redirect is followed before the flag is applied.

**Preserved behavior (executed).** A legitimate non-redirecting endpoint still completes the handshake and exchanges an auth frame and its echo through the same client. Connection timeout (`timeout`), `pingInterval` assignment, and the `GatewaySocket` wrapper are untouched. `connect()`'s own error handling and reconnect logic are untouched.

**Repository checks (gap - no Dart toolchain for the repo).** No `dart`/`flutter` toolchain is installed in this environment and the repository's own test suite (`test/domain/services/gateway/gateway_url_test.dart`, `test/data/datasources/remote/gateway/gateway_client_test.dart`) could not be executed against the patched tree. The proposed code was compiled and executed standalone with Dart 3.13.3 (the language version pinned by this project's engine revision) as part of the two probes above, so it is syntactically valid and behaviourally verified in isolation - but `flutter analyze` and `flutter test` were not run. **This gate is a stated gap.**

**Note on the `noSuchMethod` forwarder.** `_NoRedirectHttpClient` implements only `openUrl` and forwards nothing else; every other `HttpClient` member throws `UnsupportedError`. That is deliberate - the WebSocket handshake only calls `openUrl` - but if a future caller reuses this client for other request types it must be extended. A reviewer may prefer to keep the class private to `gateway_socket.dart` (as written) so that scope stays obvious.

## Assumptions

Assumes the attacker can answer the HTTP handshake for the configured gateway origin - a network man-in-the-middle, a hostile Wi-Fi/DNS/proxy environment, or control of the configured endpoint. The user must have configured a gateway profile (and thus have a stored token) and the app must attempt to connect. No user interaction beyond normal app use is required.
