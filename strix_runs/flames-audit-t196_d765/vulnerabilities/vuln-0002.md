# Sensitive app data included in Android backups because allowBackup is unset

**ID:** vuln-0002
**Severity:** LOW
**Found:** 2026-09-15 05:23:59 UTC
**Target:** /workspace/flames-audit-t196 (Flames Android application, package ai.hermes.flames)
**Endpoint:** android/app/src/main/AndroidManifest.xml
**CWE:** CWE-312
**CVSS:** 3.7
**Confidence:** Medium
**Fix Effort:** Trivial

## Description

The application declares no android:allowBackup attribute on its application element and ships no fullBackupContent or dataExtractionRules rule, so Android applies its default of allowBackup=true and includes the app private data in cloud backups and device-to-device transfers. The app keeps sensitive user content in plaintext app-private stores - chat transcripts, the agent memory vault, imported skills and the Action Center inbox - which are consequently swept into the backup set without any exclusion. This finding is based on static source review only and is unconfirmed, not dynamically validated: no device, emulator or backup extraction was available in this assessment.

## Impact

The app private storage is included in Android cloud backups and device-to-device transfers. A backup set obtained through ADB backup, a cloud-account compromise, or forensic acquisition of a backup image yields the plaintext contents of flames_memory.db (the agent memory vault, whose content column holds arbitrary user- and agent-authored text), flames_skills.db, and the Hive action_center box, together with the session titles in flames_chat.db. The LLM API key and server-profile records are held in FlutterSecureStorage and are not directly recoverable from a backup because Android excludes the Keystore master key, and chat message bodies are likewise encrypted at rest rather than stored in flames_chat.db; the exposure is therefore user content rather than credentials or full transcripts. The issue also runs the other way: a backup restored onto a different device reintroduces this data into app storage without the user having chosen to restore it.

## Counterevidence

Looked for constraints that would neutralise this. No fullBackupContent or dataExtractionRules attribute or resource exists anywhere under android/, so nothing is excluded. The stores are not outside the auto-backup set: flames_chat.db and flames_skills.db resolve to the app databases directory, flames_memory.db resolves there on Android, and the Hive action_center box resolves under the app documents directory. The genuine constraint is that the credentials themselves live in FlutterSecureStorage with default options, and Android excludes the Keystore master key from backup, so the stored LLM API key and base URL are not directly recoverable from a backup set. That is why confidentiality is rated Low rather than High. It reduces the value of the extracted data but does not neutralise the finding, because the chat transcripts, memory-vault rows and Action Center entries are plaintext SQLite and Hive files with no such protection. No dynamic validation was possible.

The static evidence is complete: no allowBackup, dataExtractionRules or fullBackupContent attribute exists anywhere in the Android configuration, and the sensitive stores were traced in code to app-private paths. ## Technical Analysis

Android includes an application's private data in cloud backup and device-to-device transfer when android:allowBackup is true, which is the platform default when the attribute is omitted. The application element in android/app/src/main/AndroidManifest.xml declares no allowBackup, fullBackupContent or dataExtractionRules attribute, and no such resource file exists under android/app/src/main/res/xml/ (that directory contains only accessibility_service_config.xml). The default therefore applies and the whole app data directory is backed up.

The data directory contains plaintext stores traced in code:

- flames_chat.db in the app databases directory (chat_local_datasource.dart:26,64). Its schema (chat_local_datasource.dart:80-95) contains a single `sessions` table: id, profile_id, title, created_at, updated_at. Message bodies are deliberately not stored here — `saveMessages` writes them through FlutterSecureStorage (`_storage.write(key: keyFor(sessionId), value: encoded)`, chat_local_datasource.dart:113-125) and `getMessages` reads them back from the same store (:240-261). The plaintext exposure from this database is therefore the session titles, which are derived verbatim from the first 40 characters of the user's first message (chat_repository_impl.dart:22-28, agent_cubit.dart:162-168), not the transcripts themselves.
- flames_memory.db in the app databases directory on Android (sqlite_memory_datasource.dart:16,88-103), holding the memories table and its FTS5 mirror. This store is plaintext and its `content` column holds arbitrary user- and agent-authored text.
- flames_skills.db in the app databases directory (skills_local_datasource.dart:15).
- the Hive action_center box opened under the app documents directory by Hive.initFlutter('flames') (lib/myapp.dart:47), storing JSON-encoded inbox entries with free-text titles, summaries and action payloads (lib/data/models/action_center/action_item_model.dart:39-55).

None is excluded by a backup rule, so all are included in the backup set. Android 12+ would honour a dataExtractionRules resource, but the attribute is unset, so no restriction is in force on any supported API level. Credentials (LLM API key, server profiles) are held in FlutterSecureStorage and are not recoverable from a backup because Android excludes the Keystore master key.

## Code Analysis

**Location 1:** `android/app/src/main/AndroidManifest.xml` (line 53)
  Declare allowBackup=false and point at a data-extraction rules resource on the application element

  **Suggested Fix:**
```diff
-     <application
+     <application
+         android:allowBackup="false"
+         android:dataExtractionRules="@xml/data_extraction_rules"
```

## Remediation

1. Add android:allowBackup="false" to the application element in android/app/src/main/AndroidManifest.xml.
2. Add android:dataExtractionRules="@xml/data_extraction_rules" alongside it and create android/app/src/main/res/xml/data_extraction_rules.xml containing a data-extraction-rules document that excludes the root, database, sharedpref and file domains under both cloud-backup and device-transfer.
3. Add android:fullBackupContent="@xml/backup_rules" with an equivalent full-backup-content exclusion list for API levels below 31.
4. If chat history should survive device migration, implement it as an explicit, user-initiated, encrypted export rather than relying on the platform backup channel.
5. Review any future plaintext store against this rule before adding it, since the default include behaviour exposes new files automatically.

## Fix Verification

Gate 1 Applicability: fix_before is a character-for-character copy of android/app/src/main/AndroidManifest.xml line 53 (four spaces followed by the opening application tag). The patch inserts two attribute lines immediately after that opening tag, before the existing label and icon attributes, which is valid XML and keeps the element well-formed. The referenced @xml/data_extraction_rules resource must be created; its target directory android/app/src/main/res/xml/ already exists and holds accessibility_service_config.xml, so no directory creation is implied. No syntax check could be executed: this environment has no Android SDK or Gradle, so the manifest was not run through aapt/aapt2 and the rules resource was not schema-validated. Gate 4 is an explicit gap.

Gate 2 Security closure: with allowBackup=false the platform excludes the app data directory from backup regardless of the rules resource, and the dataExtractionRules resource independently excludes the root, database, sharedpref and file domains from both cloud backup and device transfer. The previously reachable path - unset attribute leading to the platform default true, then the whole data directory being included - is closed where the platform reads the flag, before any file is copied into a backup set.

Gate 3 Bypass review: fullBackupContent is not set, which on API below 31 means allowBackup is the only gate, and it is now set, so those levels are covered. On Android 12+ dataExtractionRules governs the transfer decision and the new resource covers both cloud-backup and device-transfer. The debug and profile manifests declare only the INTERNET permission and contain no application element, so they cannot re-enable backup. Key-value data in FlutterSecureStorage remains excluded by the platform handling of the Keystore master key and is unchanged by this patch. Deliberately not addressed: a rooted device, or an ADB backup taken with a pre-existing backup set.

Gate 4 Repository checks: NOT RUN - no Android SDK, Gradle or Flutter toolchain is installed, so neither gradlew assembleRelease nor a manifest merge could be executed. The repository owner must run the Android build to confirm the merged manifest and validate the rules resource against the AGP schema before merging.

Gate 5 Preserved behaviour: no runtime code, public API or error semantics change. Users lose the ability to restore chat history onto a new device through the platform backup channel; that is the intended security trade-off and is called out in the PR body with the encrypted-export alternative. The rules resource is ignored below API 31, where allowBackup=false still applies, so behaviour is consistent across the app minSdk of 26. Narrowest-complete-change judgement: the smallest repository-native change that enforces the invariant that app-private content does not leave the device through the platform backup channel; it reuses the platform mechanism rather than adding an application-layer filter and folds in no unrelated manifest changes.

## Assumptions

Assumes the user has Android cloud backup or device transfer enabled (the default on most consumer devices), and that at least one sensitive store is non-empty. The unset allowBackup default (true) applies across all API levels including the app minSdk of 26.
