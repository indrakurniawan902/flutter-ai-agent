# Exported MainActivity accepts unvalidated action extra, letting any co-resident Android app start a microphone voice turn and dispatch agent prompts

**ID:** vuln-0003
**Severity:** MEDIUM
**Found:** 2026-09-15 05:25:38 UTC
**Target:** /workspace/flames-audit-t196 (Flames Android app, package `ai.hermes.flames`)
**Endpoint:** android/app/src/main/AndroidManifest.xml
**CWE:** CWE-862
**CVSS:** 5.1
**Confidence:** Medium
**Fix Effort:** Low

## Description

The exported `MainActivity` of the Flames Android app reads the string extra `extra_flames_action` from any incoming `Intent` and forwards it, unvalidated, to the Flutter layer, which dispatches on it without an allowlist. Any third-party app installed on the same device can therefore start `MainActivity` with a crafted extra and trigger privileged app behaviour with no user action beyond the app window becoming visible: `voice_input` starts a 15-second speech-recognition (microphone) capture session, and `quick_status` sends a canned prompt to the AI agent, which may then execute device tools. **This finding is unconfirmed and not dynamically validated — the audit was source-only with no emulator or device.**

## Impact

An attacker with no Android permissions and no special access — merely a co-resident app on the same device — can drive Flames' most sensitive local capability without the user tapping anything in the app.

1. **Microphone activation (`voice_input`).** The app opens a 15-second speech-recognition session (`VoiceTurnService.defaultListenFor`). Any speech in the room during that window is transcribed on-device and, when a dispatch transport is ready, transmitted to the configured remote LLM API as a chat prompt. The capture begins with the microphone permission already granted by the user to Flames, so no permission dialog appears. The recording indicator is an overlay bubble that only exists if the user previously enabled it (off by default), so in the default configuration there is no on-screen indication that capture is active.

2. **Autonomous agent dispatch (`quick_status`).** The fixed prompt `Quick status check: summarize battery, device context, and agent readiness.` is injected into the agent loop. The agent can respond by invoking the app's native device tools (clipboard, location, contacts, calendar, notifications, accessibility-tree reading, Health Connect). The dispatch path was read to confirm the resulting state machine, and a `WaitingApproval` terminal state is surfaced as a failure rather than silently bypassing the human-in-the-loop gate, so this leg is bounded by the existing tier gating rather than escalating it.

3. **Persistence and reachability.** `pendingAction` is set on both `onCreate` and `onNewIntent` and is never cleared until the Dart layer drains it, so the value survives a cold start and is replayed when the listener mounts. The chain does not require the app to be in the foreground: the action is delivered through `onNewIntent` while the activity is already alive, and the background service path (`FlamesBackgroundService` action `ACTION_VOICE_INPUT`, reachable from the ongoing notification and the Quick Settings tile) performs the same Dart injection. Injected microphone capture is the demonstrated consequence; no audio exfiltration to an attacker-controlled destination is demonstrated, so the confidentiality rating below reflects initiation of capture of the user's audio, not demonstrated attacker retrieval of it.

## Counterevidence

Actively attempted to break the chain and could not: (a) searched `android/` and `lib/` for caller-identity or permission verification (`getCallingActivity`, `getCallingPackage`, `Binder.getCallingUid`, `checkCallingPermission`, `getReferrer`) — no matches; (b) searched for any allowlist, enum or constant set constraining the action value at either the Kotlin or Dart boundary — the only consumers are the unvalidated `switch` in `_handleAction`, so an arbitrary value is accepted and simply falls through if unknown, while the three privileged values are matched exactly; (c) searched for a user-confirmation, dialog or lifecycle/foreground gate on the microphone path (`showDialog`, `AlertDialog`, `AppLifecycleState`, `didChangeAppLifecycleState`) — none exists; (d) confirmed `MainActivity` carries no `android:permission` and that the system `BIND_*` permissions on the other exported components are irrelevant to this path, since the attacker targets `MainActivity` directly; (e) confirmed the microphone precondition is satisfied in the default state — `VoiceInputService.startListening` proceeds when the user has already granted `RECORD_AUDIO`, which is required for the feature to work at all, so no additional dialog appears; (f) considered that the victim sees the Flames window open — this is a real limitation of the attack (it is not fully stealthy) but does not block the microphone capture or the agent dispatch, and the launch is indistinguishable from a normal user launch of the app.

Two honest scope limits on the impact: the audio path is bounded by whether a dispatch transport is ready (`runTurn()` returns before opening the recognizer when none is, per the guard at `voice_turn_service.dart:84-90`), and the agent-dispatch path is bounded by the existing tier gating — a Tier-3 tool still surfaces `WaitingApproval` rather than executing, which the code returns as a failure. The finding is therefore microphone-capture initiation and unattended agent dispatch, not a demonstrated bypass of the human-in-the-loop control or demonstrated exfiltration of captured audio. No dynamic validation was possible (no device, emulator or `adb`), so the attack was established by complete source trace only.

## Confidence Rationale

Static-only trace. The audit environment provided no Android device, emulator or `adb`, so the attack was not executed and no runtime response, recognizer activation or agent dispatch was observed. Every hop of the chain was verified by reading the source: exported unguarded activity, unvalidated extra read, delivery over the method channel, the Dart switch, and the call into the speech-recognition plugin. The specific unverified step is that the injected intent reaches `onNewIntent`/`onCreate` with the extra intact and that the Dart seam is live at that moment; both follow from the code but were not observed. Runtime confirmation (the recognizer opening, or the agent receiving the injected prompt) would be required to raise confidence to high.

## What Would Change This Severity

Demonstrating on a real device that the injected `voice_input` action reliably opens the speech recognizer and that the resulting transcript is transmitted to the configured remote LLM API would raise the severity, as it would establish unattended capture and off-device egress of the user's ambient audio. Conversely, evidence that the dispatch transport is normally unavailable when the app is not in the foreground, or that the microphone path requires an additional foreground user action on current Android versions, would lower it.

## Technical Analysis

## Root cause

`MainActivity` is declared exported with no guarding permission, which is required for the launcher entry point:

```xml title=android/app/src/main/AndroidManifest.xml startLineNumber=57 endLineNumber=76
<activity
    android:name=".MainActivity"
    android:exported="true"
    android:launchMode="singleTop"
    ...
    <intent-filter>
        <action android:name="android.intent.action.MAIN"/>
        <category android:name="android.intent.category.LAUNCHER"/>
    </intent-filter>
```

`extractActionFromIntent()` accepts an arbitrary string from that `Intent` and stores it, with no allowlist, no caller-identity check and no signature/authentication of the caller:

```kotlin title=android/app/src/main/kotlin/ai/hermes/flames/MainActivity.kt startLineNumber=73 endLineNumber=85
private fun extractActionFromIntent(intent: Intent?): String? {
    val actionExtra = intent?.getStringExtra("extra_flames_action")
    if (!actionExtra.isNullOrBlank()) {
        pendingAction = actionExtra
        return actionExtra
    }
    if (intent?.action == FlamesQuickTile.ACTION_QUICK_TILE_TRIGGER) {
        val fallbackAction = "voice_input"
        pendingAction = fallbackAction
        return fallbackAction
    }
    return null
}
```

The value is delivered to Dart on both lifecycle paths — cold start (`onCreate`, line 56) and warm delivery (`onNewIntent`, lines 59-66) — and is additionally readable by the Flutter layer through the `getPendingAction` / `clearPendingAction` methods on the `ai.hermes.flames/background_service` channel (lines 303-309). `FlamesBackgroundService.EXTRA_ACTION` (line 38) is the same string constant, and the ongoing notification's "Quick Status" action ships the same extra (lines 402-406), confirming the extra is a first-class control channel rather than a developer leftover.

## Sink chain

1. `VoiceTurnActionListener._handleAction` switches on the action value with no validation:
```dart title=lib/presentation/voice/voice_turn_action_listener.dart startLineNumber=162 endLineNumber=178
void _handleAction(String action) {
  switch (action.toLowerCase().trim()) {
    case 'voice_input':
      unawaited(_runTurnWithTileSync());
      break;
    case 'cancel_voice':
      unawaited(_cancelTurnAndResetTile());
      break;
    case 'quick_status':
      unawaited(
        _registry?.active?.dispatch(
          'Quick status check: summarize battery, device context, and agent readiness.',
        ),
      );
      break;
  }
}
```
2. `_runTurnWithTileSync()` calls `VoiceTurnService.runTurn()`, which passes every precondition (permission already granted, `_voiceInput.isListening` false) and reaches the microphone at line 141: `await _voiceInput.startListening(listenFor: defaultListenFor /* 15s */, pauseFor: 3s, ...)`.
3. `VoiceInputService.startListening` calls `_speech.listen(...)` on `package:speech_to_text` (line 202), which starts the platform speech recognizer and sets `_listening = true`.
4. `_checkPendingAction()` (lines 291-297) drains the same value at startup, so a cold-start injection is replayed when the widget mounts.

## Controls examined and found absent

- No allowlist of accepted action values anywhere in `android/` or `lib/` — the only consumers are the unguarded `switch` above.
- No caller authentication: `getCallingActivity`, `getCallingPackage`, `Binder.getCallingUid`, `checkCallingPermission` and `getReferrer` do not appear anywhere in `android/` or `lib/`.
- No user confirmation, dialog or HITL prompt before the microphone opens; the approval gate applies only to Tier-3 tool invocation inside the agent loop, not to microphone activation.
- No `android:permission` attribute on `MainActivity` and no `<permission>` / `signature`-level protection on the receiving side.

## Reachability

The `MAIN`/`LAUNCHER` filter is the target of the explicit-intent start, and the activity is `exported="true"` without a permission, so any installed app can start it with `Intent.setComponent(...)` and attach the extra. Because the action is carried in an extra rather than the intent action, the attacker does not even need to match a filter — a plain explicit intent suffices. `MainActivity` and `FlamesBackgroundService` share the default process, so `attachDartChannel` (line 259) makes `backgroundMethodChannel` live whenever the Flutter engine exists.

## Proof of Concept

Source-only audit: no device, emulator or `adb` was available, so the steps below describe the attack as it would be mounted against a real installation and were verified by static trace only, not executed.

1. Install any third-party app on the same Android device as Flames. It needs no Android permissions and no special access — only the ability to start an activity, which every app has.
2. From that app, build an explicit intent targeting the exported Flames activity: action `android.intent.action.MAIN`, component `ai.hermes.flames/.MainActivity`, and string extra `extra_flames_action` set to `voice_input`.
3. Call `startActivity(intent)` with `FLAG_ACTIVITY_NEW_TASK`. The Flames activity comes to the foreground.
4. `MainActivity.extractActionFromIntent()` stores the value in `pendingAction` and `onNewIntent()` forwards it over the `ai.hermes.flames/background_service` method channel as `onActionReceived`.
5. `VoiceTurnActionListener._handleAction` matches `voice_input` and calls `VoiceTurnService.runTurn()`, which calls `VoiceInputService.startListening()` — the speech recognizer opens the microphone for 15 seconds.
6. Repeat step 2 with the extra set to `quick_status` to instead inject the fixed status prompt into the agent loop with no user interaction.

````java
// PoC (static-trace only — not executed; no device or emulator available).
// Co-resident attacker app: start exported MainActivity with a crafted action extra.
import android.content.ComponentName;
import android.content.Context;
import android.content.Intent;

public final class FlamesActionInjection {

    private static final String FLAMES_PKG = "ai.hermes.flames";
    private static final String MAIN_ACTIVITY = "ai.hermes.flames.MainActivity";
    private static final String EXTRA_ACTION = "extra_flames_action";

    /** Opens the speech recognizer for one 15s turn with no user tap in Flames. */
    public static void startVoiceCapture(Context ctx) {
        startFlamesAction(ctx, "voice_input");
    }

    /** Injects a fixed prompt into the agent loop with no user interaction. */
    public static void triggerQuickStatus(Context ctx) {
        startFlamesAction(ctx, "quick_status");
    }

    private static void startFlamesAction(Context ctx, String action) {
        Intent intent = new Intent(Intent.ACTION_MAIN);
        intent.setComponent(new ComponentName(FLAMES_PKG, MAIN_ACTIVITY));
        intent.putExtra(EXTRA_ACTION, action);
        intent.addFlags(Intent.FLAG_ACTIVITY_NEW_TASK);
        ctx.startActivity(intent);
    }
}
````

## Remediation

Treat the action extra as untrusted input at the Android boundary, because any co-resident app can supply it.

1. Validate the incoming action against an explicit allowlist at the point of extraction — the three values the app actually implements (`voice_input`, `cancel_voice`, `quick_status`) — and ignore anything else. An allowlist is the correct primitive here: the set is closed and known, and a denylist would silently accept future additions.
2. Do not rely on the intent action or on the `MAIN`/`LAUNCHER` filter for trust. The extra is what selects the behaviour, so the check must be on the extra value itself, not on how the activity was started.
3. If third-party automation of these actions is a product requirement, move it behind a dedicated exported component protected by a signature-level permission, so only apps signed with the same developer certificate can trigger it. The launcher activity should never be a privileged control surface.
4. Keep the extraction function as the single choke point for validation so that both the `onCreate` and `onNewIntent` paths are covered by one check.
5. Add a regression test asserting that an unknown action value is rejected and never reaches the method channel, and that a valid value still works, so the allowlist cannot silently regress.

## Fix Verification

**Gate 1 — Applicability.** Both edited regions were read from the file immediately before writing the patch: lines 51-52 hold the two field declarations the new constant sits beside, and lines 73-85 are the whole `extractActionFromIntent` function. The `fix_before` blocks are verbatim copies of those ranges, and `fix_after` replaces exactly those ranges. The result is syntactically valid Kotlin: a `Set<String>` property plus an early-return guard. No other call site needed changing — `extractActionFromIntent` is the single extraction choke point and both `onCreate` (line 56) and `onNewIntent` (line 62) route through it.

**Gate 2 — Security closure.** Re-traced the source → sink path against the patched code: attacker `Intent` → `onCreate`/`onNewIntent` → `extractActionFromIntent` → the new `action !in ALLOWED_ACTIONS` check rejects any value outside `{voice_input, cancel_voice, quick_status}` by returning `null`, which means `pendingAction` is never set and `onNewIntent` never calls `backgroundMethodChannel?.invokeMethod("onActionReceived", action)` (guarded by `if (action != null)` at lines 63-65). Both the warm path and the cold-start path are covered because the check sits inside the single shared extraction function, and `getPendingAction` therefore can only ever return a vetted value. The PoC could not be executed against the patched code (no device or emulator), so closure was established by trace, not by re-running the attack.

**Gate 3 — Bypass review.** Re-read the diff for what the original reasoning might have missed. (i) *Sibling call sites*: `FlamesBackgroundService.kt` also defines `EXTRA_ACTION` and injects `voice_input`, `cancel_voice` and `quick_status` over the same Dart channel (lines 226, 248, 276, 404) — all three are in the allowlist, so the legitimate notification, tile and bubble flows keep working, and the service is `android:exported="false"` so it is not an independent injection point. (ii) *Equivalent sinks*: the only other consumer of `actionStream` is `QuickActionsService`, which is fed by the `quick_actions` plugin's own shortcut callback rather than by an exported intent, so it is unaffected. (iii) *Alternate input classes tested by reasoning*: a `null` extra (falls through to the tile check, unchanged), a blank extra (`isNullOrBlank` short-circuits, unchanged), mixed case (`VOICE_INPUT`), leading/trailing whitespace, and a Unicode-confusable value all fail the exact-match set membership — the added `trim()` is the one deliberate normalisation, and it can only widen matching to values the Dart layer already lowercases and trims, so it does not admit anything new. Case-insensitive matching was deliberately **not** added, so `VOICE_INPUT` is rejected — conservative, and no legitimate caller uses it (all three in-repo producers emit lowercase). (iv) *Residual exposure*: the allowlist bounds the *values*, not the *caller*, so an attacker can still trigger a real `voice_input` turn — it can no longer supply an arbitrary value, but the three privileged actions remain reachable from outside the app. Fully closing that would require moving third-party automation behind a signature-level permission, which is a product decision recorded in the remediation steps rather than something this minimal patch can assume.

**Gate 4 — Preserved behaviour.** The legitimate producers are unchanged: the launcher start sends no extra (falls through to `return null`), the Quick Settings tile path reaches the same `voice_input` fallback as before, and the notification's "Voice Input" / "Quick Status" / "Stop" actions all carry values inside the allowlist. Error semantics are preserved — an unrecognised action still results in no action being dispatched rather than a crash or a channel error. Note that the tile-trigger fallback branch (lines 79-83) is intentionally left untouched: it assigns the literal `voice_input` rather than reading attacker input, so it needs no validation.

**Gate 5 — Repository checks (not executed — gap).** No Kotlin/Gradle build, no `flutter analyze` and no test run was possible in this environment (no Android SDK/emulator, and the Flutter toolchain is not installed), so the Kotlin change was not compiled. The relevant guard is an existing read-only source assertion, `test/domain/tools/chat/quick_tile_contract_test.dart:276-285`, which requires `MainActivity.kt` to still contain `FlamesQuickTile.ACTION_QUICK_TILE_TRIGGER`, `"getPendingAction"` and `"clearPendingAction"`; the patch leaves all three untouched, so that test remains satisfied. That is a static assertion, not a run. **Explicit gaps: gates 2 and 5 were verified by inspection only, not by execution; no compiler, no device, no test run.** A reviewer should compile the change and add a unit assertion that an unknown action value is dropped.

**Narrowest complete change.** Two contiguous hunks in one file — the allowlist constant and the guard in the single extraction function. No existing helper covers this (the codebase has no action-validation utility), no unrelated refactor is folded in, and the patch does not touch the Dart layer, where the same allowlist could arguably live; enforcing it at the Android boundary is correct because that is where the untrusted input enters, and it protects the `getPendingAction` read path as well as the push path.

## Assumptions

Assumes a malicious app is installed on the same device as Flames (standard co-resident-app threat model for exported Android components), and that the user has previously granted Flames the microphone permission that the feature requires in normal use. The Flames app window becomes visible when the injected activity is started, so the attacker cannot hide the launch itself — only the subsequent microphone capture and agent dispatch. Whether the transcribed audio is transmitted off-device depends on the user's configured dispatch transport being ready at injection time; with no ready transport, `runTurn()` returns before the recognizer is opened.
