# Gateway WebSocket dispatches privileged tool-call frames before authentication completes

**ID:** vuln-0015
**Severity:** MEDIUM
**Found:** 2026-09-15 07:52:39 UTC
**Target:** Flames Android application (`ai.hermes.flames`), repository under audit
**Endpoint:** lib/data/datasources/remote/gateway/gateway_client.dart
**Method:** WebSocket (JSON-RPC frames)
**CWE:** CWE-306
**CVSS:** 4.8
**Confidence:** Medium
**Fix Effort:** Low

## Description

The Hermes gateway WebSocket client dispatches action-bearing frames to the device RPC receiver regardless of whether the authentication handshake has completed. `_handleIncomingData` intercepts only the auth success/failure frames while the connection is in the `connecting` state; every other frame type falls through to a dispatcher that contains no state check. A peer that answers the configured gateway origin can therefore drive device tool execution for the duration of the authentication timeout without ever presenting the gateway token. The client's own "authenticated" state is likewise asserted by the peer, not proven, because the success frame carries no nonce, signature, or channel binding. Unconfirmed, not dynamically validated: no emulator, device, or running gateway was available, so no frame was delivered to a running application.

## Impact

A peer positioned to answer the configured gateway endpoint — an on-path attacker, or the operator of an attacker-chosen gateway destination obtained through the QR pairing path — can issue `tool_call_request` frames that reach `GatewayDeviceRpcReceiver.handleRequest` and execute device tools without ever supplying the bearer token. Because only Tier 3 tools are gated by human approval on this path, every Tier 1 and Tier 2 tool is reachable: the demonstrated consequences in this repository include arbitrary-path file reads (`read_device_file`, `list_device_files`), notification and OTP extraction, clipboard reads, and an unrestricted outbound URL fetch (`read_web_page`). The window is not one-shot: the authentication timer is 10 seconds by default, automatic reconnection is enabled with up to ten attempts, and each reconnect re-opens the same window on the same stored endpoint. The net effect is that the token check is advisory rather than a gate — it determines when the client considers itself connected, not what the peer is permitted to make the device do.

## Counterevidence

The strongest case against this finding is that the transport is a WebSocket to an operator-chosen endpoint, so the peer answering it is often the legitimate gateway and the window may be hard to reach without already holding a privileged network position. That argument limits who can exploit it but does not neutralise the defect, for three reasons established in source rather than assumed. First, the authentication gate is the only thing separating an unauthenticated peer from tool execution, and it does not run: the code path from frame receipt to `ToolRegistry.executeTool` contains no state check, and the repo's own test confirms the listener is active while `connecting`. Second, the precondition is reachable without a network position in the general case, because the gateway destination itself is attacker-influenceable through the QR pairing path (`vuln-0012`) — a hostile pairing payload makes the attacker's server the configured endpoint, after which the token gate is the sole remaining control and it is bypassed here. Third, the exposure is not a narrow race: the authentication timeout is 10 seconds, automatic reconnection is enabled with ten attempts, and each attempt re-opens the same window against the same endpoint.

Checked and found absent: any state test in the dispatch chain from `_handleIncomingData` (`gateway_client.dart:226-290`) through `gateway_rpc_cubit.dart:127-139` to `gateway_rpc_receiver.dart:68-151`; any nonce, signature, HMAC, or channel binding in `GatewayAuthSuccessMessage` (`gateway_message.dart:129-143`); any server-identity verification beyond TLS certificate validation against the system trust store (no pinning exists in the codebase); and any secondary authorization layer on the gateway tool path beyond the Tier 3 check. The repository's existing test at `gateway_client_test.dart:660-700` asserts that "the auth frame is the only frame before auth_success" — that statement concerns outbound frames only and does not contradict this finding. No runtime confirmation was possible: there is no emulator, device, or gateway in the assessment environment, so no frame was ever delivered.

## Confidence Rationale

Static trace only. The absence of the state guard, the active listener during `connecting`, the 10-second default window with automatic reconnection, the peer-asserted success frame, and the execution sink are all evidenced at named locations, and the repository's own test independently confirms the listener behaviour that makes the window exploitable. The gap is that no frame was ever delivered to a running application: there is no emulator, no device, and no gateway in the assessment environment, so the end-to-end effect (a tool result returned over an unauthenticated socket) was never observed.

## What Would Change This Severity

A demonstration on a running device that a `tool_call_request` sent before `auth_success` returns a tool result would raise this to high, because it converts a missing gate into a demonstrated unauthenticated device-capability invocation; conversely, evidence that the deployment always terminates the socket or rejects frames until authentication completes at a proxy in front of the gateway would lower it.

## Technical Analysis

## The dispatcher has no state guard

`GatewayClient._handleIncomingData` is the single entry point for every inbound frame. While the connection is `connecting`, it intercepts exactly two message types and returns:

```dart title=lib/data/datasources/remote/gateway/gateway_client.dart startLineNumber=240 endLineNumber=259

        if (message is GatewayAuthSuccessMessage) {

          _authTimer = null;
          _reconnectAttempts = 0;
          _setState(GatewayConnectionState.connected);
          _startHeartbeat();
          _sendToolManifest();
          _messageController.add(message);
          return;
        } else if (message is GatewayAuthFailureMessage) {
          _authTimer?.cancel();
          _authTimer = null;
          _manuallyDisconnected = true; // Never auto-reconnect on auth rejection
          _cleanUpSocket(_CloseCause.authRejected);
          _setState(GatewayConnectionState.disconnected);
          _messageController.add(message);
          return;
        }
      }
```

Every other frame type falls out of that block and reaches the dispatcher below. That dispatcher carries a comment claiming a state precondition it does not enforce:

## The peer asserts its own authentication

The frame that flips the client to `connected` carries no proof:

```dart title=lib/domain/entities/gateway/gateway_message.dart startLineNumber=129 endLineNumber=143

  final String? message;
  final String? sessionId;

  const GatewayAuthSuccessMessage({
    this.message,
    this.sessionId,
  }) : super('auth_success');

  factory GatewayAuthSuccessMessage.fromJson(Map<String, dynamic> json) {
```

Both fields are optional strings. There is no nonce, HMAC, or binding to the `GatewayAuthMessage` the client sent, so the same peer that can answer the socket can also declare the session authenticated. The pre-auth window is therefore not merely a race — the peer controls both when it ends and what it claims.

## Remediation

1. Make the inbound dispatcher state-aware. Add an explicit authenticated-state guard to the frame dispatcher in `GatewayClient._handleIncomingData` so that action-bearing frames are only dispatched once the connection has reached the authenticated state. The existing "If connected:" comment describes the intended precondition; enforce it in code rather than in a comment.
2. Fail closed for the whole pre-authentication period. While the connection is in the connecting state, drop (or reply to with an error) every frame other than the authentication result and the liveness frames the handshake requires. Do not rely on the authentication timeout to bound the exposure, because the window re-opens on every reconnect.
3. Bind the authentication result to the request. Have the gateway echo a client-generated nonce (or sign the authentication result with the shared secret) so that a peer answering the socket cannot assert a successful authentication it did not perform. At minimum, treat the success frame as advisory and keep the tool-call path closed until a challenge has been answered.
4. Keep the RPC listener aligned with the authenticated state. The listener is currently started for every non-disconnected state; it should not accept requests before authentication, so that the transport-level guard is not the only control.
5. Add a regression test that delivers a `tool_call_request` frame before `auth_success` and asserts that no tool is executed and no response frame is sent.

## Fix Verification

Gate 1 — Security closure: REASONED, NOT EXECUTED. Re-traced source to sink through the patched code. `_handleIncomingData` now returns early for every frame received while `_state != connected`, before the dispatcher that calls `_toolCallRequestController.add(...)`. The only way to reach tool execution is `gateway_rpc_cubit.dart:127-139` -> `gateway_rpc_receiver.dart:148`, and that requires the frame to be added to the controller, which the guard now prevents until `_setState(GatewayConnectionState.connected)` has run — and that transition is itself only reachable from the `GatewayAuthSuccessMessage` branch at `gateway_client.dart:241-249`. Action-bearing frames are additionally answered with an error rather than silently dropped, so a legitimate peer that is merely early receives a diagnosable response instead of a timeout. Not executed: no Dart/Flutter toolchain, emulator, or device was available, so neither the vulnerable nor the patched behaviour was observed at runtime.

Gate 2 — Bypass review: reviewed without relying on the rationale that produced the patch. Sibling paths to the same sink were enumerated: `_toolCallRequestController.add` is called at exactly one site (`gateway_client.dart:276`), and `_elicitationRequestController.add` at exactly one site (`:282`); both are now behind the guard. The other consumer of frames, `_messageController.add`, is deliberately left reachable for all states so that UI state and error reporting are unaffected — that channel carries no execution authority, and the tool-call stream is a separate broadcast controller, so leaving it open does not reopen the boundary. Alternate input classes checked: a frame that self-identifies as `auth` with a success-like `status` (`gateway_message.dart:17-27`) still only sets `connected` through the existing branch and is not affected by this change; a `tool_call_request` arriving during `reconnecting` is likewise refused, which is correct because `_state` is not `connected` in that state either. The one deliberate behaviour change is that a peer which (incorrectly) issues tool calls before authenticating now receives an error frame instead of execution — that is the intended fail-closed direction.

Gate 3 — Preserved behaviour: PARTIAL. The legitimate handshake is unchanged: the auth frame is still sent on connect (`:212-216`), `auth_success` still transitions to `connected` and starts the heartbeat and manifest (`:241-249`), `auth_failure` still disconnects without reconnecting (`:250-258`), and post-authentication tool calls, elicitations, pings, and text deltas all flow exactly as before. The behaviour that changes is confined to pre-authentication frames, which is the security fix. One item could not be verified statically: whether any deployment relies on pre-auth tool dispatch as a latency optimization — the repository contains no such dependency (the tool manifest is only sent after `auth_success` at `:247`/`:299-307`, so the server cannot legitimately issue tool calls before then). The existing test at `gateway_client_test.dart:660-700`, which asserts the auth frame is the only outbound frame before `auth_success`, remains satisfied.

Gate 4 — Repository checks: NOT RUN, and this is an explicit gap. `dart analyze` and `flutter test` are unavailable (no Dart or Flutter SDK in the assessment environment). The patch introduces no new imports (`GatewayConnectionState` is already imported at `gateway_client.dart:8` and `sendToolCallResponse` / `sendElicitationResponse` are methods on the same class), the line range was verified against the file, and the surrounding code style is matched, but no formatter, analyzer, or test suite was executed. A reviewer must run the package's own checks before merging. A regression test should be added that delivers a `tool_call_request` before `auth_success` and asserts no execution and no response.

## Assumptions

Assumes the app is configured with a gateway endpoint (the normal operating state for gateway mode) and that the peer answering that endpoint is not necessarily the legitimate gateway — the attacker either sits on the path or operates the endpoint, the latter being reachable through the attacker-controlled QR pairing destination reported separately as `vuln-0012`. Assumes the device RPC receiver is active, which the application does automatically for any non-disconnected state. Assumes the user has already granted the device permissions the reachable tools depend on; the finding does not bypass the operating-system permission model, and Tier 3 tools still require human approval on this path.
