# SSRF via the `read_web_page` agent tool: unrestricted URL fetch reachable from model output and from an inbound gateway RPC frame, with no permission gate and no host validation

**ID:** vuln-0013
**Severity:** LOW
**Found:** 2026-09-15 07:00:50 UTC
**Target:** Flames Android application (`ai.hermes.flames`), repository under audit
**Endpoint:** read_web_page (lib/domain/tools/chat/tool_registry.dart:1534)
**Method:** AGENT-TOOL
**CWE:** CWE-918
**CVSS:** 3.7
**Confidence:** Medium
**Fix Effort:** Low

## Description

The agent tool `read_web_page` fetches any `http`/`https` URL chosen by the language model **or supplied in an inbound gateway RPC frame** and returns the page body to the caller, but it is registered as a permissioned tool without a permission check and its URL validator accepts loopback, private, link-local, and cloud-metadata addresses. Because the ReAct loop auto-executes every non-Tier-3 tool and the gateway RPC receiver gates only Tier 3, a URL that reaches the device as data — a poisoned web page, a notification body, a shared link, a compromised gateway, or a directly dispatched frame — can steer the device into fetching internal services that are not reachable from the public internet. On the gateway path the response is returned to the frame's sender over the same socket; on the ReAct path it is forwarded to the configured LLM API.

**Unconfirmed, not dynamically validated.** This assessment is source-only: no emulator, no `adb`, and no running application instance were available. Every claim below is supported by code at a named location and, where noted, by executing the exact validator logic in a standalone Dart runtime; the end-to-end request was never issued from the application.

## Impact

A party who can influence model input — by publishing a page the agent is asked to summarise, sending a notification the user has granted the app access to read, or controlling the configured model endpoint — can make the device issue HTTP(S) requests to addresses of their choosing and have the responses returned into the conversation, where they are forwarded to the configured LLM API.

A party who can send frames on the paired gateway connection obtains a stronger version of the same primitive. The frame names the tool and carries the destination URL, no approval is requested, and the fetched body is written back to the sender over the same socket. That removes the model from the loop entirely: the attacker does not have to induce a tool call and does not depend on a third-party model endpoint to observe the result. The device is additionally told to advertise the capability — the tool manifest sent after a successful handshake lists `read_web_page` because the manifest provider applies an enablement filter and no pruning.

The concrete targets that become reachable from the device are the ones the threat model treats as internal: the on-device Hermes gateway and API server (`http://localhost:8642`, `http://127.0.0.1:8644/rpc`), any RFC1918 host on the user's LAN, and link-local cloud metadata services. The Hermes gateway is the component that holds the operator's LLM API key, so an SSRF that can read it is a credential-access primitive, not just a reachability bug. On the ReAct path, fetched content is additionally disclosed to whichever LLM provider the app is configured against, which is an unanticipated egress path for internal response bodies.

The demonstrated consequence is unauthorized outbound request capability and information flow, with the response returned to the caller on the gateway path. The specific contents readable from each internal service were not observed, so the confidentiality impact is assessed as limited rather than high.

## Counterevidence

The strongest argument against the ReAct framing is that it requires the model to choose an internal destination, which is an extra uncertain hop the attacker does not fully control. That argument does not apply to the gateway framing, where the tool name and the URL arrive in the same frame, which is why both paths are reported together. It also does not neutralise the ReAct path on its own, because the URL is model-supplied data with no host policy behind it and the tool is reachable through `tool_search`/`tool_describe` re-discovery.

The strongest argument against the gateway framing is that the gateway is treated as trusted infrastructure, so a malicious gateway operator is not the interesting case. This narrows but does not close the finding. The Tier 2 label is the device's own declared policy for capabilities that must not run on remote say-so, and this tool runs on remote say-so. The precondition is also reachable by an outside party rather than only by the legitimate operator: a hostile pairing payload makes the attacker's server the device's gateway, and on the pairing path the client then enters gateway mode and opens the socket without a destination confirmation step. That pairing weakness is tracked separately, and this finding does not depend on it — the point here is that once any server holds the device's gateway connection, the device's own tier policy does not stop a LAN read.

A third argument is that Android 9 and later block cleartext traffic, so `http://169.254.169.254/` and `http://192.168.1.100/` would fail. This is only partly true and does not neutralize the finding. The engine revision this project pins does not apply the Android cleartext policy to `dart:io` — the Android embedder at that revision contains no `NetworkSecurityPolicy` or `isCleartextTrafficPermitted` reference, `FlutterApplicationInfo.domainNetworkPolicy` is hard-coded to an empty string, and the manifest-metadata plumbing that once carried a per-domain policy was removed upstream. More decisively, the runtime hook explicitly exempts loopback (*"Loopback connections are always allowed"*) and permits `https` unconditionally, so `http://127.0.0.1:8644/rpc`, `http://localhost:8642/health`, and `https://127.0.0.1:8642/` are reachable whether or not cleartext is restricted. That claim rests on source inspection of the pinned revision rather than a device request, and a builder using a different SDK revision could behave differently; the finding does not depend on it.

A fourth argument is that the enabling Tier-2 gate defect is reported separately. The gate defect is the enabling condition; this finding is the specific, independently actionable consequence — an unrestricted-destination fetch with a redirect bypass and two distinct trigger paths — and it is closed by URL and redirect validation alone, without touching the gate.

A fifth argument, considered and rejected, is that this is the same vulnerability as the model-output framing and should not be counted twice. It is one vulnerability with two reachability routes, and it is presented once, here, with both routes and one fix. The gateway route is included because it is materially stronger: it does not depend on model behaviour and it returns the body to the requester.

Checked for and not found: any host, IP-range, or allowlist policy on the fetch path; any destination revalidation across redirects; any approval step on the gateway path for a non-Tier-3 tool; any runtime observation of an internal response body, which is why confidentiality is assessed as limited rather than high.

## Confidence Rationale

The entire chain is a static trace on both trigger paths. No emulator, `adb`, or running application instance was available, so no request was issued from the application and no internal response body was observed, and neither the ReAct dispatch nor the gateway frame dispatch was exercised end to end. What was executed is the URL validator itself, copied verbatim into a Dart 3.6 runtime, which confirmed that every loopback, RFC1918, link-local, metadata, IPv4-mapped IPv6, and alternative-notation destination is accepted. The gateway path additionally rests on reading the frame dispatch and the RPC receiver rather than on observing a frame being executed. The specific contents readable from each internal service therefore remain unverified, which is why confidentiality is assessed as limited rather than high.

## What Would Change This Severity

A request issued from a running device that returns content from an internal-only service — for example a response body from the on-device Hermes gateway on `localhost:8642` or the Pocket Node RPC on `127.0.0.1:8644`, returned to the gateway frame's sender — would raise this to high by converting a demonstrated request capability into demonstrated internal-data access; conversely, evidence that the build environment enforces a destination policy that the pinned engine revision does not, or that the gateway connection cannot be obtained by a party other than the legitimate operator, would lower it.

## Technical Analysis

## 1. The tool is registered as permissioned but carries no permission check

`lib/domain/tools/chat/tool_registry.dart:1531-1555` registers `read_web_page`:

```dart
securityTier: SecurityTier.tier2Permission,
execute: (args) async {
  final url = args['url']?.toString() ?? '';
  return service.fetchReadableText(url);
},
```

There is no `checkPermission` field. The `RegisteredTool` constructor makes it optional (`tool_registry.dart:53-60`), so the omission compiles silently.

## 2. The single enforcement point short-circuits

`lib/domain/tools/chat/tool_registry.dart:238-258` is the only gate:

```dart
if (SecurityPolicy.requiresPermission(tool.securityTier) &&
    tool.checkPermission != null) {
  final granted = await tool.checkPermission!();
  if (!granted) {
    return Left(PermissionFailure('Permission denied for tool: $name'));
  }
}
return await tool.execute(arguments);
```

`requiresPermission` returns true for `tier2Permission`, but the `&&` requires a non-null callback. With `checkPermission == null` the entire block is skipped and execution falls straight through to `tool.execute(arguments)`. The declared tier therefore has no effect for this tool. Other Tier-2 tools in the same file do supply a checker (`tool_registry.dart:317`, `:783`, `:842`, `:872`, `:1109`, `:1366`, `:1705`), which shows the field is the intended mechanism and that its absence here is a defect rather than a design choice.

## 3. The ReAct loop auto-executes everything that is not Tier 3

`lib/presentation/screen/chat/cubit/agent_cubit.dart:752-769`:

```dart
// Tier 3: Pause loop and wait for HITL approval.
if (registered.securityTier == SecurityTier.tier3Hitl) {
  ...
  emit(WaitingApproval(request));
  return; // Execution pauses until approveAction or rejectAction
}

// Tier 1 & Tier 2: Auto-execute.
emit(ExecutingTool(toolName, arguments: arguments));
final execResult = await _toolRegistry.executeTool(toolName, arguments);
```

Only `tier3Hitl` pauses. Because `read_web_page` is Tier 2 and its permission block is a no-op, the call executes with no confirmation and no permission evaluation. The URL comes straight from the model's tool-call arguments (`agent_cubit.dart:720-728` decodes `toolCall.argumentsFragment`; `tool_registry.dart:1550` reads `args['url']`).

## 4. The URL validator imposes no host policy

`lib/domain/tools/chat/url_reader_service.dart:58-70`:

```dart
static String? validateUrl(String url) {
  final trimmed = url.trim();
  if (trimmed.isEmpty) return 'URL is empty';
  final uri = Uri.tryParse(trimmed);
  if (uri == null) return 'URL is missing a host';
  final scheme = uri.scheme.toLowerCase();
  if (scheme != 'http' && scheme != 'https') {
    return 'Unsupported URL scheme: ${uri.scheme}';
  }
  if (uri.host.isEmpty) return 'URL is missing a host';
  return null;
}
```

The only checks are a non-empty string, a parseable URI, an `http`/`https` scheme, and a non-empty host. There is no loopback, RFC1918, link-local, or metadata-endpoint rejection, and no allowlist. The parameter's own description (`tool_registry.dart:1543`) advertises this: *"Absolute http/https URL to read"*.

Executing this exact function in a Dart 3.6 runtime returned `null` (accepted) for every internal target tested: `http://127.0.0.1:8644/rpc`, `http://localhost:8642/health`, `http://169.254.169.254/latest/meta-data/`, `http://10.0.2.2:8642/v1/models`, `http://192.168.1.100:8642/v1/models`, `http://172.16.5.5/admin`, `http://[::1]:8642/`, `http://[::ffff:127.0.0.1]/`, and the decimal/hex spellings `http://2130706433/` and `http://0x7f000001/`. Only non-HTTP schemes (`file:`, `gopher:`) are refused.

A repository-wide search for any host or IP policy applied to this path — `isLoopback`, `isLinkLocal`, private-range checks, denylists, allowlists, or Dio interceptors — found none in `lib/`. The only allowlist in the tool layer is `SystemSettingsAllowList` for the unrelated `launch_system_setting` tool.

## 5. Redirects are followed without revalidation

`lib/data/datasources/tools/chat/url_reader_service.dart:40-54`:

```dart
final response = await _dio.get<String>(
  url,
  options: Options(
    responseType: ResponseType.plain,
    followRedirects: true,
    ...
```

`validateUrl` runs exactly once, in `fetchReadableText` (`:72-76`), against the initial URL. `followRedirects: true` delegates hop-following to the HTTP client, which applies no host policy. An attacker-controlled public page returning `302 Location: http://127.0.0.1:8644/rpc` therefore defeats any initial-URL check. The repository's own tests cover only scheme rejection and empty input (`test/domain/tools/chat/url_reader_html_test.dart:45-59`); no test asserts a private-host policy, which is consistent with one never having been intended.

## 6. Reachability of the tool itself

`read_web_page` is enabled by default: `register` seeds `_toolEnabledStates` with `true` (`tool_registry.dart:208-211`), and `isToolEnabled` defaults to `true` for unknown names (`:222`). `syncWithToolRegistry` (`lib/domain/services/skills/skills_registry_service.dart:386-405`) only ever disables tools named by an *inactive* skill; `read_web_page` appears in no skill's `tools:` list, so it is never disabled. With progressive tool pruning enabled by default, the tool is not in the initial tool list (it appears in no `ToolSearchIndex` category), but the Tier-1 `tool_search` meta-tool ranks over all enabled tools (`tool_registry.dart:160-176`) and `tool_describe` returns any tool's full schema (`:180-205`); discovered names are re-added to the tool list on the next turn (`agent_cubit.dart:896-905`). The tool is thus reachable in two additional auto-executing steps.

## 8. On cleartext reachability

The engine revision this project pins (`.metadata` → `d3b14c876900e553bc736ca19295fc09e3853e8e`, engine `a804b261645ef8c13eb3d5c44a5c2fb0340c5539`) does not enforce the Android cleartext policy on `dart:io`. At that revision the Android embedder contains no `NetworkSecurityPolicy` or `isCleartextTrafficPermitted` reference at all, and `FlutterApplicationInfo.domainNetworkPolicy` is hard-coded to the empty string; the manifest-metadata plumbing that once carried a per-domain policy was removed upstream. The runtime hook that does exist, `_getHttpConnectionHookClosure`, permits a connection when the scheme is `https`, **or unconditionally when the host is loopback** — its own comment reads *"Loopback connections are always allowed"* — and otherwise permits cleartext because `may_insecurely_connect_to_all_domains` defaults to `true` and the Android embedder never passes `--disallow-insecure-connections`.

The consequence is that the loopback targets in this finding are reachable regardless of the cleartext question, and the remaining cleartext targets are reachable on this pinned revision. This claim rests on source inspection of the pinned engine revision rather than on a request issued from a device, and the builder's actual SDK revision may differ from the pinned one; the finding does not depend on it, because `https://` internal targets and loopback are reachable either way.

## 9. Second trigger path: an inbound gateway RPC frame

The same tool is reachable with no model involvement, and on that path the response is delivered to the party that asked for it.

- **Frame parsing.** `lib/domain/entities/gateway/gateway_message.dart:280-293` (`GatewayToolCallRequestMessage.fromJson`) takes `tool` and `arguments` verbatim from the wire; the dispatch cases that route `tool_call_request` and `tool_call` to it are at `:48-50`.
- **Routing.** `lib/data/datasources/remote/gateway/gateway_client.dart:269-277` forwards the parsed frame to `_toolCallRequestController` whenever a listener is attached.
- **Consumer.** `lib/presentation/screen/gateway/cubit/gateway_rpc_cubit.dart:85-91` subscribes to that stream, and `:127-139` calls the receiver with `onApprovalRequired: _requestHitlApproval`.
- **Gate.** `lib/domain/services/gateway/gateway_rpc_receiver.dart:89` tests only `SecurityPolicy.requiresHitl(tool.securityTier)`. `read_web_page` is Tier 2 (`tool_registry.dart:1548`), so no approval is requested, and `:148-151` calls `toolRegistry.executeTool(request.tool, request.arguments)`.
- **Result channel.** `gateway_rpc_receiver.dart:167-179` parses the tool's raw string result and sends it straight back with `sendToolCallResponse(callId: request.id, result: resultMap)`.

This path differs from the ReAct path in two ways that matter to exploitability. It does not depend on the model choosing to emit the call, and the fetched body is returned directly to the frame's sender rather than only being forwarded to the configured model endpoint.

The device is also told to advertise the capability. `getOpenAiToolDefinitions()` (`tool_registry.dart:233-236`) applies only the enablement filter and performs no pruning, and it is wired as the manifest provider at `lib/common/injection/modules.dart:39-40`; the manifest is sent after a successful handshake at `gateway_client.dart:247` and `:299-307`. `read_web_page` is enabled by default (`tool_registry.dart:208-211`, `:222`) and appears in no skill's tool list, so it is present in that manifest and the server is informed of it.

The listener is live whenever the chat screen is mounted: `GatewayRpcCubit` starts listening from its constructor (`gateway_rpc_cubit.dart:55`, `:67-69`), the factory that builds it does not override `autoStart` (`lib/common/injection/injection.config.dart:462-467`), and the screen resolves it during `initState` (`chat_screen.dart:201-202`). `GatewayClient` only drops the frame when no listener is attached (`gateway_client.dart:270-274`), which is not the state the application runs in.

## Proof of Concept

No emulator, `adb`, or running application was available, so the end-to-end request was not executed. The following is the reachability path established from source, with the validator behaviour confirmed by executing the exact function in a standalone Dart runtime.

1. Confirm the tool is registered as permissioned with no permission check: `lib/domain/tools/chat/tool_registry.dart:1531-1555` declares `securityTier: SecurityTier.tier2Permission` and no `checkPermission`.
2. Confirm the gate short-circuits: `lib/domain/tools/chat/tool_registry.dart:250-256` requires both `requiresPermission(tier)` and a non-null `checkPermission`; the null callback skips the block and control reaches `tool.execute(arguments)` at `:257`.

## Remediation

Enforce the destination policy in the reader itself, so that every caller — the ReAct loop, the gateway RPC receiver, and the share-intent prefetch — is covered by one control rather than by per-caller checks.

1. Add a non-public-address policy to the URL validator: reject loopback, RFC1918, carrier-grade NAT, link-local, multicast, unspecified, and IPv6 unique-local and IPv4-mapped addresses, together with `localhost`, `.local`, `.internal`, `.home.arpa`, and trailing-dot variants, plus decimal, hexadecimal, and octal spellings of IPv4 addresses. Apply it after host lower-casing and dot-trimming so the comparison cannot be evaded by case or a trailing dot.
2. Stop letting the HTTP client follow redirects. Follow them manually with a small hop limit and re-run the full validator on every hop, resolving each `Location` against the current URL before checking it. This closes the redirect-to-internal bypass and bounds redirect loops.
3. Declare the tool as Tier 3 rather than Tier 2. A network fetch of an arbitrary destination is a state-changing egress action, and the current Tier-2 classification is only nominal because no runtime permission exists to check; routing it through the existing human-in-the-loop modal makes the destination visible to the user before the request is issued.
4. Where a permission check is genuinely appropriate, treat a null `checkPermission` on a permissioned tool as a failure rather than a pass, so that a tier declaration cannot be silently neutralized by omitting the callback.
5. Add regression tests covering the private-range, metadata, IPv4-mapped IPv6, alternative-notation, and redirect cases, alongside the existing scheme and empty-input tests.

Note that restricting the tool to public destinations changes behaviour for users who legitimately point the agent at a LAN service; if that use case must be preserved, gate it behind an explicit opt-in allowlist rather than leaving the destination unrestricted.

## Fix Verification

**Gate 1 — Security closure.** Re-traced source to sink through the patched code. The sink is `Dio.get` in `fetchUrl`. After the patch, every `Dio.get` is preceded by `UrlReaderServiceBase.validateUrl(current)` on the same URL string, and `followRedirects` is `false`, so the client can no longer reach a host the validator has not seen. `_isNonPublicHost` rejects `127.0.0.1`, `localhost`, `169.254.169.254`, `10.0.2.2`, `192.168.1.100`, `172.16.5.5`, `[::1]`, `[::ffff:127.0.0.1]`, and the decimal/hex spellings, returning a message that `fetchUrl` converts to `Left(ValidationFailure(...))` before any socket is opened. The three callers — `fetchReadableText`, the gateway receiver, and the share-intent prefetch — all funnel through this single function, so the control is not caller-specific. A redirect to an internal address now resolves to a new `current`, loops, and is rejected by the same check on the next iteration.

## Assumptions

**ReAct trigger path.** Assumes a configured model endpoint and a completed agent turn, so that a tool call is dispatched. Assumes the model emits, or can be induced to emit, a `read_web_page` call whose `url` argument is an internal destination — the attacker does not need direct network access to the device, only influence over text the model consumes (a page it is asked to summarise, a notification the user granted access to read, or a configured model/gateway endpoint). No user confirmation is required, because the tool is Tier 2 and its permission callback is absent.

**Gateway trigger path.** Assumes the device has completed a gateway handshake with a server the attacker controls or has compromised, and that the chat screen has been mounted so the RPC listener is attached. The attacker does not need to influence the model at all: the tool name and destination are carried in the frame. No authentication beyond the gateway handshake is required, no user interaction occurs, and the response is returned on the same socket.

**Both paths.** No authentication or device access is required beyond the application being installed, configured, and (for the gateway path) paired. The gateway and LLM endpoints themselves are otherwise treated as trusted infrastructure; this finding concerns what a server on that connection, or text the model consumes, can make the device do.
