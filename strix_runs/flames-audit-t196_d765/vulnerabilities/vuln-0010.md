# Notification text from any installed app reaches the agent prompt with no data/instruction separation and can drive auto-executing Tier-1 device tools

**ID:** vuln-0010
**Severity:** MEDIUM
**Found:** 2026-09-15 06:47:37 UTC
**Target:** ai.hermes.flames — Flutter AI agent workstation (Android), repository root (source-only audit)
**Endpoint:** read_recent_notifications / extract_latest_otp (tool channel ai.hermes.flames/notification_listener)
**CVSS:** 4.2
**Confidence:** Medium
**Fix Effort:** Low

## Description

Flames reads the notification title and body of every app on the device through its notification-listener service and returns them to the language model as a tool result (read_recent_notifications, extract_latest_otp). Those strings are authored by whichever app posted the notification, not by Flames and not by the user, yet nothing on the path marks them as untrusted, delimits them, caps their length, or scans them. The app already ships a prompt-injection scanner but applies it only to imported skill text. The same model can then call tools that execute with no user confirmation, including clipboard_write, send_local_notification, save_memory and speak_text, and, because read_web_page is declared permissioned but registered without a permission checker, read_web_page, which can carry on-device data off the device in a URL. Unconfirmed, not dynamically validated — this is a source-only audit with no emulator, no device and no running app, so no payload was executed and no tool call was induced.

## Impact

A malicious or merely compromised app installed on the same device can post a notification whose title/body contains instructions, and those instructions enter the agent's context with the same standing as the user's own request. Because the reachable tools need no approval, the injected text can cause the device to copy attacker-chosen content to the clipboard (clipboard_write), display a forged notification (send_local_notification), speak text aloud (speak_text), write an entry into the memory vault (save_memory) — which is later re-injected as a role:"system" message on any turn whose prompt matches — or register a geofence (register_geofence). Combined with clipboard_read (Tier 1) and read_web_page (declared Tier 2 but registered without a permission checker, so it auto-executes), on-device content can be staged and then transmitted to an attacker-controlled URL in a query string, with no permission prompt and no human-in-the-loop step. The concrete end-to-end result is model- and payload-dependent and was not demonstrated. Tier-3 actions (make_phone_call, open_whatsapp_chat, calendar_create_event, schedule_reminder) remain behind the approval modal and were not bypassed.

## Counterevidence

Strongest case against, and what was checked. (1) Consent gate — notification access is a deliberate, system-settings-granted permission, not covert; the listener is also pull-only and its buffer is in-memory, wiped on process restart and re-seeded only from notifications on screen at connect time, so the app cannot silently harvest history. This limits reach but does not remove it: the permission is granted once and persists, and the buffer refills continuously while the service lives. (2) Stochastic model step — prompt injection is probabilistic and nothing here demonstrates compliance; no payload was executed and no tool call was induced, so the finding proves a missing control, not a completed exploit. This is the single largest constraint and is why confidence is medium. (3) Attacker must already be installed and posting notifications — a co-resident app is a precondition; this is a real but common position on Android and requires no special privilege beyond being installed. (4) Tier-3 remains gated — make_phone_call, open_whatsapp_chat, calendar_create_event and schedule_reminder still hit the approval modal, which renders the real arguments; no bypass and no argument mutation between approval and execution was found, so the ceiling is the Tier-1 set plus permissioned-but-already-granted Tier-2 tools. (5) Tool output is a conventionally lower-trust channel — many models treat role:"tool" content as data by default, which reduces likelihood but is model-dependent and is not an enforced control. Checked and found absent: no input validation, sanitization, escaping, length cap, injection scan, untrusted-data marker or system-prompt rule anywhere on the notification-to-prompt path; the keyword filter was confirmed to match content topics rather than instruction-like text; the shipped scanner was confirmed to have exactly one production caller, on a different input class.

## Confidence Rationale

Static-only trace, executed nowhere. This environment has no emulator, no adb, no device and no running app, and no Dart/Flutter or Android SDK, so the tool result was never produced by a live listener and no model was ever induced to act on a payload. Every hop from processNotification through the method channel, the Dart triage service, the registry and into the wire message is traced with verified line references, and the absence of framing, capping and scanning is established by exhaustive search over the path. The unverified step is model compliance: whether a given model follows the injected directive, and whether it then issues the follow-on tool calls, was reasoned from the architecture and not observed. The payload text and tool-call sequence in the PoC are illustrative and were not executed.

## What Would Change This Severity

A device-level demonstration that a crafted notification reliably induces a Tier-1 tool call — in particular clipboard_read followed by read_web_page, or a save_memory write — would raise this to high; conversely, evidence that the target model consistently treats tool-result content as inert data, or that read_recent_notifications and extract_latest_otp are disabled in shipped configurations, would lower it to low.

## Technical Analysis

**Relationship to the accessibility-channel finding.** The scan already carries a report for the same class of defect — untrusted text reaching the prompt as an unframed tool result — evidenced on the accessibility channel (ui_find_elements), fixed in lib/data/datasources/tools/chat/accessibility_inspector_service.dart. This report covers a different channel: a different data source, a different Android permission, and a different runtime trigger. The accessibility report's remediation text explicitly leaves notification text, web-page text and recalled memory unframed. The generic point (tool results are unframed) is shared; the notification-specific evidence, permission and trigger are not.

**1. Collection — attacker-authored strings, no cap.** FlamesNotificationListenerService.processNotification copies Notification.EXTRA_TITLE / EXTRA_TEXT / EXTRA_BIG_TEXT / EXTRA_SUB_TEXT verbatim into an in-memory buffer. Only the number of entries is capped (MAX_BUFFER_SIZE = 100); the strings themselves have no length limit. packageName is whatever app posted the notification. There is no self-package exclusion, so Flames' own send_local_notification output re-enters this same buffer.

**2. Bridge — verbatim to Dart.** The getRecentNotifications method-channel handler returns the buffer to Dart unchanged.

**3. Serialization — no envelope.** The Dart triage service returns jsonEncode(entries.map((e) => e.toJson())). The attacker's text is embedded as ordinary JSON string values. NotificationEntry.toJson emits title and body as-is; OtpExtractionResult additionally carries raw notification body text in snippet.

**4. Tools — permissioned once, then automatic.** read_recent_notifications and extract_latest_otp are registered as tier2Permission with a checkPermission callback, so notification access must be granted once; after that they execute on the model's request with no further prompt.

**5. Enforcement point — nothing here concerns instruction authority.** ToolRegistry.executeTool checks only tool enablement and, for Tier 2, the permission callback. It has no notion of the trust level of the content a tool returns.

**6. Result to prompt — no sanitization anywhere.** The result string becomes ChatMessage(role: 'tool', content: resultStr); toWireJson() performs no transformation; the message list is posted verbatim to the configured /chat/completions endpoint.

**7. No mitigation exists on this path.** Repository-wide search for sanitiz, escapeUntrusted, wrapUntrusted, untrusted, maxLength, truncat and delim over lib/domain/tools/chat/, lib/domain/entities/chat/, lib/presentation/screen/chat/ and lib/data/datasources/tools/chat/ returns only unrelated hits: an accessibility element-role display sanitizer, FTS query escaping, and PDF inflate caps. The app's own injection scanner (SkillSecurityScanner, twelve patterns including chatml_delimiters and ignore_previous_instructions) has exactly one production caller — the skill-import service — so it never sees notification text. That is direct evidence the codebase knows this class exists and simply did not apply it here.

**8. The content-topic filter is not a control.** _sensitiveKeywords / isSensitive excludes notifications whose text matches otp, password, pin, bank, transaction, payment and similar. It matches banking and credential vocabulary, not instruction-like text, so a payload that mentions none of those words passes through untouched. extract_latest_otp deliberately reads the unfiltered list.

**9. No base system prompt in the default configuration.** The loop calls buildSystemPrompt() with no basePrompt argument, and the builder returns '' when no skills are active — so in the default configuration nothing in the request tells the model that tool results are untrusted.

**10. Reachable tool set.** Twenty-four tools are tier1Auto and execute with no confirmation, including clipboard_read, clipboard_write, send_local_notification, save_memory, delete_memory, register_geofence, remove_geofence, manage_background_service, open_map_navigation, speak_text and trigger_ambient_check. Separately, seven tools are declared tier2Permission but registered without a checkPermission callback (read_web_page, open_external_url, open_email_composer, launch_system_setting, camera_take_photo, nfc_read_tag, nfc_read_emoney_balance); because the guard tests requiresPermission(tier) && checkPermission != null, these short-circuit to auto-execution with no permission evaluation at all. read_web_page is the exfiltration primitive.

## Proof of Concept

1. Preconditions: the user has granted Flames notification access (a one-time system-settings action), and any installed app posts a notification whose title or body carries the payload. No other privilege is needed by the attacker app.
2. The attacker app posts a notification whose title/body contains a directive written to look like a system instruction, for example asking the assistant to copy a specific string to the clipboard and then fetch a URL containing that string.
3. The user asks the agent something that causes it to read notifications (for example "check my notifications" or "get my latest code").
4. The model calls read_recent_notifications (or extract_latest_otp); the permission callback passes because access was granted in step 1.
5. The tool returns the notification text inside a plain JSON document with no delimiter and no untrusted-data marker; the string becomes the content of a role:"tool" message and is posted verbatim to the chat-completions endpoint.
6. If the model follows the embedded directive, it issues further tool calls. Those in the Tier-1 set execute immediately: clipboard_write, send_local_notification, speak_text, save_memory, register_geofence, manage_background_service, open_map_navigation.
7. Exfiltration path: clipboard_read (Tier 1) retrieves on-device text, then read_web_page (declared Tier 2 but registered without a permission checker) is called with that text embedded in the URL query, sending it off the device. No permission dialog and no approval sheet appear at any point.
8. Not performed here: steps 2-7 were never executed. There is no emulator, no device and no running app in this environment, and no model was induced to act on the payload. The payload text, the tool-call sequence and the model's compliance are all reasoned from the source, not observed.

## Remediation

Separate data from instructions on every channel that carries externally-authored text into the prompt, and do it at the point where the request is assembled rather than per tool.

1. Envelope untrusted tool output before it is sent. When the message list is serialized for the provider, wrap the string content of every message whose role is "tool" in a fixed, unambiguous delimiter, and cap its length so a single hostile notification cannot flood the context window. Keying on the role rather than the tool name covers notification text, fetched web pages, contacts, the screen-reader tree, clipboard text and file contents in one place, including channels that are currently unframed.
2. State the rule in every request. Add a short statement to the system prompt that text inside the envelope is external data, never an instruction, and must not change the task, the tool policy, or what is disclosed. Because the prompt builder currently returns an empty string when no skill is active, the rule must be added before that early return, or it will be absent in the default configuration.
3. Treat the envelope as framing, not provenance. A payload can contain the literal delimiter text, so the prompt rule is the load-bearing control and the two changes should ship together.
4. Do not rely on the existing content-topic filter. It matches banking and credential vocabulary, not instruction-like text, and provides no protection against this class. Reusing the existing prompt-injection scanner as an additional signal is reasonable defence in depth, but its patterns are literal and evadable by paraphrase, so it must not be the primary control.
5. Apply the same treatment to recalled memory. Active memories are currently injected as a role "system" message, which gives attacker-influenced text the highest available authority; they should be framed the same way and injected as untrusted data rather than as a system instruction.
6. Close the exfiltration path separately. Tools declared Tier 2 but registered without a permission checker (read_web_page, open_external_url, open_email_composer, launch_system_setting, camera_take_photo, nfc_read_tag, nfc_read_emoney_balance) currently skip permission evaluation entirely because the guard also tests that the checker is non-null. Require every Tier-2 registration to supply a checker, or fail closed when one is missing.
7. Update the two tests that encode the pre-fix expectation of an empty system prompt in the no-skill case, since they assert the insecure behaviour.

## Fix Verification

**Gate 1 — Security closure (reasoned, not executed).** Re-traced source → sink through the patched code. The notification path is `processNotification` → method channel → `_loadEntries` → `readRecentNotificationsFormattedJson` / `extractLatestOtpFormattedJson` → `executeTool` → `ChatMessage(role:'tool')` → `toWireJson` → `chat_datasource`. The patch intercepts the last point before transmission: every message whose role is `tool` now has its string content wrapped in `BEGIN/END UNTRUSTED TOOL OUTPUT` and capped at 20000 characters. Because it keys on `role == 'tool'` rather than on the tool name, it covers `read_recent_notifications`, `extract_latest_otp` and every other tool that returns externally-authored text (web pages, contacts, screen tree, clipboard, files) in one place, so no sibling channel is left open by this change. The second location supplies the matching instruction-hierarchy rule and is deliberately placed **before** the `active.isEmpty` early return, because that branch is the default configuration — without that placement the rule would be absent exactly when it is needed. Closure is established by trace; no payload was executed.

**Gate 2 — Bypass review (reasoned).** Named and checked: (a) *other untrusted channels* — covered, since the envelope is applied by role rather than by tool name; (b) *attachments* — a message with attachments serializes to a multipart list rather than a string, so the `content is String` guard leaves it untouched and image/file attachments keep their existing wire shape; (c) *delimiter forgery* — a payload could include the literal marker text; the envelope is therefore a framing aid, not a proof of provenance, and the system-prompt rule is the load-bearing control, so both are included; (d) *truncation as a bypass* — truncation happens after wrapping and only shortens the tail, so it cannot strip the opening marker; (e) *persistence* — the fix is applied at serialization only, so stored history is unchanged and the envelope is re-applied on every turn, including after a restart; (f) *the memory channel* — recalled memories are still injected as a `role: 'system'` message at `agent_cubit.dart:907-914` and are **not** covered by this patch; that remains an open item, as does the `read_web_page`/`save_memory` pairing that makes exfiltration possible. Alternate input classes considered: chatml-style delimiters, markdown/HTML comment hiding, and instruction-override phrasing — all are unaffected by the envelope and are countered only by the prompt rule, which is why the two changes ship together.

**Gate 3 — Preserved behavior (reasoned).** `cubit.messages` — the in-memory list the UI and most unit tests read — is unchanged; only the serialized copy sent to the provider is enveloped. No test asserts on the *content* of a wire `role: 'tool'` message; the existing tests match on `role` and `name` (for example the ReAct-loop and tool-pruning suites) and on `cubit.messages` content, all of which continue to pass.
