# Credentials can be transmitted over cleartext HTTP/WS because endpoint validators accept http:// and ws:// URLs

**ID:** vuln-0009
**Severity:** MEDIUM
**Found:** 2026-09-15 06:39:06 UTC
**Target:** Flames Android app (ai.hermes.flames / Flutter package flutter_ai_agent) — repository /workspace/flames-audit-t196
**Endpoint:** lib/domain/services/gateway/gateway_url.dart, lib/domain/tools/pairing/pairing_parser.dart, lib/data/datasources/remote/chat/chat_datasource.dart, lib/data/datasources/remote/gateway/gateway_client.dart
**Method:** HTTP / WebSocket
**CWE:** CWE-319
**CVSS:** 5.9
**Confidence:** Medium
**Fix Effort:** Low

## Description

The app's endpoint validators accept cleartext `http://` and `ws://` URLs, and the stored credentials are then attached to whatever endpoint results: the LLM API key is sent as `Authorization: Bearer` to `$baseUrl/chat/completions` and to the TTS endpoint, and the gateway token is transmitted as the first WebSocket frame. The project's own deployment guide instructs users to configure plain-http LAN endpoints, so the credential traverses the local network unencrypted and is recoverable by anyone who can observe that segment. Critically, Android's cleartext policy does not prevent this: Flutter's HTTP/WebSocket stack is implemented in the Dart VM and never consults it, and Flutter's own equivalent gate is permissive by default on Android.

## Impact

A passive attacker positioned on the same network segment as the device — the home or office LAN that the project's own deployment guide targets with `http://192.168.1.100:8642/v1` — can read the bearer credential directly from the wire: the LLM API key from the `Authorization: Bearer` header of `/chat/completions` (and of the TTS request), or the Hermes gateway token from the first WebSocket frame. Either credential grants the holder the user's authority on that infrastructure: API spend and conversation access on the LLM endpoint, and device-tool invocation through the operator's gateway. Because the token is provisioned by scanning a QR code, an attacker who can present a QR code can also supply the cleartext `http://` gateway URL that produces the exposure. An on-path attacker able to modify the cleartext stream can additionally alter request and response content (integrity impact), though that requires active interception rather than passive observation. The exposure applies to every Android version the build supports, because the platform's cleartext restriction is not consulted by this application's network stack.

## Counterevidence

Actively sought constraints. (a) The strongest counterargument was that Android blocks cleartext by default, which would have limited this to API 26/27 devices — that argument is disproven, not merely unverified: the application's HTTP and WebSocket traffic does not go through the Android/OkHttp stack that enforces the policy, and Flutter's own equivalent gate is permissive on Android because the embedding never enables it. (b) On the Tailscale topology (`http://100.x.y.z:8642/v1`) the traffic is carried inside Tailscale's WireGuard tunnel and is therefore encrypted on the wire despite the `http://` scheme, so that documented configuration is materially less exposed than the LAN one; the LAN guidance (`http://192.168.1.100:8642/v1`) has no such protection. This narrows one deployment variant but does not affect the plain-LAN case. (c) The cleartext tolerance is deliberate rather than accidental: the test suite pins the accepted scheme set and exercises `http://`/`ws://` acceptance cases, so this is a product decision, which is why the remediation is framed as a policy change with an explicit migration cost. (d) A redirect to a third-party origin does not leak the credential, because `dart:io` strips sensitive headers on cross-origin redirects — checked and excluded. (e) No TLS misconfiguration was found that would also expose users on TLS endpoints: no custom HTTP client adapter, certificate callback or trust-store override exists in the application code, so the platform trust store is authoritative for `https`/`wss`. (f) Exploitation requires the attacker to already hold a network position on the segment (or to induce the user to scan an attacker-supplied QR code), and requires the user or operator to have configured a cleartext endpoint; neither is free, and both are reflected in the attack-vector and attack-complexity metrics.

## Confidence Rationale

Static source-only audit: no APK, emulator or device was available, so no request was ever executed against a live endpoint and this finding is explicitly **unconfirmed, not dynamically validated**. The application-layer facts are established directly from source: cleartext schemes are admitted by all four validators, and each credential-bearing client attaches the stored secret to the resulting URL. The platform-layer question that previously set the affected population has since been resolved from authoritative engine and SDK sources at the exact Flutter revision this repository pins: the connection gate is permissive by default and the Android embedding does not enable the strict mode, so `http://` and `ws://` are functional on every supported API level. What remains unexecuted is the end-to-end demonstration — a real capture showing the credential on the wire — which is why the confidence is medium rather than high.

**Deployment context.** This is not a hypothetical configuration: the project's own guide instructs users to use plain-http endpoints for the local-LAN topology — `http://192.168.1.100:8642/v1` (docs/connecting-to-remote-hermes.md:176), with the profile token defined as the value of `API_SERVER_KEY` (:178) — and for the Tailscale topology `http://100.x.y.z:8642/v1` (:161).

**Why the platform does not stop it.** Android's cleartext restriction (`usesCleartextTraffic` / `network-security-config`) is enforced by the Java/OkHttp/Conscrypt stack. This application does not use that stack for its API traffic: it uses Dart's `dart:io` `HttpClient`, reached through the Dio IO adapter, and `dart:io` never consults the Android policy. Flutter substitutes its own equivalent gate, and that gate is **permissive by default on Android**:

1. `dart:io` invokes an embedder hook before opening any connection — declared as `void Function(Uri) _httpConnectionHook = (_) {};` in the SDK's `_http/embedder_config.dart` and called from `_http/http_impl.dart` in `_openUrl`. The default implementation allows everything.
2. Flutter replaces that hook with `_getHttpConnectionHookClosure(bool mayInsecurelyConnectToAllDomains)` in the engine's `lib/ui/hooks.dart`, wired up by `lib/io/dart_io.cc`. It permits the connection when `mayInsecurelyConnectToAllDomains` is true or the URI scheme is `https`, and otherwise throws `UnsupportedError('Non-https connection ...')`.
3. That flag defaults to permissive: `bool may_insecurely_connect_to_all_domains = true;` in the engine's `common/settings.h`, and `shell/common/switches.cc` only clears it when the process command line carries `--disallow-insecure-connections`.
4. The Android embedder never passes that switch. At the exact Flutter revision this repository pins (recorded in `.metadata`; Flutter 3.47.4), the Android embedding contains no reference to it, and the domain network policy string it forwards is hard-coded empty. The former opt-in manifest mechanism for this (`io.flutter.network-policy` metadata) was removed upstream and this app's manifest declares no such metadata in any case.
5. The WebSocket transport is governed by the same gate: `dart:io`'s `WebSocket.connect` reuses the same `HttpClient` instance, so `ws://` connections are subject to the identical hook.

The consequence is that `http://` and `ws://` endpoints are fully functional for this app on every supported API level, and the credentials attached to them are transmitted in the clear. A `network-security-config` entry would not change this, because the vulnerable path does not read it — the effective control point is the application's own scheme validation.

**What does not leak.** `dart:io` strips `Authorization`, `Cookie` and other sensitive headers when following a cross-origin redirect (its `shouldCopyHeaderOnRedirect` compares scheme, host and port), so the credential is not exposed by a redirect to a third-party origin. The exposure is the direct cleartext request to the configured origin.

## Remediation

1. Restrict the accepted gateway schemes to the TLS variants. `acceptedGatewayUrlSchemes` (lib/domain/services/gateway/gateway_url.dart:15) is the shared contract consulted by the profile form, the settings form and the gateway client, so narrowing it to `https` and `wss` closes those entry points in one change and `isAcceptableGatewayUrl` then rejects cleartext URLs before they can be stored.
2. Reject the `http` scheme explicitly in the pairing parser (lib/domain/tools/pairing/pairing_parser.dart:53-56) so a scanned QR code can never select a cleartext transport, and update the parser's error message so it no longer advertises HTTP as acceptable.
3. Apply the same TLS requirement to the two duplicated validators (lib/presentation/screen/settings/cubit/settings_cubit.dart:118-121, lib/presentation/screen/server_profiles/cubit/server_profile_cubit.dart:97-100) and to the settings form field validator (lib/presentation/screen/settings/settings_screen.dart:417-420), so the contract cannot drift between entry points.
4. Migrate or reject already-persisted cleartext configuration. The validators only govern new input; a device that already stored an `http://` base URL will keep using it. Reject a non-TLS base URL when settings are read from secure storage (or clear the stored value once), so the credential can never be attached to a legacy cleartext endpoint.
5. Do not rely on the Android network security policy for this issue. Declaring `android:networkSecurityConfig` with `cleartextTrafficPermitted="false"` is worthwhile defence-in-depth for any Java-side plugin traffic, but it does not govern this application's HTTP or WebSocket stack, which does not consult it. The effective control is the scheme validation in the application code. (If the platform policy is added, it must be accompanied by the code change, or the credential path remains open.)
6. Update the deployment documentation (docs/connecting-to-remote-hermes.md:161 and :176) to stop presenting `http://` endpoints as the standard option, and instead point at the TLS options already documented in the same guide (Cloudflare Tunnel, or an Nginx/Caddy TLS reverse proxy).
7. Update the test suite to assert the new contract: the cases in test/domain/services/gateway/gateway_url_test.dart that accept `http://`/`ws://` become rejection cases, and add a case asserting that a cleartext profile is refused before any socket is opened.

## Fix Verification

Gates worked in this source-only audit (no APK, emulator or device was available, so no test, analyzer or formatter run was possible):

1. Security closure (reasoned against the patched source, not executed). After the patch, `acceptedGatewayUrlSchemes` contains only `https`/`wss`, so `isAcceptableGatewayUrl()` returns false for every cleartext URL; the profile form and the connection probe both validate through that predicate, and the settings form, the settings cubit and the profile cubit each reject a non-`https` scheme directly. A cleartext base URL can therefore no longer be saved, `SecureStorageService` cannot hold one for a new configuration, and the credential-attaching call sites can only ever see an `https`/`wss` endpoint.
2. Bypass review (reasoned, with the residual named). The credential-attaching sites were enumerated in full — the chat client, the TTS client, the connection probe and the gateway auth frame — and all four obtain their URL from the stored configuration that the patched validators gate, so one change set covers them. Alternate input classes considered: an uppercase scheme is lower-cased by the predicate before the set test; a scheme-relative `//host` form carries no scheme and was already rejected; a bare host is rejected by the predicate (though `normalizeGatewayUri` would still prepend `ws://` for scheme-less input, that value can no longer reach it from the UI). **Residual, deliberately not patched:** a cleartext URL persisted by a previous app version is still used as-is, because these validators only govern new input — this is why remediation step 4 calls for rejecting a non-TLS value at read time or clearing it once, and it must be done in the same change for the boundary to be fully closed.
3. Preserved behaviour. `https`/`wss` URLs, host validation, path defaulting (`/device/ws`) and the existing user-facing error strings are unchanged. The intended behaviour change is that plain-http endpoints — including the LAN example in the deployment guide — are now refused at configuration time with the existing validation message.
4. Repository checks: NOT executed — no Flutter/Dart toolchain with resolved dependencies was available, so no test or analyzer run was possible. This gate is an explicit gap. Note that `test/domain/services/gateway/gateway_url_test.dart` currently pins the cleartext-accepting behaviour and will fail until those cases are converted to rejection cases, as described in the proposed change description.

Minimal-change judgement: the fix is expressed inside the existing single-source-of-truth predicate plus the three other validators that duplicate its test, introduces no new abstraction, and does not fold in unrelated hardening. It deliberately does not touch the non-credential fetchers, which carry no stored secret.
