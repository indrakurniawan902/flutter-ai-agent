# Tools with device-state side effects are classified Tier 1 "Read-Only / Ambient" and auto-execute with no authorization gate

**ID:** vuln-0005
**Severity:** MEDIUM
**Found:** 2026-09-15 05:51:17 UTC
**Target:** /workspace/flames-audit-t196
**CWE:** CWE-863
**CVSS:** 6.5
**Confidence:** Medium
**Fix Effort:** Low

## Description

The agent tool registry documents Tier 1 as **"Read-Only / Ambient (auto-execute)"**, but six registered tools that modify device state, send user-visible output, or destroy user data are assigned to Tier 1 and therefore execute with no permission check and no approval prompt. Two of them (`send_local_notification`, `save_memory`) additionally give an injected instruction a user-visible spoofing primitive and a persistence foothold, because saved memories are re-injected into every subsequent model request as a `role: system` message. The misclassification is provably a defect rather than policy: `send_local_notification` (Tier 1, auto-executes) and `schedule_reminder` (Tier 3, requires a user tap) are registered against the same notification service in the same method, so sending a notification immediately is ungated while scheduling one for later is gated.

## Impact

Once the on-device agent has decided to call one of these tools, the action executes with no permission evaluation and no user confirmation. The demonstrated (static) consequences are: arbitrary attacker-influenced text written to the system clipboard; arbitrary user-visible local notifications presented under the application's identity (a spoofing primitive that can impersonate a bank, security, or system alert); the ability to start and stop the foreground service, acquire and release wake locks, and set the Quick Settings tile state; registration of persistent geofence monitoring; and destruction of the user's stored memory vault by id or key with no confirmation. Because `save_memory` writes to a SQLite vault whose contents are re-injected into every subsequent model request as a `role: system` message, an instruction that reaches the prompt can also persist attacker-authored text inside the system-role portion of the conversation, surviving the turn, the session, and application restarts. The affected scope is the local device state and local application data of the user who runs the agent; no disclosure of restricted data was demonstrated.

## Counterevidence

The strongest case against this finding, argued in full:

**1. Model cooperation is required and is stochastic.** Nothing here forces the model to call a tool. An attacker who lands injected text still depends on a non-deterministic model choosing the affected tool. This genuinely limits the finding and is why attack complexity is rated High rather than Low.

**2. Attacker-controlled text must first reach the prompt.** That requires either the user having granted Flames notification-listener access to a hostile app, or the agent fetching attacker content. This is a real precondition and is reflected in the rating.

**3. `POST_NOTIFICATIONS` must have been granted** for the notification tool to be observable, and the notification is only user-visible, not attacker-visible. This limits the spoofing impact but does not neutralize the ungated clipboard, memory, geofence, and background-service tools.

**4. Some of these tools are low-impact in isolation.** `speak_text` and `open_map_navigation` were deliberately excluded from the fix set for that reason, and `register_geofence` on its own is modest. The finding does not rest on them; it rests on the persistent memory write, the ungated destruction of stored data, the user-visible notification, and the system-clipboard write.

**5. The strongest argument that this is intended, not a defect:** Tier 1 could be read as "requires no OS runtime permission" rather than "read-only". Under that reading, `send_local_notification` is Tier 1 because it needs no permission prompt of its own, and `schedule_reminder` is Tier 3 because scheduling is a destructive-style operation. That reading fails for three independent reasons. First, the enum's own documentation states the semantics: Tier 1 is "Read-Only / Ambient", and Tier 3 is "State-Modifying / Destructive" — under the stated contract, a tool that modifies state cannot be Tier 1. Second, under the "no OS permission" reading the classification is still internally inconsistent: sending a notification immediately and scheduling one for later both call the same service and neither requires a distinct runtime permission beyond `POST_NOTIFICATIONS`, yet they are placed in opposite tiers. Third, the tool descriptions written by the authors themselves contradict their own tier assignment — `schedule_reminder` is described as "(requires user confirmation)" while the immediate notification carries no such warning, even though it is the more direct action. The application's own bundled skill metadata also labels the notification tools "Tier 2 Perm", a third answer that matches neither assignment.

**6. What was checked for a mitigating control and not found:** no input validation, no approval prompt, no permission evaluation, and no tool-call allowlist applies to these six tools on the model path; `_processPendingToolCalls` contains exactly one gating branch and it is the Tier 3 equality test; the registry contains no Tier-1 branch; and the tools are enabled by default. The only reachable stop is `isToolEnabled`, which defaults to true.

**7. What genuinely limits the persistence claim:** stored memory is re-injected only when it is retrieved by the FTS search performed for the current user message (`agent_cubit.dart:519-527`, `searchMemories(prompt.trim(), 3)`), so injected content must match the words of a later prompt to resurface. This narrows the foothold but does not remove it: the attacker chooses the memory key and content and can target likely prompt vocabulary, and `search_memories`/`list_memories` remain available to read entries back.

**8. Additive (revision) — the retrieval precondition is cheap for the attacker, and the omission is a defect rather than policy.** The retrieval constraint in point 7 was tested directly. `_sanitizeFtsQuery` joins all terms with `OR` and `_extractWords` retains stopwords, so only one term needs to match; a hostile memory whose content includes ordinary words such as `travel trip preference` is returned for the prompt `plan my travel trip` (one row, rank -0.0000). An attacker who can author memory content can therefore include high-frequency vocabulary to guarantee retrieval without knowing the user's later prompt, and the content persists across sessions, so it re-injects on every turn that retrieves it.

The "intended behaviour" reading in point 5 is further weakened by the codebase's own inconsistency: it ships a prompt-injection scanner (`lib/domain/services/skills/skill_security_scanner.dart`) whose patterns cover exactly this payload class and which is wired into the skill-import path (`skill_import_service.dart:44-68`), yet nothing screens memory content before it is promoted into the system role. The same string that the skill path would flag with `new_instructions_header`, `do_not_tell_user` and `chatml_delimiters` is accepted verbatim by `save_memory`. The capability to screen attacker-authored text therefore exists and is considered appropriate by the maintainers; the memory path simply omits it. Neither point neutralizes the model-cooperation and attacker-reachability constraints above, which remain the reason this is rated Medium rather than High.

## Confidence Rationale

Static source-only audit with an executed string-level reproduction. No device, emulator or `adb` was available, so the auto-execution of these tools, the system-role re-injection on a running device, and LLM compliance with the injected text were never executed and are not claimed. The string-level proof (Python 3 with `sqlite3` FTS5, reproducing the schema and query path at the cited lines) does establish that the hostile content is stored verbatim, retrieved by the application's own search for an ordinary prompt, and interpolated unchanged into a `role: system` message with no untrusted-data framing and no delimiter escaping; it cannot establish that a model would act on it. The repository's own integration tests exercise three of the affected tools through the real agent loop without an approval step, corroborating the ungated path, but that is likewise not an end-to-end exploit. No Dart or Flutter SDK was present in the assessment environment, so the attached Dart regression test was not executed and the repository's analyzer and test suite were not run.

## What Would Change This Severity

Demonstrating on a running device that a notification-delivered injection causes the model to emit a tool call for one of these tools with no user tap would raise this to High; conversely, evidence that these tools are in practice never advertised to the model — for example a skill policy that reliably disables them before every run — would lower it.

## Technical Analysis

## The documented contract

`lib/domain/tools/chat/security_policy.dart:1-5` defines the tier contract, and `:17-19` defines the predicate that the contract implies:

```dart title=lib/domain/tools/chat/security_policy.dart startLineNumber=1 endLineNumber=19
/// Security tiers for tool execution within the agent loop.
///
/// Tier 1: Read-Only / Ambient (auto-execute).
/// Tier 2: Sensitive / Permissioned (auto-execute only if runtime permission is granted).
/// Tier 3: State-Modifying / Destructive (HITL confirmation required).
enum SecurityTier {
  tier1Auto,
  tier2Permission,
  tier3Hitl,
}
...
  /// Whether the tool can be auto-executed without user confirmation.
  static bool isAutoExecute(SecurityTier tier) {
    return tier == SecurityTier.tier1Auto;
  }
```

Tier 1 is therefore defined as *read-only*, and Tier 3 as *state-modifying / destructive*.

## The single enforcement point

Tool calls generated by the model are queued at `agent_cubit.dart:1083-1087` and consumed by `_processPendingToolCalls` (`agent_cubit.dart:712`). The only branch that can stop execution is the Tier 3 equality test:

```dart title=lib/presentation/screen/chat/cubit/agent_cubit.dart startLineNumber=752 endLineNumber=769
      // Tier 3: Pause loop and wait for HITL approval.
      if (registered.securityTier == SecurityTier.tier3Hitl) {
        final request = ToolCallRequest(
          id: callId,
          name: toolName,
          parameters: arguments,
        );
        _pendingToolCall = request;
        emit(WaitingApproval(request));
        return; // Execution pauses until approveAction or rejectAction
      }

      // Tier 1 & Tier 2: Auto-execute.
      emit(ExecutingTool(toolName, arguments: arguments));
      final execResult = await _toolRegistry.executeTool(
        toolName,
        arguments,
      );
```

Tier 1 and Tier 2 both fall through to `executeTool`. The registry's own gate then evaluates only the Tier 2 case:

```dart title=lib/domain/tools/chat/tool_registry.dart startLineNumber=238 endLineNumber=262
  Future<Either<Failure, String>> executeTool(
    String name, [
    Map<String, dynamic> arguments = const {},
  ]) async {
    try {
      final tool = _tools[name];
      if (tool == null) {
        return Left(ServerFailure('Tool not found: $name'));
      }
      if (!isToolEnabled(name)) {
        return Left(ServerFailure('Tool $name is disabled by skill policy.'));
      }
      if (SecurityPolicy.requiresPermission(tool.securityTier) &&
          tool.checkPermission != null) {
        final granted = await tool.checkPermission!();
        if (!granted) {
          return Left(PermissionFailure('Permission denied for tool: $name'));
        }
      }
      return await tool.execute(arguments);
```

For a Tier 1 tool neither `requiresPermission` nor the HITL branch is reachable, so `tool.execute(arguments)` runs unconditionally. The second caller, the gateway RPC receiver, has the same shape: `gateway_rpc_receiver.dart:89` tests `SecurityPolicy.requiresHitl(tool.securityTier)` and then calls `toolRegistry.executeTool` at `:148`, so a remote gateway frame also auto-executes Tier 1 tools. `SecurityPolicy.isAutoExecute` — the predicate that expresses the "read-only" contract — is **dead code**: a repository-wide search finds it only at its own definition.

Tools are enabled by default (`tool_registry.dart:210` `putIfAbsent(tool.name, () => true)` and `:222` `_toolEnabledStates[name] ?? true`), so no skill policy needs to be configured for these tools to be advertised to the model.

## The misclassified tools

Six registered tools carry `securityTier: SecurityTier.tier1Auto` despite performing state-modifying work, and none of them declares a `checkPermission` callback (so reassigning any of them to Tier 2 would be a silent no-op under `:250-251`, which requires `checkPermission != null`):

- `clipboard_write` (`tool_registry.dart:279`, tier at `:291`) — writes arbitrary text to the system-wide clipboard (`:292-293`).
- `send_local_notification` (`:692`, tier at `:708`) — sends a user-visible notification with fully model-controlled `title` and `body`.
- `save_memory` (`:884`, tier at `:899`) — writes an entry into the persistent memory vault.
- `delete_memory` (`:921`, tier at `:930`) — deletes a memory by id or key.
- `register_geofence` (`:953`, tier at `:968`) — registers persistent geofence monitoring.
- `manage_background_service` (`:1168`, tier at `:1213`) — starts/stops the foreground service, acquires/releases wake locks, and sets the Quick Settings tile state.

Three further Tier 1 tools with side effects (`speak_text` `:1138`, `open_map_navigation` `:1462`, `list_device_files` `:809`) are noted but not part of this report's fix set.

## Persistence amplifier: `save_memory` → system-role re-injection

`save_memory` writes through `local_memory_service.dart:498` `saveMemoryFormattedJson` → `saveMemory` → `sqlite_memory_datasource.dart:190`, which inserts into the `memories` table of the on-disk database `flames_memory.db` (`sqlite_memory_datasource.dart:16`). The agent then re-injects those rows into the request as a system message on every turn of the loop:

```dart title=lib/presentation/screen/chat/cubit/agent_cubit.dart startLineNumber=906 endLineNumber=914
    final serializedMessages = _messages.map((m) => m.toWireJson()).toList();
    if (_activeMemories.isNotEmpty) {
      final memoryPrompt =
          'Relevant User & Device Memories:\n${_activeMemories.map((m) => '- ${m.key}: ${m.content}').join('\n')}';

        'role': 'system',
        'content': memoryPrompt,
```

This block sits inside `_runLoop` (`:864`), which recurses at `:831` after each tool batch, so the memory block is rebuilt and re-inserted at the head of the message list on every turn of the run; `_activeMemories` is re-populated per user message at `:519-527` via `searchMemories(prompt.trim(), 3)`. There is no untrusted-data delimiter and no instruction telling the model to treat the block as data, so attacker-authored `key`/`content` text is presented in the system role, where embedded newlines can impersonate the surrounding prompt structure. The repository's own integration test asserts this behaviour as a feature: `test/integration/e2e_fase3_intelligence_test.dart:281-296` drives the agent to `save_memory` with `{"key":"secops_token","content":"SecOps recovery OTP is 948210"}` and `:310-318` comments that the cubit "injects memory into system prompt".

Deletion is equally ungated: `delete_memory` → `local_memory_service.dart:570` `deleteMemoryFormattedJson` → `sqlite_memory_datasource.dart:343` `deleteMemory` / `:357` `deleteMemoryByKey`, both issuing `db.delete('memories', ...)` with no confirmation step anywhere on the path.

## How untrusted text reaches the model

Notification titles and bodies are read from other applications by `FlamesNotificationListenerService.kt:58-91` (title/text extracted at `:62-69` into a buffer at `:85-90`), surfaced through `MainActivity.kt:124-128` and `notification_triage_service.dart:53-65`, and returned to the model as an ordinary tool result. Any installed application controls that text once the user has granted notification access. Remote model output, remote gateway frames, and content the agent fetches from the network are equivalent entry points.

```python
    """_extractWords: strip every non-[A-Za-z0-9_] char, keep words >= 2 chars."""
```

## Remediation

Reclassify every tool whose execution modifies device state, produces user-visible output, or destroys stored data so that it is no longer Tier 1. Because the registry only evaluates a permission callback when one is present, and none of these six services defines one, assigning Tier 2 would not by itself introduce any enforcement; the immediate and reliable correction is to move these tools to the human-in-the-loop tier, and to add permission callbacks only where an automatic, non-interactive path is genuinely required.

Specifically: move the immediate local-notification tool, the clipboard write tool, the memory write and delete tools, the geofence registration tool, and the background-service control tool from the automatic tier to the confirmation tier, and update the tier documentation in the security policy so that Tier 1 is explicitly reserved for tools with no device-visible or persistent side effect.

Independently of the tier assignment, stop presenting stored memory content to the model as if it were trusted system context. Wrap the memory block in an explicit untrusted-data directive and escape the stored keys and content so that embedded line breaks cannot impersonate the surrounding conversation structure.

Finally, update the test suite in the same change: several existing tests assert the current tiers and several integration tests exercise these tools through the agent loop without an approval step, so they will need to expect the approval gate instead. Consider adding a regression test that fails if any tool whose executor performs a write, a notification, a clipboard operation, or an external launch is registered at the automatic tier.

**Gate 1 — Security closure.** Re-traced the model path through the patched source. The gate at `agent_cubit.dart:753` compares the registered tier against `SecurityTier.tier3Hitl`; after the change all six tools match that comparison, so `_processPendingToolCalls` emits `WaitingApproval` and returns at `:761` before reaching `executeTool` at `:766`. For the persistence fix, the memory block is now preceded by an explicit data-not-instructions directive and every key and content value is JSON-encoded, so embedded newlines and quotes can no longer terminate the entry and impersonate a following system or user turn. **Not executed** — closure is a static re-trace; the PoC in `poc_script_code` was written but not run.

**Gate 2 — Bypass review.** Re-read the diff against the finding rather than against the reasoning that produced it. Sibling call sites of `executeTool` were enumerated across the repository and there are exactly three: `agent_cubit.dart:611` (`approveAction`, which runs only after a user approval and is correct), `agent_cubit.dart:766` (gated after the change), and `gateway_rpc_receiver.dart:148` (gated after the change). Two residual sibling instances are deliberately **not** covered by this change and must not be mistaken for closed: (a) `speak_text` (`:1138`), `open_map_navigation` (`:1462`), and `list_device_files` (`:809`) remain Tier 1 with side effects; (b) the Tier 2 tools that declare no `checkPermission` callback still auto-execute because `tool_registry.dart:250-251` short-circuits when the callback is null — that is a separate root cause with a separate owner. Public API and error semantics are unchanged: `executeTool` returns the same `Either<Failure, String>` shape, and the new `WaitingApproval` pause uses the existing approval flow already exercised by the Tier 3 tools. ## Assumptions
